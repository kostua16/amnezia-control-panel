# Quick Plan: PR #1218 workflow improvement intake

## Source
- PR #1218: fix(ci): trigger shadow sweeps on orchestrator completion
- URL: https://github.com/kostua16/amnezia-control-panel/pull/1218

## Summary
PR 1218 moves shadow sweep triggers from cron-only to orchestrator-completion (workflow_run, run-ID sampling), splits concurrency into job-level groups, and adds a SHADOW_SWEEP_SUMMARY telemetry line in scan-pr-flow.cjs. Diff is coherent with base: 'scan-pr-flow.cjs:270' returns { status: 'off' } unless mode is 'shadow' so the new doc wording ("Only 'shadow' enables it") is accurate; telemetry lives in 'summary()' so 'ok' and 'unavailable' both emit; tests pin the exact 'if' string, permissions, concurrency groups and JSON schema. Two gaps worth follow-up: (1) the shadow 'if' ignores 'workflow_run.conclusion' and telemetry records neither the upstream conclusion nor run ID, so a scan after a cancelled/failed orchestrator run is indistinguishable from one after success — graduation analysis will misattribute would-wakes; (2) SHADOW_SWEEP_SUMMARY exists only in run logs, with no aggregation path toward graduation. Roadmap-scale: formalize the shadow→active graduation protocol and standardize the workflow_run trigger policy — this PR re-derived conclusion/ref/sampling/concurrency rules that four other workflow_run consumers (pr-flow.yml, fix-pr.yml, auto-cover-review.yml, fix-branch.yml) each handle ad hoc, and it fixed a real latent bug where the old top-level concurrency gave workflow_run-triggered shadow runs the 'pr-flow-watchdog' group with cancel-in-progress=true — github.event.schedule is empty on those events, so the schedule-keyed expression fell through and a shadow scan could cancel a live recovery run (scan-only cron was already isolated in the 'pr-flow-sweep-shadow' group with cancel-in-progress=false on base).

## Quick Wins
- Record upstream orchestrator conclusion and run ID in SHADOW_SWEEP_SUMMARY telemetry -- The new trigger 'workflows: ['PR Orchestrator'], types: [completed]' fires on failure and cancelled runs too, but the shadow job 'if' in pr-flow-watchdog.yml checks only run-ID sampling and ref — never 'github.event.workflow_run.conclusion'. A would-wake logged after an orchestrator run that was cancelled by concurrency supersession means something different from one after success, and SHADOW_SWEEP_SUMMARY cannot tell them apart. Change: add 'PR_FLOW_SWEEP_UPSTREAM_CONCLUSION: ${{ github.event.workflow_run.conclusion }}' and 'PR_FLOW_SWEEP_UPSTREAM_RUN_ID: ${{ github.event.workflow_run.id }}' to the scan step env — triggerEvent needs no new env var because it is already wired (scan-pr-flow.cjs:424 passes 'triggerEvent: process.env.GITHUB_EVENT_NAME' and the telemetry object at :290 already emits it), and a second 'PR_FLOW_SWEEP_TRIGGER_EVENT' source could drift from the first — github.event.workflow_run is null on the schedule/workflow_dispatch triggers the shadow job keeps, so the upstream envs resolve to empty strings there and 'no upstream run' must stay distinguishable from a cancelled or failed upstream — surface them as 'upstreamConclusion'/'upstreamRunId' in the telemetry object in scan-pr-flow.cjs (emit null upstream fields on non-workflow_run triggers, not empty strings), and update the exact-env deepEqual in scan-pr-flow.test.cjs ('shadow listens for orchestrator completions...') plus the C13 shadow row in docs/workflow-e2e-scenarios.md, including an assertion for the absent-upstream schedule/dispatch case. Read-only, no behavior change to the scan itself. (owner: gh-workflow-engineer, type: quick-task)
- Persist SHADOW_SWEEP_SUMMARY telemetry as a per-run artifact for aggregation -- The PR's stated purpose for the telemetry line is measuring shadow health, but it lands only in stdout logs (scan-pr-flow.cjs 'summary()'), and no API path recovers it cheaply: the Actions REST API exposes jobs and step names/conclusions but no step-summary body, and the downloadable run logs do not include it — '$GITHUB_STEP_SUMMARY' markdown is rendered only on the run summary page, so a scheduled aggregator would still need authenticated HTML scraping of each run page, which is the work this quick win is meant to remove. Change: follow the MON-E06 pattern (monitor-amnezia-control-panel-github-runs.yml 'Aggregate per-run cost telemetry' job + aggregate-run-costs.cjs) — have the scan job append the JSON line to a durable per-run JSONL artifact uploaded via actions/upload-artifact (name keyed on run ID, retention-days covering the graduation window), optionally also append the line to '$GITHUB_STEP_SUMMARY' for human reading only (guard on the env var being set, keep the log line unchanged so the existing SHADOW_SWEEP_SUMMARY parsing tests stay green), and add a test in scan-pr-flow.test.cjs covering the JSONL append and the no-op when the env var is absent. Graduation analysis (phase suggestion below) then downloads artifacts per run instead of scraping logs or step summaries. (owner: gh-workflow-engineer, type: quick-task)

## pr1218.x Phase Candidates
- pr1218.1: Shadow-to-active graduation protocol for PR flow sweep -- documentation.md now promises 'roughly 20%' sampling plus cron/dispatch exemptions and per-group coalescing for shadow scans (pr-flow-watchdog.yml shadow job), but nothing consumes SHADOW_SWEEP_SUMMARY at scale: the graduation decision is currently a manual log-grep by whoever remembers, and graduation is not a variable flip: no 'active' value exists — the shadow job gates on vars.PR_FLOW_SWEEP_MODE == 'shadow' (pr-flow-watchdog.yml:59) and scan-pr-flow.cjs:270 returns { status: 'off' } for any other value, so setting 'active' today would silently disable the sweep and grant no wake authority. Milestone work: a scheduled aggregation job/script that collects the telemetry artifacts across recent pr-flow-watchdog runs (per the quick task above) and defines explicit graduation criteria, stratified by triggerEvent and upstreamConclusion over candidatePrs counts and the 'would wake PR #n' log lines — not over comparison diff counts: 'comparison'/'comparisonDiffs' are computed only when recoverySlot is true (scan-pr-flow.cjs:277, :391), i.e. only on recovery-cron scans where workflow_run.conclusion is absent, so a diff-count cross-tab by upstreamConclusion is structurally empty for exactly the workflow_run rows this phase exists to measure (widening the comparison to every scan was considered and rejected — it would spend extra REST status reads on every orchestrator-triggered scan against the rate-limit budget the shadow scan already consumes). Criteria: N clean recovery comparisons on recovery-cron scans, zero unknown-evidence streak, and a stable would-wake rate on workflow_run scans with successful upstream conclusions. Graduation itself requires new code — implementing the active mode (job gate, wake path, guardrails) — not a variable change. Dispatch authority has a single scope answer: the active mode's only new authority is to wake the existing watchdog recovery path; it never dispatches fix-pr/fix-review/orchestrator runs itself, and dispatch authority stays with the watchdog before and after graduation — graduation transfers the scan, nothing else. Cites: scan-pr-flow.cjs telemetry block, pr-flow-watchdog.yml shadow job, documentation.md 'PR Flow sweep shadow'. (owner: gh-workflow-engineer)
- pr1218.2: Standardize workflow_run trigger policy across watcher workflows -- This PR hand-rolled a complete workflow_run trigger policy for pr-flow-watchdog.yml — default-branch ref guard ('github.ref == format('refs/heads/{0}', ...)', which passes for workflow_run, schedule, and a default-branch workflow_dispatch (see scan-pr-flow.test.cjs:130) — the expression is event-agnostic and the checkout pin to 'github.sha' does not change github.ref), run-ID sampling, conclusion-agnostic 'completed' type, and job-level concurrency coalescing — and fixed a latent bug in the process (the old top-level concurrency keyed on github.event.schedule, which is empty for the new workflow_run trigger and other non-schedule events, so those shadow runs fell through to the 'pr-flow-watchdog' group with cancel-in-progress=true and could cancel a live recovery run — scan-only cron was already isolated in 'pr-flow-sweep-shadow' with cancel-in-progress=false on base). Four other workflows consume 'workflow_run' today: pr-flow.yml:17 (the PR Orchestrator itself, listening on CI/PR Policy/Code Review/Dependency Review/PR Improve/PR Finalizer completions, conclusion-agnostic (no workflow_run.conclusion filter — its gates read only pull_requests and display_title) with per-PR concurrency groups), fix-pr.yml:25, fix-branch.yml:22, auto-cover-review.yml:6 (whose scan-mode coalescing is C10 in docs/workflow-e2e-scenarios.md), each with its own ad-hoc take on conclusion filtering and grouping. Milestone work: extract the rules into one documented checklist in docs/workflow-e2e-scenarios.md plus shared characterization tests using the existing .github/workflows/scripts/__tests__/helpers/github-expression.cjs (evaluateCondition/renderTemplate — proven by this PR's test style), so the next workflow_run consumer doesn't rediscover why its watcher cancels real work.
