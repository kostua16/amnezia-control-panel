# Quick Plan: PR #1218 workflow improvement intake

## Source
- PR #1218: fix(ci): trigger shadow sweeps on orchestrator completion
- URL: https://github.com/kostua16/amnezia-control-panel/pull/1218

## Summary
PR 1218 moves shadow sweep triggers from cron-only to orchestrator-completion (workflow_run, run-ID sampling), splits concurrency into job-level groups, and adds a SHADOW_SWEEP_SUMMARY telemetry line in scan-pr-flow.cjs. Diff is coherent with base: 'scan-pr-flow.cjs:268' gates on mode==='shadow' so the new doc wording ("Only 'shadow' enables it") is accurate; telemetry lives in 'summary()' so 'ok' and 'unavailable' both emit; tests pin the exact 'if' string, permissions, concurrency groups and JSON schema. Two gaps worth follow-up: (1) the shadow 'if' ignores 'workflow_run.conclusion' and telemetry records neither the upstream conclusion nor run ID, so a scan after a cancelled/failed orchestrator run is indistinguishable from one after success — graduation analysis will misattribute would-wakes; (2) SHADOW_SWEEP_SUMMARY exists only in run logs, with no aggregation path toward flipping PR_FLOW_SWEEP_MODE to active. Roadmap-scale: formalize the shadow→active graduation protocol and standardize the workflow_run trigger policy — this PR re-derived conclusion/ref/sampling/concurrency rules that three other workflow_run consumers (fix-pr.yml, auto-cover-review.yml, fix-branch.yml) each handle ad hoc, and it fixed a real latent bug where the old top-level concurrency let scan-only-cron shadow runs share the 'pr-flow-watchdog' group with cancel-in-progress=true, cancelling real recovery.

## Quick Wins
- Record upstream orchestrator conclusion and run ID in SHADOW_SWEEP_SUMMARY telemetry -- The new trigger 'workflows: ['PR Orchestrator'], types: [completed]' fires on failure and cancelled runs too, but the shadow job 'if' in pr-flow-watchdog.yml checks only run-ID sampling and ref — never 'github.event.workflow_run.conclusion'. A would-wake logged after an orchestrator run that was cancelled by concurrency supersession means something different from one after success, and SHADOW_SWEEP_SUMMARY cannot tell them apart. Change: add 'PR_FLOW_SWEEP_UPSTREAM_CONCLUSION: ${{ github.event.workflow_run.conclusion }}' (and 'PR_FLOW_SWEEP_UPSTREAM_RUN_ID: ${{ github.event.workflow_run.id }}') to the scan step env, surface them as 'upstreamConclusion'/'upstreamRunId' in the telemetry object in scan-pr-flow.cjs, and update the exact-env deepEqual in scan-pr-flow.test.cjs ('shadow listens for orchestrator completions...') plus the C13 shadow row in docs/workflow-e2e-scenarios.md. Read-only, no behavior change to the scan itself. (owner: gh-workflow-engineer, type: quick-task)
- Emit SHADOW_SWEEP_SUMMARY to $GITHUB_STEP_SUMMARY for scrape-free consumption -- The PR's stated purpose for the telemetry line is measuring shadow health, but it lands only in stdout logs (scan-pr-flow.cjs 'summary()'), so any shadow→active decision requires scraping run logs via API. Change: in the same 'summary()' helper, also append the JSON line to '$GITHUB_STEP_SUMMARY' (guard on the env var being set, keep log line unchanged so the existing SHADOW_SWEEP_SUMMARY parsing tests stay green), and add a test in scan-pr-flow.test.cjs covering the write and the no-op when the env var is absent. Graduation analysis (phase suggestion below) then reads step summaries per run instead of full logs. (owner: gh-workflow-engineer, type: quick-task)
