## Findings

### #13: Missing server-side service lifecycle (Critical — Runtime)

**Problem:** `server.mjs` is the custom HTTP+Socket.IO entry point, but it only initializes the WebSocket server. Three critical background services are **never started in production**:

1. **`real-time-broadcaster.ts`** — `startBroadcaster()` is exported but **never called** anywhere in the codebase (grep confirmed). Dashboard stats and resource updates are never pushed to WebSocket clients. The real-time dashboard is dead in production.

2. **`geoIPManager.init()`** — The GeoIP manager singleton is created at module load, but `.init()` (which creates the data directory, loads `geoip.dat`, and starts the 24h refresh scheduler) is **never called** outside of test files. Geo-routing lookups will always return `null` — the country trie is never built from disk. All geo-routing rules silently fail open.

3. **`ServiceMonitor`** — Exported but never instantiated in production. Service auto-restart and status-change alerts do not run.

**Impact:** Two shipped features (real-time monitoring, geo-routing) are functionally broken in the custom server deployment path. There is no `instrumentation.ts` (Next.js lifecycle hook) and no unified `startServices()` call in `server.mjs`.

**Root cause:** During v1.0–v1.1 rapid iteration, services were built and tested in isolation but never wired into the production startup path. The project uses a custom `server.mjs` instead of Next.js's default server, so the standard `instrumentation.ts` pattern was never adopted.

**Fix:** Add `src/instrumentation.ts` (Next.js stable API) that calls `startBroadcaster()`, `geoIPManager.init()`, and optionally `new ServiceMonitor()`. Register the instrumentation hook in `next.config.ts`. This is the canonical Next.js way to run code at server startup. The custom `server.mjs` already calls `app.prepare()`, which triggers instrumentation registration. This single file connects all orphaned singletons.

**Files:** `src/instrumentation.ts` (new), `next.config.ts` (if registration needed), optionally `server.mjs` (cleanup).

### #14: `server-connection.ts` is a non-functional stub (High — Correctness)

**Problem:** `executeOnServer()` in `src/lib/server-connection.ts` is a **complete stub** — it logs "Would execute on remote server" and returns an empty success result. No SSH, no command execution, no real connection. The entire remote server management story (install/unstart/stop services, apply configs, read logs) is non-functional.

Additionally:
- `testConnection()` uses ICMP ping only — it doesn't validate SSH access or the configured port.
- The connection pool (`connectionPool` Map) is in-process memory with no persistence across HMR restarts.
- The module has `TODO` comments acknowledging the stub: "In production, replace with a proper SSH/TCP connection test" and "In production, use the SSH2 library or similar."

**Impact:** Multi-server management features (Phase 8.1–8.4) appear to work in the UI but silently do nothing on remote servers. Admins can add servers and see "connected" status from ping, but any server-side operation is a no-op.

**Fix:** Implement SSH execution using `ssh2` (pure JS, no native deps) or `node-ssh`. Design a `RemoteExecutor` interface with production and test implementations. Wire it through `vpn-services.ts` so `awg`/`3x-ui` commands execute on the correct remote server, not just locally. The `Server` model already stores `hostname` and `port`.

**Files:** `src/lib/server-connection.ts` (rewrite), `src/lib/remote-executor.ts` (new interface + SSH impl), `src/lib/vpn-services.ts` (accept remote executor), package.json (add `ssh2` dep).

### #15: Panel sync API key lookup is O(n) bcrypt (Medium — Performance)

**Problem:** `POST /api/sync/receive` (`src/app/api/sync/receive/route.ts:64-76`) authenticates incoming sync requests by loading **all** active `RemotePanel` records (`findMany` with no filter) and iterating with `bcrypt.compare()` per panel. With N registered panels, every sync receive costs N bcrypt operations (~100ms each), totaling O(N × 100ms).

**Current code:**
```typescript
const panels = await prisma.remotePanel.findMany({ where: { isActive: true } });
for (const panel of panels) {
  const isValid = await bcrypt.compare(apiKey, panel.apiKeyHash);
  if (isValid) { matchedPanel = panel; break; }
}
```

**Impact:** For 1–3 panels (current scale) this costs 100–300ms per sync request. Acceptable now but architecturally wrong — it doesn't scale and every unnecessary bcrypt call is wasted CPU.

**Fix:** Add a `apiKeyFastHash` column (SHA-256 of the plaintext key) to `RemotePanel`. On panel creation/update, compute `sha256(apiKey)` and store it. On sync receive, first `findFirst({ where: { apiKeyFastHash: sha256(receivedKey) } })` — an O(1) indexed lookup — then verify with bcrypt on the single match. This retains bcrypt's security properties while eliminating the linear scan.

**Files:** `prisma/schema.prisma` (add `apiKeyFastHash` column), new migration, `src/app/api/sync/receive/route.ts` (two-step lookup), `src/app/api/panels/route.ts` + `src/app/api/panels/[id]/route.ts` (compute fast hash on create/update), `src/lib/panel-sync-client.ts` (no change — client sends plaintext key).
