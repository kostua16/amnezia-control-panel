# Quick Plan: Fix migration 20260617 — replace non-constant-default ALTERs with table redefines

## Goal

`prisma migrate deploy` fails at `20260617_schema_hygiene_indexes_enums_timestamps` with Prisma error **P3018** → SQLite `Cannot add a column with non-constant default` on any database where `admins` already holds a row. The migration adds `updatedAt` to `admins` and `user_quotas` using `ALTER TABLE ... ADD COLUMN "updatedAt" DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP`, which SQLite (verified on 3.53.4) accepts only on an **empty** table. Fresh CI/Docker databases pass because they are empty at that point; every upgraded database with an existing admin fails, and because `scripts/ensure-prisma-migrated.cjs` (used by `npm run dev` and `npm start`) plus `docker-entrypoint.sh` and `docker/stack-entrypoint.sh` all run `migrate deploy` and abort on failure, the app cannot boot on an upgraded database.

Replace both statements with the table-redefine pattern the same file already uses for `alerts`, `routing_rules`, `servers`, `services` and `user_protocols`, then rebuild the local `prisma/dev.db` from the corrected chain and restore its unique rows from the pre-migration backup.

## Locked design decisions (from investigation — do not revisit)

- **Root cause is proven, not assumed.** `.qwen/tmp/alter-test.cjs` reproduces it deterministically: the identical `ALTER TABLE "admins" ADD COLUMN "updatedAt" DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP` succeeds on a 0-row table and fails on a 1-row table with `Cannot add a column with non-constant default` (sqlite_version 3.53.4).
- **Editing an already-shipped migration in place is acceptable here.** Prisma 7.10 does not verify migration checksums in `migrate status` or `migrate deploy` (empirically probed). The migration is currently *unapplied and failed* on the only database that has it, so there is no successfully-migrated environment to diverge from. `prisma migrate dev` checksum behaviour was not tested — do not run `migrate dev` as part of this task.
- **Target column shape is `"updatedAt" DATETIME NOT NULL` with NO default.** `schema.prisma` declares `updatedAt DateTime @updatedAt` on both `model Admin` (line 68) and `model UserQuota` (line 321); Prisma supplies the value in the client. The `DEFAULT CURRENT_TIMESTAMP` in the broken ALTERs was never in Prisma's own generated DDL and must not be carried into the redefine — keeping it would create drift.
- **Neither table is a foreign-key target.** Grepping every migration for `"admins"` / `"user_quotas"` returns only their own `CREATE TABLE`, the two broken `ALTER`s, and the two `CREATE UNIQUE INDEX` lines. `user_quotas` does have an *outgoing* FK (`user_quotas_userId_fkey` → `users(id)`), so each redefine still gets the file's existing `PRAGMA defer_foreign_keys=ON; PRAGMA foreign_keys=OFF; … PRAGMA foreign_keys=ON; PRAGMA defer_foreign_keys=OFF;` wrapper. `defer_foreign_keys` is the pragma that actually works inside Prisma's per-migration transaction.
- **Seed values.** `admins` has `createdAt`, so seed `updatedAt` from it (mirrors `new_alerts`/`new_routing_rules`/`new_servers`/`new_services`). `user_quotas` has **no** `createdAt` column, so seed `updatedAt` with `CURRENT_TIMESTAMP` (mirrors `new_user_protocols`, whose comment already documents exactly this trap).
- **Indexes must be recreated.** `DROP TABLE` removes `admins_username_key` (UNIQUE on `username`, init migration line 117) and `user_quotas_userId_key` (UNIQUE on `userId`, init migration line 147). Both are recreated immediately after the rename.
- **Statement position is preserved.** Each redefine replaces its ALTER in place (admins block stays at the top of the file, user_quotas block stays between the `chain_presets` and `remote_panels` CREATE TABLEs) so the diff stays minimal and the surrounding ordering is untouched.
- **Line endings.** The file is CRLF in the worktree with LF in the index (`core.autocrlf=true`, no `.gitattributes`). Keep the diff to the two statement blocks only — do not renormalize the file, do not run Prettier over `.sql`.
- **Local `prisma/dev.db` cannot be repaired by replaying the migration.** It is an old `prisma db push` snapshot: `_prisma_migrations` holds `20260617…` as `applied=no, rolled_back=no` (blocking all further migrations), six tables the migration would CREATE already exist (`config_templates`, `remote_panels`, `chain_presets`, `geo_routing_rules`, `routing_rule_templates`, `cached_panel_configs`), `whitelist_entries` is missing, and `panel_connection_history` is still present. It must be rebuilt from the corrected chain. `prisma/dev.db.backup-20260927` (taken before any migration attempt) is the restore source and must not be deleted.
- **Only 4 unique rows are worth restoring**: `admins` (1 — id `cmojzs07q0000v0jlbrq4ppx3`, username `admin`, bcrypt hash prefix `$2b$10$RjC`, createdAt `2026-04-29T11:48:56.726+00:00`), `users` (1 — id 1, username `qu1`), `user_protocols` (2 — AWG/wireguard and THREE_XUI/xray for userId 1). Everything else in the backup is built-in seed data (`chain_presets` 3 rows, `routing_rule_templates` 5, `geo_routing_rules` 2 with `source: 'template'`) that the app recreates lazily via `src/lib/chain-presets.ts`, `src/lib/routing-rule-templates.ts` and `src/lib/protocol-templates.ts` (all upsert on `isBuiltIn: true`) — do not restore it.
- **`ADMIN_PASSWORD` is NOT set in `.env`.** `seedAdmin()` in `src/lib/seed.ts` (called from `src/app/api/auth/login/route.ts`) only creates the admin when `findUnique({ username: 'admin' })` returns nothing, so restoring the backup row preserves the real hash; had we let it seed, the password would silently become `'admin'`. Restore the row — never delete it and let the app reseed.
- **No backlog TODO / GitHub issue applies.** This is a bug found ad hoc during dependency+migration verification, not an item from `docs/TODOs-2.md`, so there is no `AFX-*` ID to reference in the commit.
- **Out of scope:** `.gitattributes` + worktree renormalization (separate quick task), the 5 pre-existing Windows-only test failures and the 324-file `format:check` CRLF fallout (both documented as environment artifacts, not regressions), and any change to `schema.prisma`.
