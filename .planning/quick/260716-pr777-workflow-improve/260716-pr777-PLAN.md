# Quick Plan: PR #777 workflow improvement intake

## Source
- PR #777: fix(workflows): wake and rescue PRs whose finalizer apply failed
- URL: https://github.com/kostua16/amnezia-control-panel/pull/777

## Summary
PR #777 adds two complementary rescue paths for PRs stuck on a failed finalizer apply: (1) wake-orchestrator now fires on apply_status=='failed', and (2) watchdog selects PRs with flow/finalizer-dispatched + expired failure aggregate. Three concrete follow-ups identified: missing failure-state loop detection in the watchdog (unlike the ready-pending-loop escalation), no integration test for orchestrator retry-counter advancement on watchdog-sourced wakes, and duplicated bounded-retry patterns across workers.

## Quick Wins
- Add failure-state loop detection to watchdog for finalizer-failure re-pokes -- watch-pr-flow.cjs:190 has ready-pending-loop escalation (≥8 pending aggregates → pm-escalation) but no equivalent for failure-state re-pokes. If the orchestrator's retry lane has a bug preventing it from reaching flow/manual-only terminal state, the watchdog silently re-dispatches every 30 min forever with stale-finalizer-failure. Add a finalizer-failure-loop recovery reason (e.g., ≥N failure aggregates on the same head with flow/finalizer-dispatched label) that also triggers pm-escalation, and gate it on the latest pr-flow/ready still being failure (same success-escape pattern as the pending loop at line 183). (owner: watchdog-owner, type: quick-task)
- Add orchestrator retry-counter integration test for watchdog-sourced wakes -- The PR adds 3 watchdog selection tests in watch-pr-flow.test.cjs (rescues finalizer-failure, skips non-finalizer failures, skips fresh failures) but no test proving the orchestrator increments getFinalizerRetryCount when re-dispatched by the watchdog. This is the critical handoff: watchdog selects → dispatches PR Flow → orchestrator sees flow/finalizer-dispatched + prior failure → should increment retry counter and re-dispatch finalizer. Add a test in orchestrate-pr-flow.test.cjs that simulates this wake path and asserts retry label advancement. (owner: orchestrator-test-owner, type: quick-task)
- Refactor hasExpiredReadyPendingStatus to call hasExpiredStatusInState directly -- PR #777 generalizes hasExpiredPendingStatus into hasExpiredStatusInState but hasExpiredReadyPendingStatus (watch-pr-flow.cjs:111) still calls the intermediate wrapper hasExpiredPendingStatus rather than the generalized function. Minor consistency improvement — call hasExpiredStatusInState(statuses, READY_STATUS_CONTEXT, 'pending', opts) directly to match the new pattern used in the stale-finalizer-failure rescue at line 173. (owner: watchdog-owner, type: quick-task)

## pr777.x Phase Candidates
- pr777.3: Extract unified bounded-retry helper for orchestrator workers -- orchestrate-pr-flow.cjs has two independent retry-lane implementations: code-review (MAX_CODE_REVIEW_RETRIES at line ~460) and finalizer (MAX_FINALIZER_RETRIES at line 457). Both parse retry labels with regex (getFinalizerRetryCount vs equivalent for code-review), enforce caps, and flip to terminal states. Extract a shared bounded-retry module that manages label parsing, cap enforcement, and terminal fallback so new workers inherit retry semantics by default and cap/label-format bugs are fixed in one place. (owner: orchestrator-owner)
- pr777.2: Add structured rescue-path telemetry to watchdog runs -- watch-pr-flow.cjs runWatchdog() returns dispatched[] and escalated[] counts but emits no per-reason telemetry. Adding a structured annotation or step summary line per rescue reason (stale-ready-pending, stale-finalizer-failure, ready-pending-loop) with PR number and timestamp would make it visible in GitHub Actions run logs when a rescue path fires excessively — indicating a deeper issue in the orchestrator rather than a transient lost wake. (owner: watchdog-owner)
