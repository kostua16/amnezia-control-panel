PR #1209 is merged into main as 2e1f73d (2026-11-23T16:59:23Z), so every task below is a follow-up on code already on main; line anchors such as orchestrate-pr-flow.cjs:428 refer to PR #1209's tree and must be re-derived against the then-current checkout before implementing. ## Quick Wins
- Add run-name contract guard test binding worker yml files to matchesWorkerTitle's exact 'PR #<n> @ <sha>' format -- PR 1209 tightened matchesWorkerTitle (orchestrate-pr-flow.cjs:428) to the exact substring 'PR #<n> @ <sha>'; the same filter drives summarizeWorkerRuns/getWorkerSummary for every worker, and its own comment warns a format change silently orphans a worker's runs (duplicate dispatches, stuck states). Worker run-names are hand-maintained across 10+ yml files with divergent fallback chains (code-review.yml 'format('PR #{0} @ {1}', … || 'manual', … || github.sha)', fix-review.yml '… || github.run_id', deepseek/antigravity issue-vs-PR branches). Add a node:test characterization that walks the top-level workers map from .github/pr-flow.json (there is no .github/workflows/pr-flow.json), skipping entries without a 'workflow' key (external workers such as kiloReview have none), reads each referenced workflow yml, renders its 'run-name:' expression for a PR-triggered context, and asserts the rendered title against the exact pattern /PR #\d+ @ [0-9a-f]{40}\b/ — or feeds the rendered title through matchesWorkerTitle itself — because asserting only 'both tokens joined by @' would also accept '#123 @ <sha>' or '<sha> @ PR #123', which the real filter (title.includes('PR #' + n) && title.includes(pr.headSha)) rejects; additionally assert that '|| github.run_id'-style fallback chains (fix-review.yml renders 'Fix Review PR #<event.issue.number || inputs.pr_number || github.run_id> @ <inputs.head_sha || github.sha>') resolve the PR number and the head SHA for the PR-triggered render rather than the run id — so the next run-name edit fails the CI suite command 'node --test .github/workflows/scripts/__tests__/*.test.cjs' (equivalently, from .github/workflows: 'node --test scripts/__tests__/*.test.cjs'; the bare root scripts/__tests__ directory is unrelated) instead of breaking retry accounting in production. (owner: kos-audit-fix, type: quick-task)
- Sync worker-runs-by-head.cjs header comment to the exact-format title contract -- The PR rewrote the run-name contract doc in orchestrate-pr-flow.cjs but lib/worker-runs-by-head.cjs:6-8 still says a run counts when its title "carries both 'PR #<n>' and the full head SHA" — the old loose two-token form. That header is the contract doc for population-2 base-ref runs (project-manager → pr-finalizer dispatches) that the new finalizer retry history depends on; a stale spec invites someone "fixing" a run-name back to the loose form. One-comment sync, no behavior change. (owner: kos-audit-fix, type: quick-task)
- Surface the finalizer history-read error in the deferral status and orchestration comment -- collectLegacyWorkerRuns (orchestrate-pr-flow.cjs) emits the cause only via console.warn ('could not read finalizer history: HTTP 403' / 'finalizer head history is truncated'), while makeDecision's deferral reason, the 'pr-flow/ready'/'pr-flow/finalizer' pending statuses, and the sticky comment all say the generic 'Finalizer history unavailable. Dispatch deferred.' A persistent 403 secondary-rate-limit vs a truncated page need different human responses, and today the maintainer must open the orchestrator run logs to tell them apart. Thread the warn reason (e.g. 'historyError' on the context next to unavailableWorkerRuns) into statuses.finalizer.description and the comment text; covered by extending the existing 'legacy Finalizer history errors' test matrix in scripts/__tests__/orchestrate-pr-flow.test.cjs. (owner: kos-audit-fix, type: quick-task)
