# Quick Plan: PR #1033 workflow improvement intake

## Source

## Summary
PR #1033 adds programmatic stale-label guards to issue-catch-up.yml and updates natural-language instructions in maintenance.yml and stale.yml header comments to document the MNT-I08 boundary contract. Two high-quality tests cover the boundary. Follow-ups center on enforcement gaps (maintenance.yml prompt-only filtering) and cross-workflow contract fragility.

## Quick Wins
- Add programmatic stale-label filter to maintenance.yml 90-day issue review -- issue-catch-up.yml got a hard 'hasStale' guard, but maintenance.yml's step 5 only tells the Claude agent via natural language to 'skip issues labeled stale'. The agent can ignore prompt instructions; a programmatic filter (e.g. '--label '!stale'' in the 'gh issue list' call within the agent prompt, or a pre-filter script) would make this deterministic like catch-up's guard. (owner: kos-maintenance, type: quick-task)
- Assert close-bucket ordering invariant in issue-catch-up collect tests -- The 'hasStale' continue guard must fire AFTER the 'should_close_dupe' and 'should_close_canceled' buckets but BEFORE all re-engagement buckets. This ordering dependency is correct but invisible — a future refactor could move the guard up and silently break the contract. A targeted test that places a stale+triaged issue and asserts it lands in needs_retriage=0 but still gets closed when also duplicate would catch ordering regressions. (owner: kos-maintenance, type: quick-task)
- Add 'fixed' to stale.yml exempt-issue-labels to prevent stale marking of issues awaiting verification -- issue-catch-up.yml exempts 'fixed' in EXEMPT_LABELS (catch-up skips them). But stale.yml's exempt-issue-labels is 'keep-open,backlog,in-progress' — no 'fixed'. A 'fixed' issue that sits open >7 days (orphaned_fixed bucket) could get marked stale by stale.yml at 60 days, creating conflicting automation signals. Adding 'fixed' to stale.yml's exempt list aligns both workflows. (owner: kos-maintenance, type: quick-task)
