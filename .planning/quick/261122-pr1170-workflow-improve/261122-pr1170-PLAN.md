# Quick Plan: PR #1170 workflow improvement intake

## Source
- PR #1170: fix: resolve #1049 - MON-E06: Per-run cost/turn telemetry aggregation (monitor-github-runs)
- URL: https://github.com/kostua16/amnezia-control-panel/pull/1170

## Summary
PR #1170 (MON-E06) adds 'aggregate-run-costs.cjs' plus a read-only 'cost-telemetry' job to the hourly GitHub-runs monitor: it lists up to 200 completed runs of the monitor workflow over a 7-day window, downloads the agent job log for each, parses cost/turns with 'parseClaudeExecution()', and uploads 'records.jsonl' + 'summary.json' as a 90-day artifact. 'report-failure' now also covers 'cost-telemetry' via six inline attribution expressions. Top follow-ups: (1) the job re-downloads the full window every hour (~336 PAT calls, ~168 multi-MB logs) inside a 10-minute budget, so an incremental merge with the prior artifact is the highest-value fix; (2) trimmed windows and dropped logs exit 0 and are visible only inside the JSON; (3) the records carry no budget context even though MON-E06 exists to tune MAX_TURNS; (4) MON-E06's stated target, the shared metrics store (XC-5) and the weekly digest (WHO-E05), is still unaddressed. Pins ('actions/checkout', 'actions/upload-artifact') match the repo's existing SHAs, 'cancel-in-progress' is false so supersession cancellation does not apply, and the fail-closed paths ('--since', run list, job-name drift) are well tested.

## Quick Wins
- Incremental cost scan: merge the prior telemetry artifact instead of re-downloading the 7-day window hourly -- 'collectCostTelemetry' in '.github/workflows/scripts/aggregate-run-costs.cjs' walks runs sequentially: one 'actions/runs/{id}/jobs' call plus one 'actions/jobs/{id}/logs' download per agent job, each under 'runGh''s 30 s timeout. On the hourly cron (''56 * * * *'') with '--window-hours 168 --max-runs 200' that is roughly 336 PAT-backed calls and 168 multi-megabyte log downloads per run (~8k calls/day) inside a 10-minute job. One slow GitHub API hour becomes a timeout-'cancelled' job that files "[github-runs-monitor] GitHub runs monitor failed" although the agent job succeeded. Change: add '--prior-records-file'; resolve the last successful run with 'gh api repos/{repo}/actions/workflows/$MONITOR_WORKFLOW_FILE/runs?status=success&per_page=1', 'gh run download' its 'monitor-cost-telemetry-<id>' artifact, store a 'window.scan_cursor' (newest 'run_started_at' listed) in the summary, scan from 'scan_cursor' minus a 2 h overlap, and merge through the existing 'dedupeRecords()' (re-runs refresh 'run_started_at', so they resurface). Fall back to a full scan when no prior artifact exists or once per day. After this cuts the job to a handful of calls, switch the checkout 'token' and 'GH_TOKEN' from 'secrets.GH_PAT' to 'secrets.GITHUB_TOKEN' to match the least-privilege pattern 'fleet-gate' already uses in the same file (safe only once the volume no longer competes for GITHUB_TOKEN's 1,000 req/h per-repo budget). (owner: gh-workflow-engineer, type: workflow-improvement)
- Surface truncated windows and dropped logs outside summary.json -- 'writeGithubOutput' emits 'total_cost_usd', 'missing_metrics_jobs' and friends, but the 'Aggregate run costs' step reads none of them and the step summary is a raw 'cat summary.json'. Two failure modes exit 0 and are visible only to someone reading the JSON: (a) 'window.truncated' — ~168 hourly runs per 7-day window against '--max-runs 200' leaves 32 slots for dispatches and re-runs; (b) 'fetch_errors' — a log that trips the 30 s 'runGh' timeout or the 64 MB 'maxBuffer' is skipped with a stderr warning only, and the largest logs belong to the longest, most expensive runs, so drops bias cost downward. Change: in 'main()' emit '::warning::' when 'result.summary.window.truncated' is true or 'fetch_errors.length > 0', add 'telemetry_truncated' and 'fetch_error_count' to the 'GITHUB_OUTPUT' entries, add a 'log_bytes' field to 'buildRecord', and print a short table (fleet cost, turns avg/max, missing jobs, fetch errors) above the JSON block in the monitor workflow step. (owner: gh-workflow-engineer, type: workflow-improvement)
- Report turns/wall-time utilization against the budget with p50/p95 (AFX-E09) -- MON-E06 exists to tune budgets (WHO-E05 in 'docs/TODOs-2.md:73': "aggregate cost/turns per workflow weekly to tune MAX_TURNS budgets"), but 'stats()' in 'aggregate-run-costs.cjs' returns only total/avg/max and records carry no budget reference; 'max' is outlier-driven and the wrong statistic for a budget decision. Change: accept '--max-turns' and '--job-timeout-minutes' (pass '${{ env.MAX_TURNS }}' = 50 and the agent job's 25 from the workflow), add 'turns_budget_pct' and 'duration_budget_pct' to 'buildRecord', add 'p50'/'p95' to 'stats()', and print "turns p95 vs 50" in the step summary so later 'MAX_TURNS'/'timeout-minutes' edits in 'monitor-amnezia-control-panel-github-runs.yml' cite data. (owner: gh-workflow-engineer, type: workflow-improvement)
- Add log-rate-limit accounting to the cost-telemetry job -- 'cost-telemetry' is now the monitor workflow's largest GitHub API consumer (two calls per listed run, up to 200) and authenticates with 'GH_PAT', yet it never calls './.github/actions/log-rate-limit', unlike 'collect-runs' in 'workflow-health-optimize.yml:64-68' which uses 'report-at-job-end: 'true''. The repo keys RATE_LIMIT windows by token kind, so this new load is invisible in quota accounting. Change: add a './.github/actions/log-rate-limit' step with 'label: monitor-cost-telemetry' and 'report-at-job-end: 'true'' before the 'Aggregate run costs' step in 'monitor-amnezia-control-panel-github-runs.yml'. (owner: gh-workflow-engineer, type: workflow-improvement)
- Move the report-failure coverage invariant into the shared e2e suite and add scenario-doc rows -- The PR moved 'report-failure' to two upstream jobs, but its workflow-shape tests live in 'aggregate-run-costs.test.cjs' and string-pin the monitor file, while the generic PR721 guard at '.github/workflows/scripts/__tests__/e2e-pr651-flows.test.cjs:166' checks only that 'report-failure' does not use 'if: failure()'. Nothing stops the next job from being added to 'needs:' without being evaluated in the 'if:'. 'docs/workflow-e2e-scenarios.md' §4 (line 168) covers 'monitor-…runs' but has no cost-telemetry rows, although CLAUDE.md's workflow change protocol requires a doc update when behavior changes. Change: extend the PR721 test with an invariant that every entry in a 'report-failure' job's 'needs:' appears as 'needs.<job>.result' in its 'if:' expression (and vice versa), and add §4 rows for: telemetry success artifact, telemetry-only failure filing an issue with reason 'cost-telemetry job <result>', 'agent-job-missing' exit 1, and timeout-'cancelled' telemetry filing an issue. (owner: gh-workflow-engineer, type: workflow-improvement)
