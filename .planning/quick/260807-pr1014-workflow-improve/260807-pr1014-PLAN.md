# Quick Plan: PR #1014 workflow improvement intake

## Source
- PR #1014: fix: resolve #998 - WHO-E03: Queue-latency telemetry and starvation alerts (workflow-health-optimize)

## Summary
PR #1014 adds queue-latency telemetry computation (compute-queue-latency-telemetry.cjs), a starvation alert filer (file-queue-starvation-alert.cjs), inline telemetry extraction in the collect-runs job, and a new report-queue-starvation job gated on the telemetry threshold. Two test files cover the new scripts. Analysis identified 3 quick tasks and 2 phase suggestions.

## Quick Wins
- Add report-queue-starvation to report-failure needs gate -- workflow-health-optimize.yml:521 — report-failure needs [collect-runs, detect-flaky, optimize] but NOT report-queue-starvation. If the new job fails (gh auth issue, network timeout), it silently disappears with no failure issue filed. Add it to the needs list and extend the always() condition to cover its result. (owner: workflow-health, type: quick-task)
- Add e2e invariant test for starvation alert job shape -- The new report-queue-starvation job is absent from the e2e characterization suite (.github/workflows/scripts/__tests__/e2e-pr651-flows.test.cjs line 102 lists workflow-health-optimize.yml but only tests gate/collect/detect/optimize/report-failure shapes). Add a test asserting: (1) report-queue-starvation exists, (2) its if condition references starvation-alert output, (3) it passes GH_TOKEN. Per ADR 0001 and CLAUDE.md workflow-change protocol, new jobs must keep e2e green and update docs/workflow-e2e-scenarios.md. (owner: workflow-health, type: quick-task)
- Replace raw execFileSync gh wrapper with shared gh() from detect-flaky-workflows.cjs -- file-queue-starvation-alert.cjs:18-21 hand-rolls a gh() wrapper using execFileSync — identical pattern to detect-flaky-workflows.cjs:5-18. Extract to scripts/lib/gh.cjs (shared module) so both scripts import it. This is the pattern already used by lib/gate-summary.cjs for shared logic. Eliminates 5 lines of duplicate code and ensures consistent error handling across workflow scripts. (owner: workflow-health, type: workflow-improvement)

## pr1014.x Phase Candidates
- pr1014.2: Centralize queue-latency telemetry into workflow run summary artifact -- The telemetry is computed inline in the collect-runs job (workflow-health-optimize.yml:281-287) via require() and exported as a job output string. This works but means the telemetry JSON is an opaque string output — not inspectable as an artifact, not consumable by other workflows (e.g., monitor-amnezia-control-panel-github-runs.yml), and lost if the collect-runs job times out before downstream jobs read it. Phase: serialize telemetry into the existing health-summary artifact alongside the markdown summary, add a telemetry.json artifact upload, and have report-queue-starvation read from the artifact instead of the job output. This decouples collection from reporting and makes telemetry queryable by the monitoring workflow. (owner: workflow-health)
- pr1014.1: Add dedup cooldown for queue starvation issue filing -- file-queue-starvation-alert.cjs searches for open issues with title matching 'Queue starvation' and comments if found — but has no cooldown. If p95 hovers just above 300s, every hourly run files a comment on the same issue, creating noise. Add a cooldown: skip filing if the existing issue has a comment within the last N hours (configurable, default 6h matching the lookback). This is a workflow governance concern — alert noise directly affects maintainer signal-to-noise ratio and should be policy-controlled. (owner: workflow-health)
