# Quick Plan: PR #237 workflow improvement intake

## Source
- PR #237: [codex] fix PR finalizer auto-merge stall
- URL: https://github.com/kostua16/amnezia-control-panel/pull/237

## Summary
PR #237 fixes a circular-dependency stall in the PR finalizer: `gh pr checks --required` was picking up `pr-flow/ready` as a required check, creating a deadlock where the finalizer couldn't succeed because the finalizer itself was responsible for setting that status. The fix replaces `--required` with a config-driven filter (`filter-required-pr-checks.cjs`) that reads only the CI jobs listed in `pr-flow.json`, and adds auto-merge retry logic so the orchestrator re-dispatches the finalizer when a prior run succeeded without enabling auto-merge. Well-tested with 4 new test cases covering the core scenarios.

## Quick Wins
- Extract filter-required-pr-checks.cjs into a shared module with unit test file -- The new filter script is tested only through orchestrate-pr-flow.test.ts integration tests. It has 103 lines of non-trivial normalization logic (normalizeBucket, normalizeCheck, matchesRequiredCheck) that deserve their own isolated unit test file. This prevents regressions when edge-case states like 'startup_failure', 'action_required', or 'timed_out' are added to the state normalization map. (owner: maintainer, type: quick-task)
- Replace pr-finalizer.yml inline jq check-evaluation with the shared filter script -- pr-finalizer.yml lines 149-151 still use raw jq to evaluate check buckets on the filtered JSON output. Now that filter-required-pr-checks.cjs normalizes bucket/state, the finalizer's jq filters duplicate that normalization logic (checking both .bucket and .state). Simplify the finalizer to trust the normalized output and count only by .bucket, removing the fragile dual-field jq selectors. (owner: maintainer, type: quick-task)
- Add a guard against infinite finalizer re-dispatch loops -- The orchestrator now re-dispatches the finalizer when auto-merge was not enabled. If the finalizer keeps succeeding but auto-merge keeps failing (e.g. branch protection misconfiguration, permissions issue), the orchestrator will re-dispatch on every wake cycle with no termination. Add a max-retry counter (e.g. 3 attempts per head SHA) tracked via a label like flow/finalizer-retry-3 or via worker run count, and fall back to manual_only after the limit. (owner: maintainer, type: quick-task)
- Add integration test for finalizer wake-orchestrator -> orchestrator re-dispatch cycle -- The PR adds new re-dispatch behavior (finalizer succeeds without auto-merge → orchestrator re-dispatches), but there is no end-to-end test covering the full cycle: orchestrate-pr-flow.cjs decision logic → finalizer → wake → orchestrator re-evaluation with autoMergeRequest set. The existing test covers makeDecision and buildFlowVisibility in isolation but not the cycle boundary. A targeted integration test would catch regressions in the wake-retry path. (owner: maintainer, type: quick-task)
- Update documentation.md to reflect --required removal from finalizer -- The diff already updates documentation.md with a new paragraph explaining the config-driven check filtering, but the existing line 97 still says 'revalidates required checks' which the PR updates to 'revalidates configured CI checks'. Verify the full documentation.md is consistent — the PR only patches one line but the 'PR Flow Visibility' section and 'Policy Examples' table may also reference 'required checks' in ways that are now ambiguous post-fix. (owner: maintainer, type: quick-task)

## pr237.x Phase Candidates
- pr237.2: Centralize all CI check evaluation behind filter-required-pr-checks.cjs -- Currently the orchestrator (orchestrate-pr-flow.cjs) uses its own inline check-evaluation logic while the finalizer uses both the new filter script and inline jq. Both pipelines evaluate check state, but with different normalization approaches. Consolidating on the shared filter script ensures both paths apply identical bucket/state normalization rules. This prevents divergence where a new state value (e.g. a GitHub 'neutral' conclusion) is handled in one path but not the other. (owner: maintainer)
- pr237.3: Formalize auto-merge retry policy with bounded attempts and cooldown -- PR #237 introduces re-dispatch when the finalizer succeeds without enabling auto-merge, but there's no explicit retry budget. The finalizer-wake-orchestrator loop can cycle indefinitely if auto-merge fails for a persistent reason (branch protection rule change, insufficient permissions, merge conflict). Define a formal policy: max N retries per head SHA, exponential backoff or cooldown window between attempts, and automatic fallback to flow/manual-only with a diagnostic comment explaining why auto-merge was abandoned. Track the retry count in the orchestration decision context rather than relying on label counting. (owner: maintainer)
- pr237.1: Add a self-test workflow that validates pr-flow.json config against live repo state -- The root cause of the stall was a mismatch between what GitHub considered 'required' (branch protection) and what pr-flow.json declared as required CI checks. This class of config drift will recur whenever someone changes branch protection rules or renames CI jobs. A scheduled or PR-triggered self-test job would compare pr-flow.json checks.required against the actual CI workflow job names and against GitHub branch protection required_status_checks, flagging mismatches as workflow failures before they cause stalls. (owner: maintainer)
- pr237.4: Auto-generate follow-up quick tasks from finalizer stall patterns -- PR #237 was itself the result of observing a stall pattern. The orchestrator already has visibility into flow state transitions (checks-pending → finalizer-dispatched → success/failure). Wire the orchestrator to detect repeated stall patterns (e.g. finalizer re-dispatched >2 times, checks stuck in pending >30 min) and automatically create GitHub issues or suggest /gsd:quick tasks for investigation. This turns reactive debugging into proactive planning automation. (owner: maintainer)
