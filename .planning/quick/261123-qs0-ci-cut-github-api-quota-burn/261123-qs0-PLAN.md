## Item 3 — Kilo sticky-comment edits that do not change the top of the review
Evidence (GraphQL `userContentEdits` on PR #1181, 20 edits): every Kilo review = a PAIR of edits 10–17 s apart. Edit 1 changes the part of the body BEFORE `<!-- kilo-review-history -->` (verdict, files, incremental range); edit 2 leaves that part byte-identical and only grows the history section (9 of 9 pairs: `topSame=false` then `topSame=true`). Each edit currently wakes the PR Orchestrator and Auto Cover Review (33 + 33 runs in the exhausted window).
Change:
- Pure function `isKiloHistoryOnlyEdit(event)` in `.github/workflows/scripts/lib/kilo.cjs`: true iff action is `edited`, the comment is by a Kilo login with the marker, `changes.body.from` is a string containing the marker, and the text before the history marker is byte-identical (after `\r\n`→`\n`) between `changes.body.from` and `comment.body`. Anything else (created, missing `from`, no marker, unparsable) ⇒ false (= relevant, fail-safe). Exposed through a small CLI (`evaluate-trigger-policy.cjs` already runs arg checks on import — keep the predicate in `lib/kilo.cjs` and call it from a tiny script, not from `evaluate-trigger-policy.cjs`).
- `pr-flow.yml`: the concurrency group expression gets a dedicated group for Kilo `edited` events BEFORE the `wake` fallback: `kiloedit` (cancel-in-progress false) so a skipped edit can only displace another Kilo edit, never a pending `workflow_run`/command wake. `classify-trigger`: enable the (credential-less) checkout also for Kilo `issue_comment` events (git fetch, not REST) and call the predicate; relevant edits proceed exactly as today. Rollback: `${{ vars.KILO_EDIT_FILTER }}` = `off` disables the filter (env into the classify step).
- `auto-cover-review.yml`: same dedicated `kiloedit-<PR>` workflow group (cancel-in-progress false) and a cheap `classify` job (checkout + predicate, no setup-environment) that `cover` depends on; irrelevant edits end there. Keep `cancel-in-progress: true` for the other events.
- Document the residual race (a relevant edit pending behind an in-flight `kiloedit` run displaced by a later history-only edit; `watch-pr-flow.cjs` only rescues pending statuses) and why it is rare (the edit pair is serialized by the first run finishing before the next review).
Tests: predicate with fixtures built from REAL before/after bodies (pair 1: top differs ⇒ relevant; pair 2: top same ⇒ history-only), created ⇒ relevant, missing `from` ⇒ relevant, CRLF; update the pinned concurrency regexes in `workflow-triggers.test.ts`; checkout-before-node tests; structural test that the `kiloedit` branch precedes the `wake` fallback; A/B/C interleaving test of the group expression semantics where expressible. ## Item 6 — autofix delay (separate commit) — do AFTER 3
Goal: no instant autofix after a review; ~15 min quiet period (no runner held, zero API calls while waiting). Design (no `sleep`):
- New workflow `.github/workflows/auto-cover-dispatch.yml` (`workflow_dispatch` only, inputs `pr_number`, `head_sha`; `run-name` includes `PR #n @ sha`):
  - job `wait`: `environment: auto-cover-delay` (wait timer configured on the repo environment), job-level `concurrency: { group: auto-cover-wait-<pr>, cancel-in-progress: true }` — a newer candidate for the same PR replaces the waiting one (debounce); no side effects, cancellable freely.
  - job `dispatch` (`needs: wait`): job-level `concurrency: { group: auto-cover-dispatch-<pr>, cancel-in-progress: false }` (serialized, never cancelled mid-dispatch). After checkout + setup-environment it REBUILDS fresh inputs and re-runs BOTH existing evaluators (`evaluate-external-review.cjs`, `evaluate-auto-cover-review.cjs`) with `--head-sha <head_sha>` (so green-after-wait, label changes, a completed manual fix, consumed attempts, no-op/terminal-skip verdicts and an active fix-review run all veto), then, if still eligible, does what the inline script does today: dispatch `fix-review.yml` (`--ref main`, `automation_review_loop=true`), the post-dispatch run-url lookup, the summary comment. Reserve gate (item 4) here too.
- `auto-cover-review.yml` (`evaluate`): keeps all current triggers/evaluation; when eligible and delay enabled it dispatches `auto-cover-dispatch.yml` for each candidate instead of dispatching fix-review directly (one candidate per PR; scan runs loop over PRs and dispatch one handoff per eligible PR, partial-success preserved; every origin (comment, workflow_run, scan, dispatch) goes through the same per-PR path). `dry_run` never dispatches. Rollback switch `${{ vars.AUTO_COVER_DELAY_MODE || 'delayed' }}` (`direct` = today's behavior: dispatch fix-review inline).
- Share code: extract the dispatch+comment+run-url logic into one script used by both the direct path and the dispatch workflow, so it exists once (update pinned regexes in `workflow-triggers.test.ts:145-183` accordingly).
- Attempt accounting: keep counting by existing markers (workflow-owned comment) but post the attempt-recording summary comment immediately after the accepted dispatch within the non-cancellable job; document the residual window (dispatch accepted, comment write fails) and make the evaluator count only comments authored by `github-actions[bot]` where it does not already.
- Operator prerequisite (document, do not automate): create the environment with a typed integer timer: `gh api -X PUT repos/<repo>/environments/auto-cover-delay -F wait_timer=15` (needs admin; wait timers are available on public repos; confirm on this repo). If the environment does not exist GitHub creates it with no protection ⇒ fail-open (no delay). Rollback: set `wait_timer=0` or `AUTO_COVER_DELAY_MODE=direct`. Expected side effect: a deployment record on the PR timeline per candidate; no workflow listens to `deployment*` events.
- Hosted acceptance check after merge (static tests cannot prove it): waiting job holds no runner; replacement by a newer `dispatch` for the same PR cancels the waiting one; timer expiry then dispatch.
Tests: structural (new workflow shape, `needs`, environment present, concurrency groups, no `sleep`, dry-run path), the handoff script (eligible ⇒ one dispatch of the delay workflow; dry-run ⇒ none; two eligible PRs ⇒ two handoffs), re-validation script with every mutable veto (green PR, draft, label, attempt cap reached during the wait, active run, no-op verdict, stale head). Docs rows. `.github/workflows/documentation.md`/README mention of the new workflow if other workflows are listed there.
