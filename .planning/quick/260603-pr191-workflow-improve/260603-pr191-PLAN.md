# Quick Plan: PR #191 workflow improvement intake

## Source
- PR #191: [codex] ci: orchestrate PR automation flow
- URL: https://github.com/kostua16/amnezia-control-panel/pull/191

## Summary
Analyzed PR #191 which introduces a PR Orchestrator (pr-flow.yml + orchestrate-pr-flow.cjs) that centralizes dispatch of code-review, dependency-review, pr-improve, and pr-finalizer workflows. The PR converts those workers from event-driven to dispatch-only, adds head SHA staleness protection, and includes unit tests. Found 6 quick-task follow-ups and 4 phase-scope improvements across phases 13.1-13.4.

## Quick Wins
- Handle dispatchWorker failures gracefully -- The gh workflow run command in dispatchWorker() (orchestrate-pr-flow.cjs:868-889) can fail silently (workflow not found, branch mismatch) but has no error handling — the orchestrator reports success (applied) and sets flow/finalizer-dispatched even if the dispatch failed. Wrap dispatchWorker in a try/catch, set decision state to the matching flow/*-failed label on failure, and log the gh stderr. (owner: ci-automation, type: quick-task)
- Add orchestrator decision as a PR status check or comment -- The orchestrator outputs a JSON summary to stdout but surfaces nothing on the PR itself. Maintainers can't see why a PR is stuck at flow/review-pending or flow/checks-failed without digging into Actions logs. Add a lightweight PR comment summarizing the decision — especially valuable for flow/review-blocked and flow/checks-failed states. (owner: ci-automation, type: quick-task)
- Extract ensureLabels into a one-time setup or conditional path -- ensureLabels() calls gh label create --force for all 10 flow/* labels on every orchestration run. On a self-hosted runner with frequent PRs this is 10 unnecessary API calls per invocation. Gate it behind a cache file or move it to a separate setup workflow triggered on config changes. (owner: ci-automation, type: quick-task)
- Document the run-name contract that matchesWorkerTitle depends on -- matchesWorkerTitle() (line ~206) parses displayTitle strings for PR #N and head SHA patterns. If any worker changes its run-name format, the orchestrator silently stops matching active runs and may double-dispatch. Add a comment block in orchestrate-pr-flow.cjs and pr-flow.yml documenting the expected run-name format. (owner: ci-automation, type: quick-task)
- Add resolvePrNumber test coverage for workflow_run events -- The test file covers makeDecision extensively but resolvePrNumber (lines ~84-105) has zero coverage. The workflow_run path extracts PR numbers from display_title via regex and from pull_requests array — both paths are fragile and untested. Add unit tests for: (a) workflow_run with pull_requests in payload, (b) workflow_run with title-based extraction, (c) fallback to inputs.pr_number. (owner: ci-automation, type: quick-task)
- Either use or remove the orchestrated input on worker workflows -- All four worker workflows (code-review, dependency-review, pr-improve, pr-finalizer) accept an orchestrated boolean input set by the dispatcher, but none of them read or act on it. Either remove the dead input or use it to gate behavior (e.g., skip duplicate policy evaluation since the orchestrator already checked). (owner: ci-automation, type: quick-task)

## 13.x Phase Candidates
- 13.1: Centralize trust policy in the orchestrator with maintainer-only event gates -- PR #191 removes pull_request/pull_request_target triggers from worker workflows and routes everything through pr-flow.yml. This is the foundation for Phase 13.1's central policy, but the trust boundary is incomplete: (1) the orchestrator still relies on evaluate-pr-policy.cjs as a separate script rather than a unified policy surface; (2) issue_comment /review dispatches bypass the orchestrator entirely and go straight to code-review.yml; (3) manual-only path rules (policy.json manualOnlyPathGlobs) are evaluated per-worker rather than centrally. The orchestrator should become the single trust gate that all events pass through. (owner: maintainer)
- 13.2: Add retry logic and rate-limit awareness to worker dispatch and check polling -- The orchestrator has no retry mechanism — if a worker fails (flow/review-failed, flow/improve-failed), the state is terminal until the next push or label change. Additionally, collectWorkerRuns() fetches 50 runs per worker (4 workers × 50 = 200 list entries) on every invocation, which can exhaust API rate limits on busy repos. Phase 13.2 should add: (1) configurable retry with exponential backoff for transient worker failures; (2) a single gh api call with pagination instead of N per-worker queries; (3) a dedicated re-trigger mechanism (e.g., /recheck comment) that re-runs the orchestrator for a stuck PR. (owner: ci-automation)
- 13.3: Wire orchestrator decision output into finalizer approval gating -- The pr-finalizer.yml now receives head_sha from the orchestrator and skips if stale, but the approval decision is still independent — it re-evaluates policy.json from scratch. Phase 13.3 should: (1) pass the orchestrator's decision context (which gates passed, which workers completed) as structured input to the finalizer so it doesn't re-evaluate; (2) have the finalizer validate that flow/finalizer-dispatched label exists before proceeding (trust the orchestrator's gate sequence); (3) emit a merge-ready commit status when the finalizer approves, visible in the PR UI. (owner: ci-automation)
- 13.4: Integrate orchestrator prImprove worker with GSD planning PR lifecycle -- The pr-improve workflow was converted to dispatch-only and now runs once per PR through the orchestrator. Phase 13.4 should leverage this by: (1) having the orchestrator pass the PR diff and review signal labels to pr-improve so it can generate more targeted planning artifacts; (2) creating a feedback loop where planning-draft-open triggers the orchestrator to skip re-dispatching prImprove for the same head SHA; (3) auto-linking the created planning PR back to the source PR via the intake section in ROADMAP.md (replacing the manual AUTO-13X-INTAKE comment pattern). (owner: ci-automation)
