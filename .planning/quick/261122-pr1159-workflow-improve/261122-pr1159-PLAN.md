# Quick Plan: PR #1159 workflow improvement intake

## Source
- PR #1159: feat(ci): read Kilo review inputs via GraphQL with REST fallback
- URL: https://github.com/kostua16/amnezia-control-panel/pull/1159

## Summary
PR #1159 cleanly swaps Kilo review-input transport to one GraphQL query with REST fallback, ships a read-only parity script (53/53 verdict-identical), and defaults to graphql behind the PR_FLOW_REVIEW_SOURCE rollback variable. Two real follow-ups: the REST fallback's check-run fetcher still reads only the first page (the exact 12-PR blindness the parity run surfaced, dangerous when a cancelled Kilo check sits on page 2), and GraphQL→REST fallback is invisible outside run logs. Roadmap-worthy: scheduled transport-parity monitoring, gate coverage for late-page Kilo checks, governed transport policy, and quick-task merge-order tracking.

## Quick Wins
- Paginate fetchCheckRuns so the REST fallback sees Kilo checks beyond page 1 -- orchestrate-pr-flow.cjs fetchCheckRuns calls 'gh api .../check-runs' with no --paginate (fetchPrIssueComments and fetchPrReviews already paginate), so the REST path sees only the first ~30 runs. The PR's own parity run found 12 PRs where REST missed the Kilo check that GraphQL saw; verdicts only matched because the check was 'success'. On a fallback wake (PR_FLOW_REVIEW_SOURCE=rest or ReviewInputsUnavailable), a 'cancelled'/'skipped' Kilo check beyond page 1 is invisible and the flow can pass a review that should block. Fix: paginate and merge check_runs exactly like the sibling fetchers, add a unit test that a Kilo check on page 2 yields the blocked verdict, and update docs/workflow-e2e-scenarios.md R-rows per the workflow-change protocol (both suites green). (owner: kos-audit-fix, type: quick-task)
- Surface review-input transport in the flow status comment on GraphQL→REST fallback -- collectExternalReview (orchestrate-pr-flow.cjs, the new graphql branch) only console.warns when the adapter throws and silently reads REST for that wake — a persistent ReviewInputsUnavailable (e.g. GitHub adds a new statusCheckRollup.contexts union member in lib/review-inputs-graphql.cjs toContext) would permanently degrade to REST with no signal beyond grep of run logs, defeating the REST-quota-saving purpose. Fix: record the transport (graphql | rest+reason) in the wake result and render it in the flow status comment via renderFlowComment (orchestrate-pr-flow.cjs) and upsertComment (lib/sticky-comment.cjs), so an operator can see degradation and flip vars.PR_FLOW_REVIEW_SOURCE without triage. Extend the orchestrate-pr-flow flow-comment test fixture. (owner: kos-audit-fix, type: workflow-improvement)

## pr1159.x Phase Candidates
- pr1159.2: Scheduled REST-vs-GraphQL parity and fallback-rate monitoring for Kilo review inputs -- compare-review-input-sources.cjs (new in this PR) is a manual, local-only gate: shape drift — a new GitHub statusCheckRollup.contexts union member that toContext rejects, a REST field rename, a bot-login rule change — surfaces only when someone remembers to run it, and until then every wake silently pays REST. Add a scheduled/workflow_dispatch job (maintainer-only trigger, read-only like the script) running 'node compare-review-input-sources.cjs --open --merged 30', posting the parity table to a sticky tracking comment and failing on any verdict DIFFERENT or sustained fallback count; this also gives the measured rateLimit cost history. Must follow the repo workflow-change protocol: both 'npm run test-only' and the scripts node --test suite green, docs/workflow-e2e-scenarios.md updated. (owner: gh-workflow-engineer)
- pr1159.3: Merge-gate characterization: Kilo check signals on late pages and superseded runs on both transports -- The parity run proved the two transports can disagree exactly where it matters for the merge gate: a superseded 'cancelled' Kilo run is visible to GraphQL but (today) beyond REST's first check-runs page, and statusCheckRollup drops superseded suites. The PR only relied on the accident that those checks were 'success'. Characterize and gate the review-signal semantics: extend R21–R23 in docs/workflow-e2e-scenarios.md with a scenario 'Kilo check cancelled/skipped beyond REST page 1' and add e2e tests asserting kilo-review=blocked via the GraphQL adapter and via a paginated REST fallback, so evaluate-external-review verdicts cannot silently regress per transport; ci.yml's scripts node --test gate enforces it. (owner: gh-workflow-engineer)
- pr1159.1: Central workflow policy for review-input transport toggles -- PR_FLOW_REVIEW_SOURCE enters as a free-form repository variable; unknown values currently fall back to 'rest' with only a console.warn, and nothing records which transport production actually runs — a stale or typo'd vars value quietly changes cost/behavior characteristics with no policy trail. Follow the repo's central-config pattern (pr-flow.json read via readConfig): declare the allowed transport values there, validate at read time, and render the effective transport in the flow comment (pairs with the fallback-visibility quick task), so transport overrides go through the same governed, documented path as the rest of the PR-flow policy and the rollback switch stays auditable. (owner: gh-workflow-engineer)
- pr1159.4: Declare merge-order dependencies between sibling quick tasks in planning artifacts -- The m4e PLAN.md carries a 'Merge order with the sibling plan (261122-m3o, issue #1156)' section: both tasks edit orchestrate-pr-flow.cjs in different regions and m4e must rebase onto m3o — but that dependency lives only in prose inside .planning/quick/, invisible to /gsd-quick list and to whoever merges second. Add a 'depends_on' (and 'touches_files') field to quick-task PLAN frontmatter, have gsd-planner emit it and /gsd-quick list|status surface it, so concurrent quick tasks on the same workflow script declare merge order structurally instead of relying on each plan remembering its sibling. (owner: kos-gsd-planning)
