## Summary
PR #1002 adds flaky-workflow detection (WHO-E04) as a new 'detect-flaky' job in workflow-health-optimize.yml, with a companion script 'detect-flaky-workflows.cjs'. Two sharp follow-ups identified: untested 'ensureFlakyIssue' function and missing e2e scenario coverage for the new job. One phase-level suggestion around query/classification inconsistency for 'cancelled' runs.

(owner: claude, type: quick-task)

## pr1002.x Phase Candidates
- pr1002.2: Harmonize cancelled-run handling between query and classification -- queryWorkflowRuns uses --status completed which excludes cancelled runs, but isFlaky maps cancelled→pass. If concurrency-cancelled runs should contribute to flaky signal, the query filter must include --status cancelled. If they shouldn't count as pass either, isFlaky needs a third state. Current inconsistency means a pattern like [failure, cancelled, failure, success] could be misclassified. (owner: claude)
- pr1002.1: Add lifecycle policy for flaky-tracking issues -- ensureFlakyIssue creates issues with labels auto-fix,needs-review and appends recurrence comments, but there's no rotation or auto-close. A persistently flaky workflow accumulates unbounded comments. Add: auto-close after N days with no new recurrence, or escalate to a blocker label after K recurrences. (owner: claude)
