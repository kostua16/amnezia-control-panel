# Quick Plan: PR #690 workflow improvement intake

## Source
- PR #690: fix(workflows): never auto-close umbrella/tracking issues from automation
- URL: https://github.com/kostua16/amnezia-control-panel/pull/690

## Summary
PR #690 adds centralized tracking-issue detection (lib/tracking-issue.cjs + detect-tracking-issue.cjs) and wires it into fix-issue, issue-catch-up, and auto-fix-ci workflows so umbrella/tracking issues never get auto-closed or linked with closing keywords. Solid defensive layer with 12+ tests and e2e scenario coverage. Three follow-up opportunities surfaced.

## Quick Wins
- Add isTrackingIssue guard to triage.yml duplicate-close step -- triage.yml:161 runs 'gh issue close' on issues carrying the 'duplicate' label without checking isTrackingIssue. An umbrella issue that accidentally gets 'duplicate' would be auto-closed. Add the same guard used in issue-catch-up.yml:148 — require lib/tracking-issue.cjs, skip close if isTrackingIssue(issue). ~10 line change. (owner: claude, type: workflow-improvement)
- Replace fragile try/catch require in _auto-fix-ci.yml with top-level import -- _auto-fix-ci.yml uses inline 'try { ({ isTrackingIssue } = require(...)) } catch { core.warning(...) }' inside the issue-search step. The fallback silently degrades to legacy Closes behavior if the lib is missing. Since tracking-issue.cjs is now a first-class lib with tests, a top-level require at the step's start (or a shared action wrapper) would fail loud instead of silently degrading. Matches the pattern used by issue-catch-up.yml:142-144 which requires at the top of the inline script. (owner: claude, type: workflow-improvement)
- Add umbrella-awareness to kos-maintenance.md stale-issues sweep -- The maintenance agent runs '/gsd:inbox' for stale issues (>90d). kos-maintenance.md has zero mention of umbrella/tracking issues. If a '[todo-backlog]' umbrella goes 90d without activity, the sweep could flag it for closure. Add a guideline: skip umbrella/tracking issues (same heuristics as issue-catch-up) from the stale-issues category. (owner: claude, type: workflow-improvement)

## pr690.x Phase Candidates
- pr690.1: Centralize issue-type classification into a shared workflow action -- tracking-issue.cjs, detect-tracking-issue.cjs, and the isTrackingIssue checks are now duplicated across 3 workflows (fix-issue, issue-catch-up, auto-fix-ci) with slightly different integration patterns (CLI script vs inline require vs action step). A shared composite action 'classify-issue' that accepts title/body/labels and outputs is_tracking, is_duplicate, is_security would eliminate these integration variations and give a single place to add new issue-type classifiers (e.g., security-vuln, feature-request). (owner: claude)
- pr690.2: Add integration test: workflow PR body must not contain closing keywords for tracking issues -- The new e2e scenario A12 and unit tests cover tracking-issue detection in isolation, but there is no integration test that verifies the full pipeline: fix-issue workflow run on a tracking issue → created PR body contains 'Part of' not 'Closes' → merge does not close the issue. A workflow-level test (similar to e2e-merge-gate.test.cjs) would catch regressions if the build-automation-pr-body or the closing/related split in fix-issue.yml drifts. (owner: claude)
