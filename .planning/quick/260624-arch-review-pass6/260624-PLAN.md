### #16: SQLite WAL mode for write concurrency

**Severity:** High (Performance)
**Area:** `src/lib/prisma.ts:9-12`

**Problem:**
`createPrismaClient()` initializes `PrismaBetterSqlite3` without WAL mode. Default SQLite uses rollback journal — every write locks the entire database, blocking concurrent reads. With the real-time broadcaster inserting traffic logs, `traffic-log-cleanup` running periodic deletes, and multiple API routes writing simultaneously, write contention is real and measurable under load.

**Evidence:**
```
src/lib/prisma.ts:9-10 — adapter = new PrismaBetterSqlite3({ url: ... })
No journal_mode pragma, no connection string parameters.
```

**Fix:**
Append `?journal_mode=WAL` to the DATABASE_URL or execute `PRAGMA journal_mode=WAL` after connection. With `@prisma/adapter-better-sqlite3`, WAL can be set via:
- Connection URL parameter: `file:./prisma/dev.db?journal_mode=WAL`
- Or post-connection pragma in `createPrismaClient()` via `prisma.$executeRaw` after client creation

Also consider `busy_timeout=5000` to retry on lock instead of failing immediately.

**Impact:**
- Reads no longer blocked by writes (WAL allows concurrent readers + single writer)
- Write throughput improves under concurrent load
- Zero application code changes beyond config
- WAL file needs monitoring in low-disk environments (roughly 2× DB size in worst case)

**Files:** `src/lib/prisma.ts`
**Verify:** `PRAGMA journal_mode;` returns `wal` after app startup.

### #17: Security response headers via Next.js middleware

**Severity:** Medium (Security)
**Area:** `src/middleware.ts` (new or extend existing)

**Problem:**
Zero security response headers are set anywhere in the codebase. No Content-Security-Policy, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, or Permissions-Policy. For a self-hosted admin panel with JWT authentication and VPN management capabilities, this leaves the application exposed to clickjacking, content-type sniffing, and other browser-level attacks.

**Evidence:**
```
grep -ri "security.*header|Content-Security-Policy|X-Frame-Options|helmet" src/ → No matches
```

**Fix:**
Add security headers in `src/middleware.ts` (Next.js stable middleware API runs on every request):
```
Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; connect-src 'self' ws: wss:;
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

Note: Socket.IO requires `connect-src 'self' ws: wss:` and the app uses inline scripts/styles from Next.js, so CSP must be relaxed initially. CSP can be tightened incrementally.

**Impact:**
- Blocks clickjacking (X-Frame-Options: DENY)
- Prevents MIME-type sniffing (X-Content-Type-Options: nosniff)
- Mitigates XSS by restricting resource loading (CSP)
- Zero breaking changes for same-origin access
- CSP `unsafe-inline` keeps Next.js working; tighten later with nonce-based approach

**Files:** `src/middleware.ts` (create or extend), possibly `next.config.ts` for `headers()` config
**Verify:** `curl -I http://localhost:3333` shows security headers.

### #18: Bounded parallelism for sequential VPN service loops

**Severity:** Medium (Performance)
**Area:** `src/app/api/users/[id]/route.ts:177-200`, `src/lib/user-sync.ts:234-240`

**Problem:**
User mutation and sync endpoints iterate over VPN service calls in sequential `for` loops. Each VPN API call has a ~10s timeout. For user delete with 2 services: ~20s worst case. For `syncAllUsers()` with 50 users: O(50 × VPN calls × timeout).

**Evidence:**
```
src/app/api/users/[id]/route.ts:177-200
  for (const serviceType of toRemove) {
    if (serviceType === 'AWG') vpnResult = await deleteAwgUser(...)
    if (serviceType === 'XUI') vpnResult = await deleteXuiUser(...)
  }

src/lib/user-sync.ts:234-240
  for (const user of users) { const userReport = await syncUser(user.id); }
```

**Fix:**
Replace sequential loops with `Promise.allSettled()` for bounded concurrent execution:
1. User delete: parallelize AWG + XUI deletion (2 calls max) — trivial `Promise.allSettled`
2. User sync: batch users into concurrency-limited groups (e.g., 5 concurrent) using a simple pool or `p-limit`-style utility

`Promise.allSettled` (not `Promise.all`) ensures partial VPN failures don't abort the entire operation — one service failing shouldn't prevent the other from completing.

**Impact:**
- User delete: 20s → 10s worst case (parallel AWG + XUI)
- User sync: linear → O(N/concurrency) scaling
- `allSettled` preserves partial-failure reporting (already pattern exists in panel-sync-client)
- No new dependencies if using a simple pool utility (10-line implementation)

**Files:** `src/app/api/users/[id]/route.ts`, `src/lib/user-sync.ts`
**Verify:** User delete with 2 active protocols completes in ≤12s instead of ≤22s. Sync of 10 users shows parallel execution in logs.
