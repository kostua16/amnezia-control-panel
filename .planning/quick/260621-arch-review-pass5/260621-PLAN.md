## New Proposals (non-duplicative)

### Proposal 13: Panel push sequential stall — no circuit breaker

**Severity:** High (UX/Reliability)
**Area:** `src/lib/panel-sync-client.ts` → `pushConfigToAllPanels()`

**Problem:**
`pushConfigToAllPanels` processes panels sequentially. Each dead panel currently blocks up to **67 seconds**:
- 4 fetch attempts × 15s `AbortSignal.timeout` = 60s
- Plus backoff delays: 1s + 2s + 4s = 7s

One unreachable panel stalls the entire push. Admin sees no progress for nearly a minute.

Additionally, `pushConfigToPanel` has no circuit breaker and its retry loop appears off by one:
`attempt <= RETRY_DELAYS.length` yields 4 attempts even though the comment describes 3 total attempts.
The function therefore retries the full 4-attempt pattern even when the panel has been consistently failing.

**Proposed fix:**
1. Push panels in parallel with `Promise.allSettled()` instead of sequential `for` loop
2. Add per-panel circuit breaker: track last N failure timestamps; if panel failed 3 consecutive
   times within a 5-minute window, skip it with an immediate "panel degraded" result and a
   suggestion to check connectivity
3. Fix the retry loop to match the intended attempt count, then reduce `AbortSignal.timeout`
   from 15s to 8s for individual attempts (still generous for Tailscale mesh, but caps
   worst-case to ~31s per panel with 3 attempts plus backoff)

**Files:** `src/lib/panel-sync-client.ts`
**Effort:** Small (~40 lines)

### Proposal 14: Quota monitor N+1 alert dedup queries

**Severity:** Medium (Performance)
**Area:** `src/lib/quota-monitor.ts` → `checkUserQuotas()`

**Problem:**
`checkUserQuotas` iterates active users with quotas and calls `checkQuotaThreshold` per user
per exceeded threshold. Each `checkQuotaThreshold` does `prisma.alert.findFirst()` to check for
recent duplicates.

With 50 users and 3 thresholds (80%, 90%, 100%), worst case is **150 individual DB queries**
per 5-minute check cycle.

**Proposed fix:**
1. Bulk-fetch all recent alerts matching the `quota_*` pattern in a single query:
   ```ts
   const recentAlerts = await prisma.alert.findMany({
     where: {
       type: { startsWith: 'quota_' },
       createdAt: { gte: oneHourAgo },
     },
     select: { type: true },
   });
   const alertSet = new Set(recentAlerts.map(a => a.type));
   ```
2. Replace `checkQuotaThreshold` with an in-memory set lookup — O(1) instead of O(N) DB round-trips

**Files:** `src/lib/quota-monitor.ts`
**Effort:** Small (~20 lines)

### Proposal 15: No rate limiting on auth login endpoint

**Severity:** Medium-High (Security)
**Area:** `src/app/api/auth/login/route.ts`

**Problem:**
The login endpoint has no brute-force protection. For a single-admin panel exposed to the
internet (managing VPN servers), an attacker can attempt unlimited credential guesses. The only
protection is bcrypt's cost factor, which slows individual hashes but doesn't limit attempts.

SQLite handles the load fine — the risk is account compromise, not DoS.

**Proposed fix:**
1. Add in-memory rate limiter on POST `/api/auth/login` (e.g., `rate-limiter-flexible` or a
   simple Map-based sliding window)
2. Allow 5 failed attempts per IP per 15-minute window, then 429 for 15 minutes
3. Log rate-limit events to audit log for visibility
4. For single-admin panels, consider locking the admin account after 10 failed attempts
   (manual unlock via server restart or DB reset)

**Files:** `src/app/api/auth/login/route.ts`, optionally `src/lib/rate-limiter.ts` (new)
**Effort:** Small (~30 lines)
