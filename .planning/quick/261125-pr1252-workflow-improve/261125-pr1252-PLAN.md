## Summary
PR #1252 adds a Linux gh CLI PATH-shim counter (gh-counter.cjs + rest-routes.cjs route classifier), via={node,gh} source split in REST_COUNT reports, and wires preload into ~11 workflows plus 4 composite actions. Remaining gaps: jobs that call `gh` or node API scripts without running setup-environment stay uncounted (after #1252, setup-environment installs the gh shim by default and no script under .github/workflows/scripts/ uses Node HTTP — every call is execFileSync('gh', ...) — so jobs that already run setup-environment are covered), and report-failed inflates gh_unavailable_reports.

## Quick Wins
- Count API traffic in jobs that skip setup-environment -- the node-script-heavy workflows (maintenance.yml, triage.yml, pr-finalizer.yml, monitor-amnezia-control-panel-github-runs.yml, gsd-planning-execute.yml, audit-auto-prs.yml, audit-fix.yml, project-manager.yml, rebase-pr.yml, merge-pr.yml, perf-check.yml, planning-intake-repair.yml) all run setup-environment in the relevant jobs, so after #1252 their gh calls — including execFileSync('gh', ...) from node scripts — are already counted by the default-installed shim; none of their scripts makes Node HTTP calls (no fetch/@actions/github/octokit/https.request outside __tests__), so a bash `preload=(--require ...)` on those steps records nothing, and none of them uses actions/github-script. The residual gap is jobs/steps that invoke `gh` or node API scripts without any setup-environment step, plus actions/github-script call sites outside the wired set (for those, copy the guarded-require preamble pattern): enumerate them, add setup-environment (or the github-script preamble where a full setup step does not fit), and update docs/workflow-e2e-scenarios.md. (owner: kos-audit-fix, type: quick-task)
- Stop counting reason=report-failed as CLI-unavailable in summarize-rate-limit.cjs -- parseRestCount sets 'ghUnavailable: unavailable[1] === 'report-failed'', and summarizeRestCounts then increments gh_unavailable_reports for it. report-failed means the post action itself could not build the report (Node reporting path) — the CLI counter may be healthy, and the job is already visible via unavailable_jobs. Drop the special case (or gate ghUnavailable on actual gh_status/gh_reason evidence) so gh_unavailable_reports tracks only real CLI-counter outages like launcher-shadowed or node-unusable. (owner: kos-audit-fix, type: quick-task)

Dropped at review: "extend checkRestCounterWiring to assert the guarded require body" — the described gap does not exist. checkRestCounterWiring (action-metadata-shape.test.cjs) already asserts, for every opted-in step, `preload=(--require "$REST_COUNTER_PRELOAD")` plus `node "${preload[@]}"` on run: steps and the guarded `try { if (process.env.REST_COUNTER_PRELOAD) require(...) } catch` body on actions/github-script steps; #1252 keeps those assertions and only changes the setup-source lookup. The hand-copied preambles are a duplication smell, not a coverage gap (~19 files post-#1252: the ~12 it touches plus 8 pre-existing on main — _auto-fix-ci.yml, antigravity.yml, antigravity-code-review.yml x2, deepseek-code-review.yml x2, dependency-review.yml x2, issue-catch-up.yml x3, pr-improve.yml, pr-policy.yml — all already satisfy the generic body assertion).

## pr1252.x Phase Candidates
- pr1252.1: Generated, exhaustive enforcement of the API-call instrumentation policy -- Today only a hand-written 'required' map in action-metadata-shape.test.cjs (auto-pr-branch-cleanup.yml and two workflow-health-optimize.yml jobs) forces preload on bash steps invoking node scripts; everything else relies on reviewers copying the pattern. Generate the required-steps list by parsing step `run:` bodies and step `uses:` across all .github/workflows/*.yml and composite actions for 'node .github/workflows/scripts/' and actions/github-script usage — do not raw-scan YAML text, which false-positives on agent-prompt `with:` inputs quoting the literal path (fix-issue.yml:278, monitor-amnezia-control-panel-github-runs.yml:371) and on bare `gh ` inside prompts. Treat a job that runs setup-environment as satisfying bare `gh ` CLI usage (the default-installed shim already counts it) so the e2e gate (npm run test-only + node --test scripts/__tests__) per docs/code-standards.md workflow change protocol flags only genuinely uninstrumented API-calling steps. (owner: kos-workflow-health-optimize)
- pr1252.2: Close the loop: feed REST_COUNT telemetry into workflow-health-optimize -- The counter now records via={node,gh}, graphql_via, gh_status and gh_unavailable_reports per job, but nothing consumes them. Add a WHO sweep step that pipes job logs through summarize-rate-limit.cjs across a lookback window, ranks top quota consumers by route template, flags jobs persistently gh_status=unavailable (e.g. launcher-shadowed after a PATH change), and files deduped issues — turning the instrument into a request-reduction loop for pagination-heavy scripts like fetch-auto-cover-context.cjs and cleanup-orphan-branches.cjs. (owner: kos-workflow-health-optimize)
- pr1252.3: Quota guard on the pr-finalizer / auto-merge path -- pr-finalizer.yml (~10 gh calls + 6 node scripts per PR close) and merge-pr.yml already have their gh calls counted (both run setup-environment, so #1252's default shim instruments them; no extra preload wiring needed — that would duplicate the Quick Win 1 audit), but they spend budget with no pre-flight check: during burst merges they can exhaust the shared GITHUB_TOKEN core budget and fail auto-merge governance steps non-deterministically. Add a pre-flight check against log-rate-limit's `core-remaining` output (exposed by setup-environment) that defers non-critical work (label cleanup, status comments) when remaining quota drops below a threshold, keeping merge/approval-critical calls budgeted. (owner: kos-audit-auto-prs)
