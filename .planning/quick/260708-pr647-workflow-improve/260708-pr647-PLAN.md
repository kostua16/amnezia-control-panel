# Quick Plan: PR #647 workflow improvement intake

## Source
- PR #647: feat: replace sticky workflow comments on refresh
- URL: https://github.com/kostua16/amnezia-control-panel/pull/647

## Summary
PR #647 replaces sticky comment update-in-place with create-then-delete across 4 workflow files (dependency-review, planning-intake-repair, pr-finalizer, pr-improve) and adds replaceExisting to the shared sticky-comment.cjs library. Key finding: the 4 workflows duplicate the pattern inline via github.rest.issues.* API instead of calling the shared library that already implements it via gh api — creating a 5-place maintenance burden. Secondary: create-then-delete has an error-handling gap where a failed DELETE after a successful POST leaves duplicate marker comments.

## Quick Wins
- Migrate 4 inline sticky-comment blocks to shared upsertComment() -- dependency-review.yml:198, planning-intake-repair.yml:142, pr-finalizer.yml:182, and pr-improve.yml:242 each duplicate the create-then-delete logic inline using github.rest.issues.* calls, while sticky-comment.cjs already exports upsertComment({ replaceExisting: true }) doing the same via gh api. Refactoring these 4 call sites to shell out to a thin wrapper around the shared lib eliminates 4 copies and ensures future behavior changes touch one place. (owner: workflow-maintainer, type: quick-task)
- Add error-handling guard for partial create-then-delete failure in sticky-comment.cjs -- In sticky-comment.cjs upsertComment(), if the POST (create new comment) succeeds but the subsequent DELETE (remove old comment) throws, two comments with the same marker coexist. Next run's findExistingComment() matches the first hit, leaving a ghost comment that accumulates across reruns. Wrap the DELETE in a try/catch that logs the orphan comment ID so a sweep can clean it up. (owner: workflow-maintainer, type: quick-task)

## pr647.x Phase Candidates
- pr647.1: Enforce shared-library-only rule for sticky comment operations -- The PR demonstrates the pattern: new behavior gets copy-pasted into inline workflow JS blocks instead of going through sticky-comment.cjs. A CI lint step or pre-commit check that scans .github/workflows/*.yml for direct github.rest.issues.createComment/deleteComment calls outside comment-posting-only workers would catch future duplication before merge. (owner: workflow-maintainer)
- pr647.2: Add e2e scenario for sticky comment replacement ordering -- workflow-e2e-scenarios.md V2/V6 were updated to describe 'deleted and refreshed as latest timeline comment' but no corresponding e2e test verifies the old comment is actually deleted after the new one appears. Adding a test that asserts comment count stays at 1 per marker after a rerun would guard against the ghost-comment accumulation failure mode. (owner: workflow-maintainer)
