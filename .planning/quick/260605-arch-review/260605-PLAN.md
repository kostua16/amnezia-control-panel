## Proposal 1: GeoIP Lookup Index — Replace Linear Scan with Prefix Trie

### Problem

`geoip-manager.ts:lookupCountry()` (line 350-370) iterates every country × every CIDR for each lookup.
v2fly geoip.dat has ~250 countries with thousands of CIDRs. This is O(N×M) per lookup.

The function sits in the chain-application hot path:
`chain-router.ts` → `resolveGeoRoute()` → `lookupGeoIP()` → `GeoIPManager.lookupCountry()`

### Solution

Build a sorted `[networkNum, mask, countryCode]` array at parse time and use binary search for O(log N) lookups.
Alternatively, build a prefix trie (radix tree) for O(prefix_length) lookups.

### Scope

- `src/lib/geoip-manager.ts`: Add `private lookupIndex` built during `parseDatFile()`
- Rewrite `lookupCountry()` to binary-search the index
- Update tests in `src/lib/__tests__/geoip-manager.test.ts`

### Impact

Geo-routing decisions drop from ~250×thousands iterations to ~log₂(total_cidrs) ≈ 15 comparisons.
No schema or API changes.

## Proposal 2: Extract Shared `postConfigToRemote()` in config-applier

### Problem

`applyAwgConfig()` and `applyThreeXuiConfig()` in `config-applier.ts` share ~80% identical code:
- HMAC signing
- POST to `/api/sync/apply` with same headers
- Identical 200/404/other error handling
- Identical error enrichment pattern

Both functions are ~90 lines; only the service type and payload shape differ.

### Solution

Extract a shared `postConfigToRemote<T>(url, panelName, apiKey, payload, serviceType)` function that handles signing, fetch, response parsing, and error enrichment. The two public functions become thin wrappers.

### Scope

- `src/lib/config-applier.ts`: Extract shared helper, slim down both apply functions
- `src/lib/__tests__/config-applier.test.ts`: Update test expectations if function signatures change

### Impact

~60 lines of duplicated error handling collapsed into one place.
Bug fixes (e.g., timeout handling, error enrichment) propagate to both paths automatically.

## Proposal 3: Replace Full-Table Traffic Aggregate with Rolling Counter

### Problem

`real-time-broadcaster.ts` (line 16-47) runs `prisma.trafficLog.aggregate({ _sum: { bytesIn, bytesOut } })` every 30 seconds with NO time filter. This scans the entire `traffic_logs` table.

As the table grows, this query degrades linearly. SQLite has no materialized views or query cache.

### Solution

Option A: Add a `TrafficSummary` model that stores pre-computed totals, updated incrementally when traffic logs are written. Broadcaster reads the single row.

Option B: Time-bound the aggregate to a recent window (e.g., last 24h) and accept that "total traffic" is approximate for the dashboard stat.

### Scope

- `src/lib/real-time-broadcaster.ts`: Replace aggregate query
- `prisma/schema.prisma`: (Option A) Add TrafficSummary model
- Traffic-writing codepaths: (Option A) Increment summary on write

### Impact

Dashboard stats query drops from O(total_rows) to O(1) or O(recent_rows).
Prevents future performance regression as traffic data accumulates.
