## Quick Wins
- Gate reconcileEscalationLabels behind a durable, cadence-re-verified completion marker -- escalate-repeated-fixes.cjs:reconcileEscalationLabels() issues 'gh issue list --search 'APR-E10 escalate in:title' --limit 500' on EVERY audit run forever (audit-auto-prs.yml runs every 3h, cron '17 */3 * * *' → 8 scans/day), even after it returns 0 relabeled — the code comment accepts this as 'a no-op scan'. The repo is actively cutting per-run REST calls (de15daa9 'ci(code-review): cut REST calls per run', ecf3ddef per-job REST counter). Persist completion state somewhere durable and versioned — a committed state file or a repository variable — and state which credential owns the marker: the escalation step runs in publish-digest under GH_TOKEN=secrets.GH_PAT, so `gh variable set` must be owned by that PAT with the repo Variables write scope (the default GITHUB_TOKEN is not granted it), and a committed state file needs contents:write added to the publish-digest job (currently contents:read) plus a branch-protection-safe push path for the scheduled run. NOT a free-form line in the recommendation-log issue body (buildLogBody regenerates the whole body from entries on every run, and trimEntries evicts entries past MAX_LOG_ENTRIES=20, so a marker line is erased or evicted) and NOT a '--migration-done' GITHUB_OUTPUT (per-run only, nothing consumes it on the next run). The gate must stay bounded, not permanent: skip the scan while the marker exists AND the last scan relabeled 0 with no legacy label found — except on a fixed re-verification cadence (e.g. the first run of each UTC day, derived from the marker's last-refreshed date so the cadence check costs zero REST calls), where the scan runs unconditionally and re-derives the marker. The re-scan IS the re-arm observer, and the observer must NOT be a per-run label-filtered call (e.g. `gh issue list --label umbrella-sub-issue --state all`): every spun-off sub-issue carries umbrella-sub-issue (umbrella-sub-issues-core.cjs:67), so a label-filtered observer hits and clears the marker on essentially every run — the scan is never skipped and the stated REST saving never materializes; even scoped, it is itself one `gh issue list` request per run traded against the single narrow scan it gates (net zero saving plus new durable state); and it must not rely on the default `gh issue list` window (30 results, newest first), which can miss a reopened pre-split escalation — the observer is the same exact title predicate 'APR-E10 escalate in:title' with explicit --limit 500, so a reopened, late-indexed, or missed match re-enters within one cadence window regardless of label state. Net: 8 scans/day → 1, with the reopen blind window bounded to one cadence period. Once the scan is skipped no existing code reads issue labels — reconcileEscalationLabels is the only label reader and it is gated off, findEscalationIssue searches titles only, and createEscalationIssue only writes the new label — so 'seen on any issue again' never fires on its own; the cadence re-scan is what re-arms the gate. Sequenced AFTER quick win 3's non-open-state pass. Unit-testable with the existing injectable runGh harness in escalate-repeated-fixes.test.cjs.
