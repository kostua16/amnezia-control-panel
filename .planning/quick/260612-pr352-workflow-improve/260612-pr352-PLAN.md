# Quick Plan: PR #352 workflow improvement intake

## Source
- PR #352: fix: resolve #347 - Security: esbuild RCE + arbitrary file read (HIGH) and postcss XSS (moderate)
- URL: https://github.com/kostua16/amnezia-control-panel/pull/352

## Summary
PR #352 bumps esbuild 0.28.0→0.28.1 (HIGH RCE/file-read CVE) and postcss 8.5.12→8.5.15 (moderate XSS), removes a stale `next/node_modules/postcss@8.4.31` nested shadow, and adds `postcss` to `package.json` overrides. The analysis reveals 4 concrete quick-task follow-ups and 4 milestone-scale phase suggestions across the requested buckets. The most impactful gap: `npm audit` runs nowhere in CI — only `npm audit signatures` (provenance) runs in supply-chain.yml, leaving CVEs undetected at merge time.

## Quick Wins
- Add npm audit gate to ci.yml -- CI runs lint/typecheck/test/build but never `npm audit`. Adding a dedicated `security-audit` job with `npm audit --audit-level=high` on every PR/push would have caught the esbuild RCE before it reached main. Narrow change: one job (~15 lines) in `.github/workflows/ci.yml`. (owner: maintainer, type: quick-task)
- Add npm audit --audit-level=high to supply-chain.yml alongside signatures check -- supply-chain.yml already triggers on package-lock.json changes but only verifies provenance signatures (`npm audit signatures`). Adding `npm audit --audit-level=high` as a non-continue-on-error step catches CVEs at the exact moment a vulnerable lockfile is introduced. (owner: maintainer, type: quick-task)
- Schedule a weekly npm audit workflow to catch CVEs between Dependabot runs -- Dependabot checks weekly on Mondays but groups minor/patch updates. CVEs published mid-week (like the esbuild RCE) can sit undetected. A scheduled workflow running `npm audit --audit-level=high` that opens a GitHub issue on failure fills this gap. Model after `audit-fix.yml` cadence. (owner: maintainer, type: quick-task)
- Track removal of postcss override once Next.js bundles postcss ≥8.5.15 -- The `"postcss": "^8.5.12"` override in package.json is a band-aid for Next.js shipping a stale nested postcss@8.4.31. Once Next.js updates its bundled postcss dependency, the override becomes unnecessary and should be removed to avoid masking real version requirements. Create a tracking issue. (owner: maintainer, type: quick-task)

## pr352.x Phase Candidates
- pr352.2: Automated CVE severity gate in CI with configurable thresholds -- The CI pipeline lacks any vulnerability scanning. A new `security-audit` job in ci.yml should run `npm audit` with configurable severity thresholds (fail on HIGH/CRITICAL, warn on MODERATE). This prevents security regressions from merging without human review. The job should use `--audit-level=high` and parse the output for actionable advisories, integrating with the existing PR policy/label system to block auto-merge when HIGH+ CVEs are present. (owner: maintainer)
- pr352.1: Transitive dependency drift detection workflow -- The postcss XSS was caused by Next.js bundling postcss@8.4.31 while the top-level was 8.5.12 — a 30+ minor version gap in a nested dependency. No existing workflow detects this pattern. A scheduled workflow should compare versions of security-critical nested deps (esbuild, postcss, ws, nanoid) across the full dependency tree and open issues when nested versions drift beyond a threshold from the top-level. This would have flagged the postcss 8.4.31→8.5.12 gap proactively. (owner: maintainer)
- pr352.3: Security-override PR classification in PR Policy and Finalizer -- PR #352 modified `package.json` overrides to fix CVEs. Currently pr-policy.yml applies `area/dependencies` and `needs-review` only when the override is in a workflow/planning path. PRs touching `package.json` overrides or fixing CVEs should be classified as security-sensitive, get `needs-review` + `area/dependencies` labels, and route to `manual_only` in the PR finalizer — preventing auto-merge of security patches without maintainer approval. Extend policy.json with a `securityOverride` classification. (owner: maintainer)
- pr352.4: GSD security-fix intake workflow (gsd:quick --security template) -- Security CVE responses like PR #352 are currently manual: identify the CVE, find the affected dep tree, bump versions, add overrides, verify with npm audit. A GSD quick-task template for security fixes would automate this: read the CVE advisory from npm audit output, determine affected dependency tree, propose version bumps and override additions, and use `npm audit` as the verification gate. This turns ad-hoc security PRs into a repeatable, auditable workflow that can be triggered from CI or manually. (owner: maintainer)
