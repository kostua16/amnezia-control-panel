# Quick Plan: PR #185 workflow improvement intake

## Source
- PR #185: ci(workflows): hourly optimization - 26855106173
- URL: https://github.com/kostua16/amnezia-control-panel/pull/185

## Summary
PR #185 makes two targeted workflow optimizations: (1) a null-PR guard on pr-finalizer.yml that prevents the workflow from running on workflow_run events with no associated PRs, and (2) reducing triage.yml MAX_TURNS from 40 to 15 since triage is a lightweight label/classify task. Both changes are sound. The analysis produced 4 quick-task follow-ups and 4 phase-level suggestions across trust gates, CI correctness, review signals, and planning automation.

## Quick Wins
- Add early-exit no-op guard to workflow-health-optimize.yml optimize job -- The optimize job already gates on has-problems, but the collect-runs job runs every hour unconditionally. When has-runs is false, it still pays the self-hosted runner setup cost. An early-exit at the job level when the hour has zero completed runs would save runner time. (owner: devops, type: quick-task)
- Synchronize workflow-health-optimize.yml MAX_TURNS with the triage reduction pattern -- PR #185 reduced triage MAX_TURNS from 40 to 15 because triage is bounded. The optimize job in workflow-health-optimize.yml still has MAX_TURNS: 40 but is constrained to max 3 file edits and minimal diffs — 25 turns would likely suffice and reduce agent cost on self-hosted runners. (owner: devops, type: quick-task)
- Add workflow_run null-PR guard pattern to other workflow_run consumers -- PR #185 added a null-PR guard to pr-finalizer.yml. If any other workflow adds workflow_run triggers in the future, the same guard pattern should be documented or templated. Quick task: add a comment in policy.json or a shared note documenting the pattern. (owner: devops, type: quick-task)
- Validate that pr-finalizer concurrency group handles workflow_dispatch inputs correctly -- The concurrency key uses github.event.inputs.pr_number, but when triggered by workflow_run (no manual input), this resolves to empty and falls back to github.run_id. This is correct but fragile — a quick validation that no race exists between multiple concurrent workflow_run events for different PRs would confirm safety. (owner: devops, type: quick-task)

## 13.x Phase Candidates
- 13.1: Centralize workflow_run null-PR guard as a reusable gate -- The if-condition added in PR #185 (github.event_name != 'workflow_run' || toJSON(...) != '[]') is a pattern that should be enforced uniformly wherever workflow_run triggers exist. A shared composite action or a evaluate-trigger-policy.cjs check would prevent future workflows from silently running on orphaned workflow_run events. This fits 13.1 (central workflow policy, trust gates). (owner: devops)
- 13.2: Pin MAX_TURNS per workflow based on empirical turn usage -- PR #185 reduced triage MAX_TURNS from 40 to 15 based on the nature of the task. A systematic pass should (a) collect actual turn usage from claude_num_turns outputs in completed runs, (b) set MAX_TURNS for each workflow to 1.5x observed median, and (c) add a comment documenting the empirical basis. This is CI correctness (cost and timeout accuracy). Workflow-health-optimize (40), suggest-improvements (100), code-review (100), and dependency-review (80) are all candidates. (owner: devops)
- 13.3: Add finalizer decision logging for post-hoc approval governance -- The pr-finalizer posts a status comment but does not persist the decision rationale in a queryable form. Adding a structured log entry (e.g., to a claude-health issue or a JSON artifact) would enable auditing approval patterns over time — which PR classes get auto-approved, which get blocked, and why. This supports auto-merge governance under 13.3. (owner: devops)
- 13.4: Auto-generate planning PR follow-ups from workflow-health-optimize findings -- The hourly workflow-health-optimize already analyzes run failures and produces fix PRs. Extending it to also generate planning PRs (using the claude-planning-pr- branch prefix already in policy.json) for non-fixable issues would close the loop between CI observation and roadmap intake. The upsert-planning-pr.cjs script already exists — it just needs to be invoked from the optimize workflow when the Claude agent identifies architectural rather than YAML-level issues. This maps to 13.4 (planning PRs, milestone/phase intake). (owner: devops)
