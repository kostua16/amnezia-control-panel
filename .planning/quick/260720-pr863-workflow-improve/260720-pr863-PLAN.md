# Quick Plan: PR #863 workflow improvement intake

## Source
- PR #863: fix: resolve #707 - WHO-I02: Bound failure-log collection in 'collect-runs' (workflow-health-optimize)
- URL: https://github.com/kostua16/amnezia-control-panel/pull/863

## Summary
PR #863 wraps 'runs_data' in an envelope '{failureLogCapApplied, failureLogCapMax, failureLogCapTotal, runs: [...]}' to bound failure-log API calls at 10. The cap logic is sound, but the downstream claude agent in the 'optimize' job is never told about the new envelope shape — it still expects a raw array. Three concrete follow-ups identified: downstream envelope awareness, truncation ordering, and skipped-run traceability.

## Quick Wins
- Teach downstream optimize agent about the runs_data envelope -- The 'optimize' job injects 'runs-data' into the claude agent prompt at 'workflow-health-optimize.yml:309'. Before this PR the value was a plain JSON array; now it's '{failureLogCapApplied, failureLogCapMax, failureLogCapTotal, runs: [...]}'. The agent contract in 'kos-workflow-health-optimize.md' says 'Assess the provided run data' with no mention of unwrapping '.runs'. The claude agent will receive the envelope object and may try to iterate it as an array, missing all run entries. Fix: update the prompt block (lines 302–342) to instruct the agent to access '.runs' from the envelope and use the cap metadata to annotate ambiguous findings. (owner: workflow-health-optimize, type: quick-task)
- Move 50KB truncation check after envelope construction -- In 'collect-runs', the truncation loop at line 229 ('while (JSON.stringify(trimmed).length > 51200 ...)') checks the bare array size, but envelope wrapping (lines 78–85) happens afterward. The final 'runsJson = JSON.stringify(envelope)' at line 85 can exceed 50KB. Currently harmless (envelope metadata is ~100 bytes) but violates the stated 50KB constraint and will silently break if envelope fields grow. Move the size check to after 'JSON.stringify(envelope)' and truncate 'envelope.runs' instead of a bare 'trimmed' variable. (owner: workflow-health-optimize, type: quick-task)
- Include run URL in skipped failure-log entries for manual follow-up -- When a failed run is outside the 'MAX_DETAILED_FAILURES' cap, 'workflow-health-optimize.yml:166' sets 'summary.failureLogs = [{job: 'skipped', reason: '...'}]'. The 'summary' object already has 'url', 'runNumber', and 'name' fields, but the 'failureLogs' entry doesn't include 'summary.url'. Operators reading the capped output cannot click through to investigate the skipped failure. Add 'url: summary.url' to the skipped entry so downstream consumers (PR body evidence, trend analysis) have an actionable link. (owner: workflow-health-optimize, type: quick-task)

## pr863.x Phase Candidates
- pr863.2: Add e2e coverage for capped failure-log envelope in collect-runs -- The PR changes the shape of 'runs_data' from a plain array to an envelope object. The repo's e2e suite under '.github/workflows/scripts/__tests__/' should have a case that: (a) simulates >10 problem runs, (b) asserts 'failureLogCapApplied === true' and 'failureLogCapTotal > MAX_DETAILED_FAILURES' in the output, (c) asserts capped runs carry the 'skipped' marker with a URL, and (d) asserts the optimize prompt's injected JSON is valid. Without this, future changes to the envelope shape risk silent breakage in the downstream claude agent. (owner: workflow-health-e2e)
- pr863.2: Make MAX_DETAILED_FAILURES configurable via workflow env or inputs -- The cap is hardcoded as 'const MAX_DETAILED_FAILURES = 10' in the inline script at 'workflow-health-optimize.yml:101'. Different repos or periods (post-release spike) may warrant a higher or lower cap. Expose it as 'env.MAX_DETAILED_FAILURES' with the current 10 as default, so operators can override per-run via 'workflow_dispatch' inputs without editing the YAML. (owner: workflow-health-optimize)
