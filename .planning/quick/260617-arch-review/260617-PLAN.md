## Proposal 1: Migrate audit-log.ts from Raw SQL to Prisma ORM

**Severity:** Medium (Correctness / Maintainability)
**Area:** `src/lib/audit-log.ts`, `prisma/schema.prisma`

### Problem

The `AuditLog` model already exists in `prisma/schema.prisma` (lines 370–384) with proper `@@map("audit_logs")`, three indexes, and typed fields. However, `src/lib/audit-log.ts` **completely bypasses Prisma**:

1. **`ensureAuditLogTable()`** (lines 16–42) creates the table via `$executeRawUnsafe` with a hardcoded `CREATE TABLE IF NOT EXISTS` DDL statement, plus three `CREATE INDEX IF NOT EXISTS` calls.
2. **`writeAuditLog()`** (lines 44–62) inserts via raw SQL tagged template literal with manual `JSON.stringify(input.metadata)`.

This creates dual ownership of the same table:
- Prisma migrations manage the schema definition
- Runtime code recreates the same table via raw DDL
- The raw DDL column definitions (e.g., `resourceId TEXT`) diverge from the Prisma model (`resourceId String` with `@@index`)
- Metadata is serialized manually instead of using Prisma's native `Json` type handling
- Any future schema change (adding columns, changing types) must be updated in **two places**

The `$executeRawUnsafe` on the CREATE TABLE is particularly concerning — the function name itself signals the risk, even though in this case the SQL is a string literal.

### Concrete Divergence

| Aspect | Prisma Schema | Raw SQL in audit-log.ts |
|--------|--------------|------------------------|
| resourceId type | `String` (nullable) | `TEXT` (nullable) |
| metadata type | `String` (Prisma `String`, not `Json`) | `TEXT` (manual JSON.stringify) |
| Index creation | Via `@@index` annotations in schema | Via `CREATE INDEX IF NOT EXISTS` at runtime |
| Insert method | `prisma.auditLog.create()` (typed) | `$executeRaw` (untyped) |

### Proposal

1. Delete `ensureAuditLogTable()` entirely — Prisma migrations handle table creation.
2. Replace `writeAuditLog()` with `prisma.auditLog.create()`:
   ```ts
   export async function writeAuditLog(input: AuditLogInput): Promise<void> {
     try {
       await prisma.auditLog.create({
         data: {
           action: input.action,
           resource: input.resource,
           resourceId: input.resourceId == null ? null : String(input.resourceId),
           actor: input.actor ?? 'admin',
           outcome: input.outcome ?? 'success',
           metadata: input.metadata ? JSON.stringify(input.metadata) : null,
         },
       });
     } catch (error) {
       console.error('[audit-log] Failed to write audit event:', error);
     }
   }
   ```
3. Optionally, change the `metadata` field in Prisma schema from `String` to `Json` for native JSON handling (separate migration).

### Affected Files

- `src/lib/audit-log.ts` — remove raw SQL, use Prisma ORM
- `prisma/schema.prisma` — optionally change `metadata` field type to `Json`

### Acceptance Criteria

1. `ensureAuditLogTable()` removed — no raw DDL anywhere in the codebase
2. `writeAuditLog()` uses `prisma.auditLog.create()`
3. All existing audit log consumers produce identical records
4. All tests pass

### Risk

Low. The Prisma model already maps to `audit_logs` — the table name, column names, and indexes are identical. The switch is a drop-in replacement.

## Proposal 2: Promote String-Typed Discriminated Fields to Prisma Enums

**Severity:** Low-Medium (Type Safety / Data Integrity)
**Area:** `prisma/schema.prisma`, all code referencing these fields

### Problem

Several Prisma models use `String` for fields with documented finite value sets. Invalid values are accepted at the DB level and only caught by application logic (if at all):

| Model | Field | Documented Values | Current Type |
|-------|-------|-----------------|-------------|
| `GeoRoutingRule` | `matchType` | `"country"` \| `"region"` \| `"special"` | `String` |
| `RoutingRuleTemplate` | `category` | `"geo"` \| `"ip"` \| `"domain"` \| `"bundle"` | `String` |
| `ChainPreset` | `topology` | `"linear"` \| `"split"` \| `"mesh"` | `String` |
| `GeoRoutingRule` | `source` | `"custom"` \| `"imported"` \| `"template"` | `String` |

Currently, `matchType: "banana"` would be silently accepted by the database. A typo in `category: "domian"` would create a template that no code path can display. These fields function as enums semantically but lack enum enforcement.

Prisma supports enums and generates TypeScript union types for them, giving compile-time safety.

### Proposal

1. Define four new Prisma enums in `schema.prisma`:
   ```prisma
   enum GeoMatchType { COUNTRY REGION SPECIAL }
   enum TemplateCategory { GEO IP DOMAIN BUNDLE }
   enum ChainTopology { LINEAR SPLIT MESH }
   enum RuleSource { CUSTOM IMPORTED TEMPLATE }
   ```

2. Update the model fields:
   ```prisma
   model GeoRoutingRule {
     matchType GeoMatchType  // was: String
     source    RuleSource    // was: String, default("custom")
   }
   model RoutingRuleTemplate {
     category TemplateCategory  // was: String, default("geo")
   }
   model ChainPreset {
     topology ChainTopology    // was: String, default("linear")
   }
   ```

3. Update all TypeScript references to use the generated enum types instead of string literals.

### Affected Files

- `prisma/schema.prisma` — add 4 enums, update 4 fields
- `src/lib/geo-routing.ts` — update matchType usage
- `src/lib/routing-rule-templates.ts` — update category usage
- `src/lib/chain-presets.ts` — update topology usage
- `src/lib/geo-rule-migration.ts` — update source usage
- Any component code referencing these string values

### Acceptance Criteria

1. Prisma generates TypeScript enum types for all four fields
2. Passing an invalid string to these fields produces a TypeScript compile error
3. SQLite enum values are enforced through Prisma Client/runtime validation, not database-level CHECK constraints
4. All existing tests pass
5. Import routing templates and geo rule imports still work (they write correct enum values)

### Risk

Low-Medium. Prisma enums provide generated TypeScript types and Prisma Client validation, but SQLite stores enum fields as `TEXT` and does not add database CHECK constraints. Existing bad data will not fail during migration; it can surface later as Prisma Client runtime errors. Mitigate by auditing and normalizing existing data before migration (`SELECT DISTINCT matchType FROM geo_routing_rules`).

## Proposal 3: Deduplicate Panel HTTP Push Pattern

**Severity:** Low (DRY / Maintainability)
**Area:** `src/lib/panel-sync-client.ts`, `src/lib/config-applier.ts`

### Problem

Two modules push configs to remote panels with near-identical HTTP patterns:

**`panel-sync-client.ts:pushConfigToPanel()`** (lines 88–175):
- POST to `/api/sync/receive`
- HMAC signature via `signPayload(payload, apiKey)`
- Headers: `Content-Type`, `X-API-Key`, `X-Signature`
- Timeout: `AbortSignal.timeout(15000)`
- Retry: 3 attempts with exponential backoff (1s, 2s, 4s)
- WebSocket broadcast of push progress
- Error enrichment via `enrichError()`
- Returns `PushResult`

**`config-applier.ts:pushToRemotePanel()`** (lines 34–~80):
- POST to `/api/sync/apply`
- HMAC signature via `signPayload(bodyPayload, apiKey)`
- Headers: `Content-Type`, `X-API-Key`, `X-Signature`
- Timeout: `AbortSignal.timeout(15000)`
- No retry
- No WebSocket broadcast
- Error enrichment via `enrichError()`
- Returns `ConfigApplierResult`

The shared surface is ~30 lines (signature, headers, fetch call, error enrichment). The differences are:
- Target endpoint (`receive` vs `apply`)
- Retry behavior (yes vs no)
- WebSocket broadcast (yes vs no)
- Response type (`PushResult` vs `ConfigApplierResult`)

This is distinct from the VPN service adapter proposal (260609, which covers CLI/HTTP dispatch per service type). This is the server→server HTTP push layer.

### Proposal

Extract a shared `pushToPanel()` primitive that handles signing, headers, fetch, and response parsing. Each consumer provides the endpoint, retry config, and broadcast callback:

```ts
// src/lib/panel-push.ts
interface PanelPushOptions {
  panelUrl: string;
  panelName: string;
  panelId: number;
  apiKey: string;
  payload: Record<string, unknown>;
  endpoint: string;           // '/api/sync/receive' or '/api/sync/apply'
  retries?: number;           // 0 or 3
  broadcastProgress?: boolean;
}

interface PanelPushResult {
  success: boolean;
  latencyMs: number;
  error: StructuredPushError | null;
  data?: unknown;
}

async function pushToPanel(options: PanelPushOptions): Promise<PanelPushResult>
```

Both `panel-sync-client.ts` and `config-applier.ts` delegate to this primitive, keeping their higher-level orchestration logic (sequential push to all panels, AWG/xui-specific payload building) intact.

### Affected Files

- `src/lib/panel-push.ts` — new shared push primitive (~50 lines)
- `src/lib/panel-sync-client.ts` — delegate to `pushToPanel()`, reduce by ~30 lines
- `src/lib/config-applier.ts` — delegate to `pushToPanel()`, reduce by ~25 lines

### Acceptance Criteria

1. `pushToPanel()` handles signing, headers, fetch, response parsing
2. Both consumers produce identical HTTP requests for equivalent payloads
3. Panel sync retry behavior preserved
4. Config applier no-retry behavior preserved
5. All existing tests pass

### Risk

Very low. Pure extraction — no behavioral change. The existing tests for `panel-sync-client.test.ts` and `config-applier` indirectly cover the HTTP pattern. New tests for the shared primitive add coverage.

## Out of Scope (Confirmed)

- **In-memory state lifecycle** (connection pool, fallback maps, API key cache): Adequate for single-admin, single-process deployment. The `panelApiKeyCache` TTL concern is mitigated by process restart clearing memory.
- **Naive IP matching in `rule-enforcement.ts`**: Acknowledged stub (`startsWith` for CIDR). Actual enforcement happens in Xray/3x-ui, not in this application-level helper.
- **Unified shutdown coordination**: `real-time-broadcaster.ts` and `service-monitor.ts` both have `start()`/`stop()` methods. Process exit handles cleanup. Not a priority for single-process deployment.
- **vpn-services.ts decomposition**: Already proposed in 260611. This review defers to that proposal.
