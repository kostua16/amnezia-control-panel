## Quick Wins
- Extract duplicated manifest-restore block into a shared bash helper -- The 'Restore original head action manifests after push' and always() 'Restore original head action manifests' steps in .github/workflows/rebase-pr.yml duplicate the identical original-head validation + 'git restore --source="$original_head" --staged --worktree -- .github/actions' block (~40 lines each), differing only in the trailing ::error note. Extract to .github/workflows/scripts/restore-head-actions.sh (bash helper convention exists: analyze-claude-runs.sh, edit-issue-labels.sh) with the error note as an argument. Security constraint: the rebase job checks out the PR head with secrets.GH_PAT and contents: write, so a step must never run 'bash ./.github/workflows/scripts/restore-head-actions.sh' from the checkout -- that executes PR-head code with repo write credentials. Require the trusted-control-dir form the workflow already uses: .github/workflows/scripts is copied from the trusted github.workflow_sha checkout into $REBASE_CONTROL_DIR ('cp -R .github/workflows/scripts "$control_dir/scripts"' at rebase-pr.yml:128) and invoked as "$REBASE_CONTROL_DIR/scripts/restore-head-actions.sh"; placing the helper under .github/workflows/scripts puts it in that existing recursive copy, so no export-step change is needed -- but commit it executable (mode 100755), since the step invokes the path directly rather than via 'bash'. Must update src/lib/__tests__/workflow-triggers.test.ts regexes that pin inline 'run: |' git commands in the job YAML (assert the script content + step invocation instead), and keep both gates green per the workflow-change protocol (npm run test-only AND 'cd .github/workflows && node --test scripts/__tests__/*.test.cjs' exactly as docs/code-standards.md:122 requires -- a bare 'node --test scripts/__tests__/*.test.cjs' from the repo root matches the unrelated root suite and silently skips the workflow tests). (owner: gh-workflow-engineer, type: quick-task)
- Teach run monitoring the 'rebase succeeded - manifest cleanup failed' outcome -- The PR introduces ::error title='rebase succeeded - manifest cleanup failed' in both restore steps, but grep shows zero matches for 'manifest cleanup' / 'Index was out of range' across .github/workflows/scripts/*.cjs and src/lib. Run monitoring will classify a red run whose push and summary already succeeded as a real workflow failure, risking requeue/escalation of an already-completed rebase. Add the error-title string as a known cleanup-only outcome in the run failure classification path (e.g. the same taxonomy layer as classify-* / escalate-repeated-fixes.cjs) so it is reported but not re-dispatched. (owner: kos-run-monitoring, type: quick-task)
- Bound the post-push window with per-step timeout-minutes -- The restore-after-push comment admits a timeout-minutes or runner-shutdown termination between push and the restore 'can hardly leave the rebased manifests on disk' — but no step after 'Push rebased branch' in rebase-pr.yml carries a timeout-minutes (only two timeout entries exist in the file, at lines 71 and 114, both before the push): Capture new head SHA, Disable auto-merge (gh pr merge network call), Wake the PR orchestrator, and Post summary (upsert-rebase-comment.cjs, the last step before the always() restore) are all unbounded. A hung wake or summary step burns the whole job budget and shrinks the chance the always() restore runs cleanly. Add tight explicit timeout-minutes to the post-push network/git-inspection steps only (Capture new head SHA, Disable auto-merge, Wake the PR orchestrator, Post summary) so the admitted window is bounded by seconds; the two manifest-restore steps are post-push too but must NOT get a tight timeout -- killing 'git restore --staged --worktree -- .github/actions' mid-run would leave exactly the half-restored manifests this fix exists to prevent and fail an otherwise successful run, so give them the remaining job budget or leave them without a step timeout. Record the residual shutdown-only window in the RB10 row of docs/workflow-e2e-scenarios.md. (owner: gh-workflow-engineer, type: quick-task)

## pr1243.x Phase Candidates

Those restores are step-scoped rather than always() post-job steps, which is the actual gap: a timeout or runner shutdown between the rewrite and the restore can still trigger the actions/runner#2816 crash, and nothing prevents a future workflow from re-checking out / rewriting .github/actions mid-job without any restore at all. Derive the gate scope from that inventory (rebase-pr.yml, audit-fix.yml, fix-issue.yml, fix-review.yml) rather than a single-workflow premise. Extend the characterization layer (src/lib/__tests__/workflow-triggers.test.ts, which already scans workflow YAML) with a repo-wide invariant scan: any job that invokes ./.github/actions/* before mutating its worktree must end with an original-head manifest-restore always() step. Turns PR #1243's one-off fix into a permanent CI gate in the ci-correctness family (perf/build/CI accuracy). (owner: gh-workflow-engineer)
