# Quick Plan: PR #1076 workflow improvement intake

## Source
- PR #1076: fix: resolve #1071 - MNT-I09: Trim allowed-tools to the sweep's needs (maintenance)
- URL: https://github.com/kostua16/amnezia-control-panel/pull/1076

## Summary
PR #1076 is sound: it moves debug-doc pruning into a deterministic script and stops the maintenance agent from inheriting the repo's wide Bash grants. Three narrow follow-ups remain in the sweep itself. The allowlist is now fully enumerated, but 'run-zai' still appends 'Agent' and 'TaskCreate' to it unconditionally, wider than the 'kos-maintenance' agent contract. The new prune script keys on 'status: resolved', a value no debug doc in '.planning/debug/' has, so it prunes nothing. The settings-isolation generator lives in an unlinted heredoc that the test scrapes out of the YAML. At phase scale: extend settings isolation to the other read-only Claude workflows with a policy test, finish converting the sweep's agent-judgment checks into scripts with exact issue titles, and path-scope trust for the maintenance PR now that only a script can change the tree. This intake supersedes the pre-merge pass for the same PR and carries over what is still open there: broad 'git' and 'gh' grants in the deepseek review and monitor workflows, and a single home for allowed-tools policy.

## Quick Wins
- Make the 'Agent' and 'TaskCreate' append in 'run-zai' opt-out-able and turn it off for maintenance -- Merged #1076 already dropped the bare 'Bash(rtk:*)' wildcard: the allowlist at '.github/workflows/maintenance.yml:112' enumerates every grant ('Read', 'Glob', 'Grep', the health query, 'Bash(npm audit --json)', the exact 'git log --grep' call, and a 'Bash(...:*)' plus 'Bash(rtk ...:*)' pair for six 'gh' subcommands), and the test 'maintenance runs pruning before change detection and pins the explicit tool grants' ('.github/workflows/scripts/__tests__/prune-stale-debug-docs.test.cjs:50') asserts 'deepEqual' of the sorted allowlist against that set ('prune-stale-debug-docs.test.cjs:91'), so a wildcard cannot come back without failing CI. What remains is the append: 'run-zai' adds ',Agent,TaskCreate,TaskUpdate,TaskGet,TaskList' to the caller's allowlist ('.github/actions/run-zai/action.yml:224') with no input to drop any of it. Two of those five tools, 'Agent' and 'TaskCreate', are outside the 'kos-maintenance' agent contract, which lists only Glob, Grep, Read, Bash, TaskGet, TaskList, TaskUpdate ('.claude/agents/kos-maintenance.md:5'); 'TaskUpdate', 'TaskGet', and 'TaskList' are in it and must stay appended. Change: add one boolean input to 'run-zai' (for example 'append-agent-tools', default 'true') that gates the 'Agent,TaskCreate' pair only, keep the current behavior as the default, and set it to 'false' in maintenance next to 'user-settings-only' ('maintenance.yml:111'). The value 'run-zai' forwards must resolve to '${{ inputs.allowed-tools }},Agent,TaskCreate,TaskUpdate,TaskGet,TaskList' when the input is on and '${{ inputs.allowed-tools }},TaskUpdate,TaskGet,TaskList' when it is off. Because 'prune-stale-debug-docs.test.cjs' parses 'action.yml' as YAML, it can inspect only expression text, never both resolved strings, so write the gate as one conditional in the 'with:' map — e.g. allowed-tools: ${{ inputs.append-agent-tools == 'true' && format('{0},Agent,TaskCreate,TaskUpdate,TaskGet,TaskList', inputs.allowed-tools) || format('{0},TaskUpdate,TaskGet,TaskList', inputs.allowed-tools) }} — comparing against 'true' because a bare 'inputs.append-agent-tools &&' is truthy for the string 'false' — and replace the single-string 'assert.equal' on 'wrapper.with['allowed-tools']' in the test 'run-zai forwards settings isolation to every Claude attempt' ('prune-stale-debug-docs.test.cjs:122-123') with branch coverage of that expression: assert it references 'inputs.append-agent-tools' and contains both the on-branch literal '{0},Agent,TaskCreate,TaskUpdate,TaskGet,TaskList' and the off-branch literal '{0},TaskUpdate,TaskGet,TaskList'; the '{0}' prefix keeps the off-branch literal from being a substring of the on-branch one, so dropping either branch fails the test. Run both e2e suites per the workflow change protocol. (owner: workflow-health-optimize, type: workflow-improvement)
- Make debug-doc retention match GSD's real status vocabulary: 'status: resolved' prunes nothing -- 'prune-stale-debug-docs.cjs' deletes only docs whose frontmatter says 'status: resolved'. No doc in '.planning/debug/' carries that value. Of the 12 docs, 5 carry another status ('fixed' at '.planning/debug/users-create-404.md:3', 'fixing', 'diagnosed', 'investigating' at '.planning/debug/pr-522-rebase-disallowed-tools.md:2') and 7 have no top-level 'status:' line at all. GSD's debug template only writes 'status: investigating' ('.claude/get-shit-done/workflows/debug.md:184'); 'status: resolved' belongs to UAT gap frontmatter ('.claude/get-shit-done/workflows/execute-phase.md:1181'), not debug sessions. Every 'updated' date is May or June 2026, so the new deterministic step is a no-op on real data and the P16 row in 'docs/workflow-e2e-scenarios.md' describes a path that never fires. Change: treat 'fixed' and 'resolved' as terminal, add both to the test matrix, and decide what happens to docs with no parseable 'updated' (today they are immortal): fall back to 'created:' or leave them and say so in P16. (owner: workflow-health-optimize, type: workflow-improvement)
- Move the isolated-settings heredoc into a linted script module -- The 'Prepare isolated Claude guard hooks' step in '.github/actions/run-claude-params/action.yml' embeds a 'node - <<'NODE'' program, and the new test in 'prune-stale-debug-docs.test.cjs' digs it out of the YAML with the regex '/<<'NODE'\n([\s\S]+?)\nNODE$/m' and pipes it to 'node -'. The inline JS is invisible to 'eslint .', even though the config covers '.github/workflows/scripts/**' ('eslint.config.mjs:42'). The test also asserts 'post[0].timeout === 5', a value owned by '.claude/settings.json:202', so an unrelated settings edit fails a workflow test. The same PR already established the better pattern for pruning: a 'require.main === module' script under '.github/workflows/scripts/'. Change: extract to '.github/workflows/scripts/build-isolated-claude-settings.cjs' taking the output path as argv[2], call it from the step, 'require' it directly in the test, and derive the expected timeout from the parsed settings file instead of the literal. (owner: workflow-health-optimize, type: workflow-improvement)
- Trim 'Bash(git *)' in the deepseek review workflows -- 'deepseek-code-review.yml:200' and 'deepseek.yml:132' grant 'Bash(git *)', allowing 'git push' and 'git reset --hard'. Review-only workflows need only 'git diff'/'git log'/'git show'. Same class as the fix now on main at '.github/workflows/maintenance.yml:112'. (owner: kos-maintenance, type: workflow-improvement)
- Trim 'Bash(gh:*)' and 'Bash(git:*)' in the monitor workflow -- 'monitor-amnezia-control-panel-github-runs.yml:257' uses colon-star 'Bash(rtk:*)', 'Bash(gh:*)', and 'Bash(git:*)'. Colon-star grants every subcommand, including 'gh repo delete' and 'git push --force'. Narrow each grant to what the agent prompt actually runs. (owner: kos-maintenance, type: workflow-improvement)

## pr1076.x Phase Candidates
- pr1076.1: Roll 'user-settings-only' out to every read-only 'run-zai' caller and enforce it with a policy test -- '.claude/settings.json:15-65' grants 'Bash(git:*)', 'Bash(gh:*)', 'Bash(npm:*)', 'Bash(node:*)', 'Bash(python3:*)', and 'Bash(rtk:*)' to any session that loads project settings. Before this PR there was no way to stop those grants from riding along with a workflow's 'allowed-tools', so every least-privilege allowlist in the repo was wider in practice than on paper. The PR switches the mechanism on for maintenance only. Read-only callers that still load the repo grants: 'project-manager.yml:125' ('Bash(gh api:*)' with the PAT), 'triage.yml:122', 'dependency-review.yml:132' ('Bash(node *)'), 'issue-catch-up.yml:920', 'release-notes.yml:55', and 'pr-improve.yml:167' ('Bash(node *)', 'Bash(rtk:*)'). Phase: flip 'user-settings-only: 'true'' on those callers, trim each allowlist to exact commands, and add one e2e test that parses every 'run-zai' step and fails when a step without 'Edit'/'Write' omits the flag or contains 'Bash(rtk:*)'. That closes the gap the RB5b least-privilege test leaves ('e2e-ai-review.test.cjs:469-486' bans 'Bash(*:*)' and 'Bash(bash:*)' but passes 'rebase-pr.yml:437'). Two limits to respect: keep it to non-writing workflows, because '--setting-sources user' also drops the Write/Edit guards ('gsd-prompt-guard.js', 'gsd-read-guard.js', 'gsd-workflow-guard.js'), 'descriptive-name.cjs', and 'gsd-validate-commit.sh' ('.claude/settings.json:78-146'); and confirm that plugins enabled through 'plugin-marketplaces'/'plugins' ('pr-improve.yml:168-171') survive '--setting-sources user' before flipping that workflow, or exempt it. (owner: claude)

- pr1076.3: Path-scope trust for the maintenance PR now that only a script can change the tree -- After this PR the maintenance agent has no 'Edit'/'Write' and no 'git add'/'git commit', and none of its granted commands is meant to write to the working tree. No bare tool wildcard such as 'Bash(rtk:*)' or 'Bash(git *)' remains in the allowlist ('.github/workflows/maintenance.yml:112'). Its entries are the 'Read', 'Glob', and 'Grep' tools, five exact commands (the health query, 'Bash(npm audit --json)', and the 'git log --grep' call, the last two also as 'Bash(rtk ...)' twins), and twelve prefix grants that stay narrow: a 'Bash(gh ...:*)' and 'Bash(rtk gh ...:*)' pair for each of 'issue create', 'issue list', 'issue view', 'pr comment', 'pr list', and 'pr view'. So the only mutation source is the step 'Prune stale resolved debug docs' ('maintenance.yml:141-142'), and a maintenance PR should never contain anything but deletions under '.planning/debug/'. Nothing asserts that today. The step 'detect_changes' ('maintenance.yml:144-163') accepts any diff, and the step 'Create maintenance PR' opens the PR as non-draft with 'maintenance,needs-review' ('maintenance.yml:239-240'); the project-manager workflow knows it only by title prefix ('.github/workflows/scripts/project-manager.cjs:149'). Phase: have 'detect_changes' or a small script classify the changed paths, fail or mark the PR human-required when anything outside '.planning/debug/*.md' changed, and let the direct-merge decision fast-track the deletions-only case. Add a step summary listing pruned files so a reviewer sees what the script removed without opening the diff. (owner: claude)
- pr1076.4: Centralize allowed-tools policy in policy.json -- PR #1076 fixed one workflow by hand, and the deepseek review and monitor workflows still need the same broad-to-specific trimming.
