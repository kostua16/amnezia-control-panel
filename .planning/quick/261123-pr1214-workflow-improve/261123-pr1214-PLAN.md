# Quick Plan: PR #1214 workflow improvement intake

## Source
- PR #1214: feat(ci): add read-only PR flow sweep shadow
- URL: https://github.com/kostua16/amnezia-control-panel/pull/1214

## Summary
PR #1214 adds a read-only shadow sweep to pr-flow-watchdog.yml: a second cron (8 extra slots/hour) gated by vars.PR_FLOW_SWEEP_MODE=shadow, a new scan-pr-flow.cjs that pages all open PRs via one GraphQL query (lib/open-pr-flow-graphql.cjs), reuses selectStalePrs to compute would-wake reasons, and on recovery slots (7,22,37,52) compares itself against the incumbent watchdog using two cached REST status reads per head with a 90s deadline. Adds a new shadow-only reason 'checks-completed-after-ready' (strict single-attempt check-run evidence), 2 new characterization test files, a YAML invariant test, and doc updates. Analysis found: (1) when the variable is unset, the 8 extra hourly slots still produce ~192 zero-job skipped runs/day that pollute fleet-kpi-digest.cjs's queryGateSkips KPI; (2) comparison evidence exists only as a log line with no retained artifact or promotion criteria; (3) the ready-status sentinel/context constants are duplicated between scan-pr-flow.cjs and watch-pr-flow.cjs; (4) the natural milestone work is implementing the reserved canary/active modes so the watchdog itself migrates from gh pr list + per-head REST reads to the GraphQL page, which also unlocks the checks-completed-after-ready rescue in the real recovery path.

## Quick Wins
- Exclude scan-only watchdog runs from the fleet gate-skips KPI -- With PR_FLOW_SWEEP_MODE unset (rollout default), the new cron '2,12,17,27,32,42,47,57 * * * *' in pr-flow-watchdog.yml still starts ~192 runs/day whose only two jobs ('watch', 'shadow') both skip — GitHub marks those runs conclusion=skipped. fleet-kpi-digest.cjs queryGateSkips (repos/{repo}/actions/runs filtered to conclusion == "skipped", .github/workflows/scripts/fleet-kpi-digest.cjs:206-220) counts every one as a gate skip, silently corrupting the MNT-E03 digest baseline. Exclude those runs in queryGateSkips before the variable is ever set — its jq projection currently selects only {id, name, created_at, updated_at, conclusion}. Discriminator caveat: both crons live in pr-flow-watchdog.yml under the same `name: 'PR Flow Watchdog'` and both fire as `event: schedule` (adding `event` to the projection adds no separating power), so a workflow-name + scheduled-event filter is really a name-based exclusion of every scheduled `PR Flow Watchdog` run. It happens to match only the scan-only slots because the `watch` job is gated by `github.event.schedule == '7,22,37,52 * * * *'`; if that gate changes or another job-level condition appears during the pr1214.2 migration, genuine gate skips silently disappear from the MNT-E03 digest with no error. The robust discriminator is to move the sweep into its own workflow file, so a filter on that workflow's name excludes exactly the scan-only runs. A created_at-minute test (runs whose minute is one of 2,12,17,27,32,42,47,57, derivable from the already-projected created_at) is only a stopgap, and it must be applied after the workflow-name + scheduled-event filter — on its own it would also exclude skipped runs from every unrelated workflow that happens to be created in those minutes. The stopgap assumes a scheduled run starts inside its cron minute, which GitHub does not guarantee: this repo already treats multi-minute queue drift as normal (detect-schedule-drift.cjs reports a problem only when median drift exceeds DRIFT_THRESHOLD_HOURS = 2). A delay of just +5 minutes already moves sweep runs off the sweep-minute set (2→7, 17→22, 32→37, 47→52 — all recovery minutes), so delayed scan-only runs would still be counted as gate skips, the exact KPI pollution this quick win exists to remove; in the reverse direction, a delayed recovery run lands on a sweep minute (7→12, 22→27, 37→42, 52→57) and is silently dropped from the digest. (A head-SHA filter is not viable: scheduled runs report the current default-branch head SHA, which changes with every merge on main.) (owner: kostua16, type: workflow-improvement)
- Persist shadow comparison evidence beyond the job log line -- scan-pr-flow.cjs summary() emits a single 'PR flow shadow {…}' console line and the would-wake/differences evidence lives only in job logs — unqueryable and lost to retention, so the shadow→active promotion decision has no reviewable record. Append the summary JSON to $GITHUB_STEP_SUMMARY (one fs.appendFileSync in summary(), .github/workflows/scripts/scan-pr-flow.cjs:~250) or upload it as a JSON artifact from the shadow job, so divergence trends (comparison.differences, unknown, cost) accumulate per recovery slot. (owner: kostua16, type: quick-task)
- Deduplicate the ready-status context sentinel between shadow and watchdog -- scan-pr-flow.cjs defines its own READY_CONTEXT ('pr-flow/ready') and UNREADABLE_STATUSES = [{context: READY_CONTEXT}], duplicating watch-pr-flow.cjs's local READY_STATUS_CONTEXT and the unreadableStatuses sentinel inside createStatusReader (.github/workflows/scripts/watch-pr-flow.cjs:309). The sentinel shape is load-bearing — selectStalePrs treats it as 'evidence unavailable' — and a drift between the two copies would make the shadow comparison lie. Export the constant pair from watch-pr-flow.cjs and import them in scan-pr-flow.cjs. (owner: kostua16, type: quick-task)

## pr1214.x Phase Candidates
- pr1214.2: Promote the sweep from shadow to the watchdog's active GraphQL data path -- The reserved 'canary' and 'active' values of PR_FLOW_SWEEP_MODE are stubbed off in scan-pr-flow.cjs's mode gate (only 'shadow' works). The incumbent watchdog still pays the per-PR API cost the GraphQL query was built to replace: gh pr list --limit 200 (listOpenPullRequests, watch-pr-flow.cjs:285) plus per-head REST reads on every recovery slot — GET /commits/{sha}/status (createStatusReader) for each open non-draft head, and GET /commits/{sha}/statuses?per_page=100 (createStatusHistoryReader) only for heads whose latest `pr-flow/ready` is still pending or failure-with-flow/finalizer-dispatched. Implementing canary (dual-read, log differences) → active (GraphQL-only) mirrors the #1208 auto-cover consolidation (7 REST → 1 GraphQL) and cuts the recovery slot to one paginated query — the incumbent baseline is one `gh pr list` plus one `GET /commits/{sha}/status` per open non-draft PR (N reads) and `gh repo view` calls that are cached per reader, not per slot — `createStatusReader` and `createStatusHistoryReader` each memoize their own `repository` (watch-pr-flow.cjs:308, :338) and `runWatchdog` constructs both (:413-415), so a slot that fires any history read issues two `gh repo view` calls, not one. The `GET /commits/{sha}/statuses?per_page=100` history read fires only for heads whose latest `pr-flow/ready` is still pending or failure-with-flow/finalizer-dispatched, so typical cost is 1 + N reads (one repo view + N status reads), 2 + N once any history read fires, and 2N + 2 in the worst case of a fleet entirely stuck in a re-poke loop (N history reads plus the second repo view). It also unlocks the shadow-only 'checks-completed-after-ready' rescue (completedRequiredChecks, scan-pr-flow.cjs) in the real recovery path — the existing gh pr list call selects only number,title,url,state,isDraft,labels,headRefOid (listOpenPullRequests, watch-pr-flow.cjs:285-300), no check-run data, so stuck flow/checks-pending PRs (the #695 class) stay invisible to the incumbent. Adding `statusCheckRollup` to that call's --json fields restores visibility of check names and conclusions, but it does not reproduce the strict `checks-completed-after-ready` evidence: `completedRequiredChecks` also requires each check's check-suite id, the joined workflow run's `attempt === 1`, a `pull_request`/`pull_request_target` triggering event, and completion timestamps compared against the ready status `created_at` — none of which `gh pr list --json statusCheckRollup` returns (PR #1214 itself fetches them via a separate GraphQL `checkSuites { workflowRun { databaseId runAttempt event } }` field). The strict single-attempt rescue therefore still needs `GET /repos/{owner}/{repo}/commits/{sha}/check-suites` (or check-runs) REST evidence, or that GraphQL field, even after the statusCheckRollup addition. (owner: kostua16)
- pr1214.1: Sweep rollout governance: maintainer-only comparison dispatch plus written promotion criteria -- The shadow job's if is schedule-only (github.event_name == 'schedule' && vars.PR_FLOW_SWEEP_MODE == 'shadow' && …), so a maintainer cannot trigger an on-demand comparison when evaluating the rollout — evidence only arrives on the crons. And .github/workflows/documentation.md documents how to enable/disable shadow but defines no exit condition. Add a manual-only dispatch path (e.g. a 'sweep' workflow_dispatch input routed to the shadow job with read-only permissions) and document promotion/rollback criteria in documentation.md: N consecutive recovery-slot comparisons with comparison.differences == [], unknown rate below a stated threshold, and observed GraphQL cost/elapsedMs within bounds — plus the rollback step of clearing PR_FLOW_SWEEP_MODE. (owner: kostua16)
- pr1214.3: Extend shadow comparison to escalation decision parity before activation -- compareWatchdog (scan-pr-flow.cjs) validates wake reasons only (scope: 'status-evidence-only'), but the incumbent watchdog also drives a human-review signal: selectStalePrs results feed pm-escalation labeling on ready-pending-loop / finalizer-failure-loop PRs (runWatchdog escalate path, watch-pr-flow.cjs:430-440, scenario C13b). If the active migration ships on status-evidence parity alone, escalation behavior could diverge silently — over-escalating floods the human queue, under-escalating hides stuck PRs. Extend the comparison to predict and diff escalation decisions per PR, and gate the shadow→active promotion on zero escalation divergence too. (owner: kostua16)
