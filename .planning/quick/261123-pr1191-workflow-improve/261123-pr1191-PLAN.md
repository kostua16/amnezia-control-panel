(owner: kos-suggest-improvements workflow → ROADMAP phase, split into the two commits the plan style prescribes)
- pr1191.3: Separate quota bucket for automation identities (App token) so autofix/finalizer stop competing with human pushes -- Plan Out-of-scope "App-token bucket": today every automation workflow (fix-review dispatch, pr-finalizer auto-merge path, auto-cover evaluation) draws from the same installation token bucket that human 'git push' cycles need, which is why a busy autofix day can starve CI. Installing a GitHub App and giving the finalizer/Auto Cover jobs an App installation token moves their REST writes to a separate rate bucket and makes the 'QUOTA_RESERVE' gate meaningful for human traffic. Requires documenting App-token limit semantics and a rollback to 'GITHUB_TOKEN' via a vars switch, mirroring stage 0's pattern. (owner: human maintainer (App registration is an admin action) + kos-suggest-improvements for the workflow wiring plan)
- pr1191.4: Deferred-with-retry semantics for 'pr-improve' (and other once-per-head Claude workflows) under quota pressure -- Item 4 deliberately excludes 'pr-improve.yml' from the reserve gate because a green skip would leave the required 'pr-flow/improve' check pending forever, stranding the PR. A planning-automation phase can add a re-enqueue companion: when 'check-quota-reserve.cjs' defers, the workflow exits green but writes a deferred marker (or relies on the existing 3-hourly scan) that re-dispatches pr-improve for the same head SHA once quota recovers, with a max-age cutoff so stale heads are dropped. This makes Claude/GSD planning PRs quota-safe without breaking required-check semantics — the exact gap called out in the plan's item-4 scope note. (owner: kos-suggest-improvements workflow → ROADMAP entry under the pr-improve/pr-flow automation track)
