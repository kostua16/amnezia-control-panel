## Quick Wins
- Bound fetchCompletedRuns with a server-side 'created=>=' filter -- In the new .github/workflows/scripts/aggregate-run-costs.cjs, fetchCompletedRuns calls 'gh api repos/{repo}/actions/workflows/{workflowFile}/runs --paginate -f status=completed' and filters the 168h window only client-side. The hourly monitor accumulates runs forever, so every hourly cost-telemetry job re-downloads the whole run history (8+ pages today, growing unbounded), wasting REST quota (counted by the log-rate-limit gh wrapper wired via setup-environment) and 10-min job budget. Add '-f created=>=${sinceWithSlack}' as a server-side qualifier (list-workflow-runs supports 'created'), where sinceWithSlack = since minus a queue slack (2h): the script's runTimestamp predicate uses run_started_at || updated_at || created_at and the monitor documents multi-hour queue waits (~1000s), so a run created before the window can still start inside it -- the slack keeps the server-side window strictly wider so the client-side filter, not the server cutoff, keeps defining the window (do NOT pass raw ${since}: that silently drops long-queued runs that currently count). Keep the client-side sinceMs filter as the authoritative window, and keep the existing '--method GET' pin next to the new '-f' field ('-f' implies POST and these GET-only endpoints answer 404 to a POST, per the script's own comment). Extend __tests__/aggregate-run-costs.test.cjs to assert the created qualifier is passed with the slack applied and that '--method GET' is still pinned. (owner: kos-fix-issue, type: quick-task)
- Remove the dead 'errors' array in fetchCompletedRuns -- aggregate-run-costs.cjs declares 'const errors = []' in fetchCompletedRuns, returns it, and never pushes to it: a mid-pagination gh failure is all-or-nothing through execFileSync (runGh returns ok:false for the whole call), so partial-pages-plus-errors cannot occur. Remove the dead field and spell out the caller change so the success path cannot throw: fetchCompletedRuns returns '{ runs }' with no errors field on success (the two failure paths -- invalid --since and runs-list gh failure -- keep returning 'errors: [{ scope, detail }]'), and collectCostTelemetry destructures with a default ('const { runs, errors = [] } = fetchCompletedRuns(...)') so 'errors.length' and '[...errors]' never read undefined; update the affected tests on both the fetch and collect sides. The 'errors.length > 0' check in collectCostTelemetry then only reacts to the invalid-since / runs-list failure paths, which is the actual contract documented in MON-E06c (docs/workflow-e2e-scenarios.md). (owner: kos-fix-issue, type: quick-task)
