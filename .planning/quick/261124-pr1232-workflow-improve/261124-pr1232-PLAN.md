## pr1232.x Phase Candidates
- pr1232.2: Unify all PR/issue label writers on one read-then-delta write helper -- PR #1232 is the third hand-rolled quota cut in the review chain (R25-R27 head-lookup/date reads, now R28/R29 label writes), each copy-pasted as inline YAML JS with its own fail-open semantics. Sweep all remaining label/REST writers — deepseek-code-review.yml, dependency-review.yml, antigravity-code-review.yml, pr-policy.yml, auto-pr-branch-cleanup.yml, issue-catch-up.yml, .github/actions/report-failure/action.yml — onto one shared read-then-delta write helper in .github/workflows/scripts/lib/ (pattern of workflow-labels-diff.cjs), unit-tested outside YAML, with e2e scenario rows in docs/workflow-e2e-scenarios.md pinning 'unchanged state costs zero REST writes' per workflow. Turns a recurring manual pattern into enforced policy. (owner: gh-workflow-engineer)
- pr1232.2: Per-workflow REST-core + GraphQL-points budget attribution for the review chain -- The PR's rationale is quota accounting ('REST core budget' vs 'GraphQL points budget'), and per-run accounting already exists (.github/actions/log-rate-limit logs a job-end RATE_LIMIT reading via setup-environment's report-at-job-end — a reading, not a summary — and every reading records workflow=, core, and graphql buckets; .github/workflows/scripts/summarize-rate-limit.cjs aggregates windows and per-job mismatches only as a manual offline pipe, not run by any workflow; and a step reintroducing rest.issues.listLabelsOnIssue in the Apply review signals step would fail #1232's regex test, which pins only that step's slice). The real gap: readings are not aggregated per workflow, so cuts like R28/R29 cannot be verified run-over-run per workflow. Add a small accounting helper that attributes REST core requests and GraphQL points consumed per run of code-review.yml, pr-flow.yml, and auto-cover-review.yml (wrapping octokit calls or reading /rate_limit deltas), emitted into the job summary so budget cuts and regressions are measurable per workflow. (owner: gh-workflow-engineer)
- pr1232.3: Review-signal freshness validation in pr-flow before auto-merge gating -- The PR documents that review labels can change during a 20+ minute review and that re-runs reuse stored outputs — it fixed the writer side (fresh read at apply time), but pr-flow.yml still consumes ai-review-passed/ai-review-concerns/security-review-passed/security-review-concerns as gate signals without checking they match the review conclusion they came from. Add a characterization phase for the consumer: pr-flow re-derives verdict labels from the latest Code Review run conclusion at gate time (or rejects stale combinations), with e2e simulator scenarios for 'label flipped mid-run' and 're-run with stored outputs' so auto-merge never acts on a label the writer's fail-open path missed. (owner: kos-code-review)
- pr1232.4: Auto-file pr-improve phase_suggestions as umbrella sub-issues -- pr-improve runs (this workflow) return quick_tasks/phase_suggestions as JSON that currently dies in the run log; follow-ups only land when a human re-reads them (see commits 'planning: workflow improvement follow-ups for PR #1181' / '#1191'). The repo already has .github/workflows/scripts/lib/umbrella-sub-issues-core.cjs and the docs/TODOs-2.md stable-ID convention (AFX-xx). Add a workflow step that turns each accepted phase_suggestion into a sub-issue under the workflow-improvements umbrella with a stable TODO ID referenced in issue, commits, and PR, so roadmap intake from PR analysis is automated instead of manual. (owner: kos-gsd-planning)
