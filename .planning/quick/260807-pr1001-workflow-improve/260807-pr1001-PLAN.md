## pr1001.x Phase Candidates
- pr1001.2: Unify queue-latency and schedule-drift signals into a single runner-capacity report -- Two separate tools now measure runner-capacity pressure: (1) detect-schedule-drift.cjs measures cron drift vs expected schedule, (2) the new inline queue-latency code in the monitor workflow measures actual queue wait per run. These are complementary signals — schedule drift shows sustained pressure over days, queue latency shows acute per-run starvation. A unified runner-capacity reporter (or a shared output format consumed by the monitor prompt) would let the agent correlate both signals when diagnosing slow CI. Currently the monitor prompt (line 245+) instructs queue-latency flagging but has no visibility into schedule-drift data, and vice versa. (owner: gh-workflow-engineer)
- pr1001.1: Add runner-capacity incident auto-escalation threshold to monitor workflow -- The PR defines a runner_capacity_queue_threshold_seconds input (default 300s) and instructs the agent to 'report it as a runner-capacity incident' when multiple runs exceed it. But this is advisory text in the prompt — there's no automated escalation (e.g. auto-file an issue, post a warning summary, or mark the run with a specific output that a downstream notification job consumes). For a signal this important (runner starvation blocks all workflows), an automated escalation path would ensure human attention even when the monitor agent's report is buried in a long output. (owner: gh-workflow-engineer)
