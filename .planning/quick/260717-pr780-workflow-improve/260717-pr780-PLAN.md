# Quick Plan: PR #780 workflow improvement intake

## Source
- PR #780: fix(workflows): repair the triage→fix pipeline and add automations that catch stranded issues
- URL: https://github.com/kostua16/amnezia-control-panel/pull/780

## Summary
PR #780 repairs the triage→fix pipeline by replacing bot-authored /triage comments (inert under GITHUB_TOKEN) with real workflow_dispatch API calls, adding invariant detection, and hardening progress-tracking/credential interactions. The diff is large (+348/-29 across 12 files) but tightly focused on issue-pipeline reliability. Three sharp follow-ups and two phase-scale suggestions emerged.

## Quick Wins
- Drop the issue_comment trigger from triage.yml -- PR #780 replaced the re-triage mechanism: catch-up now dispatches triage.yml via the workflow_dispatch API, making the `issue_comment` trigger (triage.yml:5-6) dead weight. Every comment on any issue/PR still starts a triage run that immediately exits 'skipped' — dozens per day of pure runner noise. No `docs/TODOs-2.md` entry exists for this yet (no `TRI-I01`); file one before implementing. (owner: claude, type: quick-task)
- Add re-triage dispatch→run liveness as a flow-simulator test -- No `docs/workflow-e2e-scenarios.md` entry characterizes the re-triage dispatch path (the P11 series ends at P11i; there is no P11j), and no test covers it. The dispatch→run checks in issue-catch-up.yml:105 and :118 (classify step `listWorkflowRunsForRepo` for in_progress + queued triage/fix runs) detect whether a dispatched triage run has started, but no test verifies this detection classifies correctly when runs are missing. A flow-simulator test would replay the dispatch + listWorkflowRuns sequence and assert the classification output. (owner: claude, type: quick-task)
- Harden the Triage Result comment post against silent failure -- The deterministic "Triage Result" comment is authored by the triage agent at triage.yml:134 (a prompt-instructed `gh issue comment` with no programmatic guard) and detected by issue-catch-up.yml:317 (`c.body.includes('Triage Result')`) to key the triaged_no_fix bucket. If that comment post fails (agent omits it, rate limit, locked issue), the issue enters catch-up without triage evidence and flows to triaged_no_fix instead of auto-fix, silently stranding it. (Note: umbrella-sub-issues.cjs:152-158 is only the spin-off link warn + `created #N` log, not this comment post.) Guard: have the triage step verify the "Triage Result" comment landed before completing, or retry. (owner: claude, type: quick-task)

## pr780.x Phase Candidates
- pr780.1: Central workflow policy enforcement for track-progress + persist-credentials invariants -- The P19c test in persist-credentials-hygiene.test.cjs catches the conflicting combo at CI time, but it's a post-hoc gate — a new workflow can still be authored with the regression and fail CI. A pre-commit hook or a shared GitHub Action that validates workflow YAML against the invariant before push would catch it at authoring time. The test suite already has the detection logic; extracting it into a reusable action would give both CI and local enforcement. (owner: claude)
- pr780.2: Structured health state for the claude-health invariant tracker -- The invariant_findings bucket in issue-catch-up.yml reports to a free-form claude-health issue via markdown comments (issue-catch-up.yml:471-538). The findings include structured data (inert_bot_command, stuck_fixable) but the health tracker is human-read markdown — no machine-readable state for automated remediation or dashboarding. A structured JSON comment (or a separate health-state artifact) would enable the monitor workflow to auto-escalate stuck_fixable issues and close resolved invariant findings without human triage. (owner: claude)
