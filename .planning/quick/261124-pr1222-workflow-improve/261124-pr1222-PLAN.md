## Summary
PR #1222 (MNT-I10) adds an inline single-line json-schema to maintenance.yml's run-zai step, drops the inert track-progress input, echoes structured_output into GITHUB_STEP_SUMMARY behind a four-backtick fence, adds a visible-failure guard for successful-but-reportless sweeps, swaps the agent/skill legacy SWEEP:/ESCALATION: text block for the JSON contract, adds a 6-test structural e2e suite (20 assertions), and records MNT-I11 (deferred track-progress half) in docs/TODOs-2.md. Verified in base checkout: build-automation-pr-body.cjs already surfaces the schema's summary field (extractResultText checks 'summary'), the escalation-contract test does not pin the removed text format, and no SWEEP:/ESCALATION: remnants survive outside the two files the PR fixes. Gaps found: (1) skip_reason:'error' lets a silently-failed category pass with findings_count=0 and no signal; (2) the record step's env mapping/if:always() plumbing is unpinned while the guard pins only its own condition; (3) the visible-failure guard is maintenance-only — 10 sibling workflows declare json-schema and depend solely on classify-claude-retry's single retry; (4) structured reports have no longitudinal consumer despite being machine-readable.

## Quick Wins
- Escalate when any sweep category reports skip_reason 'error' -- maintenance.yml's new schema allows skip_reason enum ['no-findings','duplicate','error'] (maintenance.yml json-schema input, per-category outcome block), and the new guard 'Fail when a successful sweep has no structured report' only fires on an empty report. A category whose check could not run (e.g. npm audit --json timeout) reports findings_count=0 + skip_reason='error' and the run still goes green — exactly the silent-degradation class MNT-I10 was meant to eliminate. Extend the same guard step (or add one sibling step) to parse STRUCTURED_REPORT with node and emit ::error:: plus exit 1 when any categories.*.skip_reason == 'error', keeping the report echoed to the summary first. Add a maintenance-sweep-schema.test.cjs assertion pinning the error-escalation behavior, and a row in docs/workflow-e2e-scenarios.md (MNT-I10 series). (owner: gh-workflow-engineer, type: quick-task)
- Pin the structured-report record step's env wiring and always() condition in the e2e test -- maintenance-sweep-schema.test.cjs pins the record step's fence and verbatim echo and the guard's if-condition, but not the plumbing that feeds them: 'Record structured sweep report' reads env STRUCTURED_REPORT from steps.claude_run.outputs.structured_output and runs under if: always(), while the guard checks steps.claude_run.outputs.structured_output directly. If the env key is renamed or the always() dropped, the guard can still pass while the summary silently loses the payload. Add assertions: recordStep (the 'Record structured sweep report' step, located by name in doc.jobs.maintenance.steps) has no 'with' key, recordStep['if'] === 'always()', recordStep.env.STRUCTURED_REPORT === '${{ steps.claude_run.outputs.structured_output }}', and the record step's index precedes the guard step's index in doc.jobs.maintenance.steps. (owner: gh-workflow-engineer, type: quick-task)
