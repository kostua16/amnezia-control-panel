# Quick Plan: PR #1207 workflow improvement intake

## Source
- PR #1207: fix(ci): isolate Auto Cover scan errors per PR
- URL: https://github.com/kostua16/amnezia-control-panel/pull/1207

## Summary
PR 1207 adds per-PR error isolation to the Auto Cover scan CLI ('run-auto-cover-repairs.cjs'): stage-tagged '::warning' annotations, 'failed' vs new 'unrecorded' lists, per-PR summaries, exit 1 after the batch, plus tests and QD2b scenario docs. Base-checkout analysis shows two residual gaps the PR's own code comment names but does not close: (1) 'unrecorded' heads can be re-dispatched by the next scan because attempt counting still derives from PR comments and 'hasActiveFixReviewRun' only vetoes active runs; (2) a transient 'gh workflow run' 5xx (the exact failure the new test simulates) costs the PR its repair until the next 3-hourly scan — no retry, no reconciliation of red scans. Suggestions below cite base-checkout symbols.

## Quick Wins
- Count auto-cover-dispatched fix-review runs toward the attempt cap so 'unrecorded' heads cannot be re-dispatched -- The new 'unrecorded' list exists precisely because the attempt marker is a best-effort PR comment, and the code comment in run-auto-cover-repairs.cjs admits "the next scan could dispatch the same head again". Today evaluateAutoCoverReview computes attemptsCount as max(countFixReviewCommits(commits), countRecordedAttempts(attempts)) and hasActiveFixReviewRun only vetoes queued/in_progress runs — the residual under-count gap is a dispatched run that completes without pushing fix commits while its attempt comment also failed to post. Narrow fix: in evaluateAutoCoverReview, also count fixReviewRuns entries toward attemptsCount whose title matches the full 'PR #<n> @ <headSha>' token regardless of status AND are scoped to automation dispatches — not `hasActiveFixReviewRun`'s bare `title.includes('PR #<n>')` substring, which collides across PR #12 / #120 / #1207 when heads coincide — event 'workflow_dispatch' with the automation actor as trigger (github-actions[bot]) — because fix-review.yml's run-name gives maintainer-dispatched runs the identical 'Fix Review PR #<n> @ <sha>' title, and counting those would spend the auto-cover budget on human-initiated repairs. Actor-scoping the run term alone does not keep maintainer repairs out of the cap: countFixReviewCommits still counts any commit matching the FIX_REVIEW_COMMIT pattern, and maintainer-started /fix-review pushes carry the same commit-message (fix-review.yml's commit-and-push step) and the same GH_PAT author identity, so author-scoping the commit term is impossible. Scope the commit term by correlation instead: count a fix-review commit only when its first parent SHA equals the head-sha named in an automation-scoped run's title (dispatchFixReview passes the current head as head_sha and fix-review pushes on top of it; GitHub commit listings expose parents), so maintainer-initiated repairs stop consuming the automation budget; commits that fail correlation (run-list window loss, rebase between dispatch and push) fail closed toward the cap: count them toward attemptsCount and emit a stage-tagged '::warning' naming the uncorrelated commit, because silently dropping them undercounts the cap until the durable paged ledger lands — the runaway-dispatch failure the cap exists to prevent — while the residual over-count risk (an uncorrelated maintainer repair consumes one automation attempt) only skips a single dispatch and surfaces in the warning plus the next 3-hourly scan. Correlation is a stopgap: schedule the durable paged ledger pr1207.2 as the immediate follow-up that deletes this heuristic. Treat the derived count as best-effort within the repo-wide run-list window (fetch-auto-cover-context.cjs fetches the DEFAULT_RUN_LIMIT=50 most recent runs of the workflow, all events). Data is already fetched into pr-<n>-fix-review-runs.json; add tests in __tests__/evaluate-auto-cover-review.test.cjs for the under-count gap, the maintainer-dispatch exclusion, the maintainer-pushed-commit exclusion, and the fail-closed handling of uncorrelated commits. (owner: workflow-automation, type: quick-task)
- Add bounded retry with backoff to the 'gh workflow run' calls before a PR is marked failed -- The PR's own dispatch-failure test simulates 'HTTP 500 (100%)\r\nrequest failed' — a transient error class that now permanently costs that PR its repair until the next scan cycle. run-auto-cover-repairs.cjs calls 'gh workflow run' exactly once in `dispatchFixReview` and in `handOff` (symbol anchors, not line numbers — the functions sit at different lines in this base vs post-#1207 main). Wrap each in a 2-attempt retry with short exponential sleep, and reconcile before re-dispatching: a 5xx after the API already accepted the request still creates the run, so a blind retry would start a second repair on the same head. The reconcile lookup must target the workflow each call dispatches: `lookupFixReviewRun` is hard-wired to '--workflow fix-review.yml', so it can reconcile dispatchFixReview ('Fix Review PR #<n> @ <sha>') but sees nothing of handOff's DISPATCH_WORKFLOW (auto-cover-dispatch.yml) — parameterize the lookup by workflow file + title and reconcile handOff against 'Auto Cover Dispatch PR #<n> @ <sha>' runs, because a duplicate handOff is worse than a duplicate repair: the dispatch workflow's wait job uses concurrency group 'auto-cover-wait-<pr>' with cancel-in-progress, so the re-dispatch cancels the waiting run and restarts the quiet period. Also make the reconcile distinguish absent from unknown in both directions: lookupFixReviewRun swallows every error and returns '' after LOOKUP_ATTEMPTS x LOOKUP_DELAY_MS (~20s), so under persistent 5xx "no run found" is indistinguishable from "could not check" — treat an all-attempts-errored lookup as unknown, do not re-dispatch. And do not treat a clean-but-empty probe as absent either: the reconcile only ever runs after a failed dispatch attempt, and a 5xx that the API actually accepted can still list zero runs on an immediate probe, so after an ambiguous dispatch failure (HTTP 5xx, network timeout/reset) an empty-but-successful probe must resolve to unknown too — do not re-dispatch; only a probe following a definitive 4xx failure (validation, permissions — no run can exist) may treat empty as absent and re-dispatch. Either unknown path lets the PR land in 'failed' with its stage-tagged warning for the next 3-hourly scan to retry. Use a short reconcile probe (1-2 attempts) rather than reusing the full 10x2s URL-resolution loop, so the wait cost does not repeat per failed PR in the sequential loop. Note `handOff` currently takes no injected 'sleep' (dispatchFixReview already does); the retry wrapper must add one there, matching dispatchFixReview's pattern. Keep the per-PR isolation so an eventual failure still lands in 'failed' with its stage-tagged warning. Tests: make the injected gh throw once then succeed and assert dispatched === 1 and failed === []; a case where the throw is followed by the reconcile finding the already-created run (no second dispatch), for both the fix-review.yml and auto-cover-dispatch.yml reconcile targets; and a case where the reconcile itself errors through every probe — the PR lands in 'failed' with no second dispatch; and a case where the dispatch throws HTTP 500 but the reconcile returns a clean empty list — also 'failed' with no second dispatch, pinning that empty is not absent after an ambiguous failure. (owner: workflow-automation, type: quick-task)
- Cover the revalidate variant of the record-attempt failure in the e2e tests -- Blocked on PR #1207 merging: the referenced test ('a failed attempt comment after a started fix-review still counts as dispatched') and the 'unrecorded'/'onDispatched' symbols it exercises exist only on that branch, not in this base — pick this task up from a post-#1207 base. The test runs only '--mode direct', but the same 'unrecorded' path is live in revalidate mode: dispatchFixReview calls 'gh workflow run' first (so onDispatched fires), then posts the comment, and auto-cover-dispatch.yml:126 invokes the CLI in revalidate mode per PR. Extend the test to loop over ['direct', 'revalidate'] (matching the existing for-loop style used for the evaluate-failure test) so the recordFirst branch of the comment-write failure is pinned too; update QD2b in docs/workflow-e2e-scenarios.md only if behavior text needs the explicit mode mention. (owner: workflow-automation, type: quick-task)

## pr1207.x Phase Candidates
- pr1207.2: Durable attempt ledger: derive auto-cover attempt counts from the fix-review run list instead of PR comments -- This PR patches around the root cause — attempt state lives in workflow-owned PR comments that can fail to post ('unrecorded'), while the authoritative record of what was dispatched already exists as fix-review workflow runs titled 'Fix Review PR #<n> @ <sha>' and is fetched into pr-<n>-fix-review-runs.json every scan. Milestone-scale change: make evaluateAutoCoverReview treat run-list-derived dispatches as the source of truth for attemptsCount (comments stay as human-visible UI), teach fetch-auto-cover-context.cjs to page beyond the current run-list window when needed, and update __tests__ + documentation.md. This makes 'unrecorded' structurally impossible instead of alert-only, and removes the class of bugs where a lost comment silently under-counts attempts. (owner: workflow-automation)
- pr1207.1: Central red-scan response policy: what happens after the Auto Cover scan exits 1 -- After this PR, a scan with failed/unrecorded PRs ends red with per-stage warnings, but nothing consumes that signal — the job has no continue-on-error consumer, no alert, and no retry, so failed PRs wait for the next 3-hourly scan and unrecorded heads rely on the fragile comment ledger. Define the response centrally (policy.json, alongside maxAutoReviewFixAttempts): a backoff-and-retry-sweep for transient dispatch failures, a maintainer-only manual re-trigger path for repeated failures, and a consolidation step that files/updates one tracking issue after N consecutive red scans instead of per-run noise. Wire the policy flag through run-auto-cover-repairs.cjs main() and auto-cover-review.yml:219 so the governance rule is one central decision, not per-workflow improvisation. (owner: workflow-automation)
