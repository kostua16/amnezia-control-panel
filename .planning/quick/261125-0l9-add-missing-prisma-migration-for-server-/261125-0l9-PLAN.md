<objective>
Add the missing Prisma migration for `Server.redirectIp`. The field `redirectIp String?` is in `prisma/schema.prisma` (since commit 07d82cfd) but in no migration, so every database built by `prisma migrate deploy` (fresh installs, Docker, the stack image, CI) lacks the column. Prisma selects all scalar fields, so GET /api/servers fails with P2022 (`main.servers.redirectIp does not exist`) and POST /api/servers fails too.

Purpose: let deployed panels serve the servers API again with no manual DB surgery.
Output: one new migration directory, verified on a throwaway SQLite DB, committed alone.
</objective>

<planner_findings>
These facts were checked during planning. The executor does not need to re-derive them.

1. **There is already an unpushed version of this fix: reuse it byte-for-byte.** Commit `251908d0` ("fix(prisma): add the missing migration for servers.redirectIp", 2026-09-27) sits only on the LOCAL `main` branch, 6 commits ahead of `origin/main` (and on local `chore/migrate-to-github-hosted-runners`). No remote branch contains it. It adds `prisma/migrations/20260927000000_add_server_redirect_ip/migration.sql`, which is a 3-line file: an `-- AddColumn: Server.redirectIp ...` comment and `ALTER TABLE "servers" ADD COLUMN "redirectIp" TEXT;`. If this task used a different directory name (for example the suggested `20260725000000_...`) and those local commits were pushed later, history would hold two migrations that both add `redirectIp`. SQLite has no `ADD COLUMN IF NOT EXISTS`, so every fresh `migrate deploy` would then fail with "duplicate column name". Using the identical name and identical blob makes a future merge a no-op. `20260927000000` is later than the newest migration on this branch (`20260712000000_config_template_unique_name`), so it still meets the ordering constraint. The comment explains the invariant and contains no plan or phase references.
2. **The full drift check can never come back empty on this base, for an unrelated pre-existing reason.** Before the fix, a fresh deploy diffed against the schema reports exactly three items: `[*] Redefined table admins`, `[*] Redefined table user_quotas`, and `[*] Changed the servers table / [+] Added column redirectIp`. The admins and user_quotas items come from migration `20260617_schema_hygiene_indexes_enums_timestamps`, which adds `updatedAt` in place with `DEFAULT CURRENT_TIMESTAMP` while the schema's `@updatedAt` has no DB default. That is out of scope here. The fix for it (`ff8b1445`) is also only on local `main`. So the drift gate is: no `servers`/`redirectIp` entry remains, and the residual equals exactly those two pre-existing redefinitions. `--exit-code` will return 2 because of that residual, and that is expected.
3. `npx prisma` is broken under the rtk hook ("Binary 'prisma' not found on PATH"). Call `./node_modules/.bin/prisma` directly from the repo root.
4. `prisma.config.ts` loads `dotenv/config`, which does NOT override an already-exported `DATABASE_URL`. Exporting `DATABASE_URL=file:<abs scratch path>` in the same shell command reliably targets the scratch DB. Planning confirmed this: the probe deploys hit the scratch file, and `prisma/dev.db` was not touched.
5. The generated client (`src/generated/prisma`, gitignored) already includes `redirectIp`, so no `prisma generate` is needed. A Prisma-client smoke run reproduced P2022 on the pre-fix DB and passed after the ALTER, using `node --import tsx --input-type=module -e` from the repo root.
</planner_findings>
