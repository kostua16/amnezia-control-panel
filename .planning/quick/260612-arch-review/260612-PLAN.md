## Proposal 1: Migrate audit-log.ts from Raw SQL to Prisma Model

**Severity:** Medium (Dead Code / Consistency)
**Area:** `src/lib/audit-log.ts`, `prisma/schema.prisma`

### Problem

The `AuditLog` model is fully defined in `prisma/schema.prisma` (lines 369-383) with proper fields, indexes, and a migration (`20260611000000_add_audit_logs`). However, `src/lib/audit-log.ts` completely ignores this model and instead:

1. **Creates the table via raw SQL** at runtime (`CREATE TABLE IF NOT EXISTS audit_logs ...` at line 18-29) — this means the Prisma migration is dead code and the table definition may drift from the schema
2. **Inserts via `$executeRaw`** (lines 48-56) — no type safety, no Prisma-level validation
3. **Stores `metadata` as a raw JSON string** (line 56) — the Prisma model uses `String?` for this field too, but using Prisma's `Json?` type would give automatic serialization

This creates a dual-source-of-truth: the Prisma schema says one thing about the table, but the runtime code creates and writes to it independently.

### Proposal

Replace the raw SQL implementation with Prisma model calls:

```ts
// Before (current):
await ensureAuditLogTable(); // raw CREATE TABLE IF NOT EXISTS
await prisma.$executeRaw`INSERT INTO audit_logs ...`;

// After:
await prisma.auditLog.create({
  data: {
    action: input.action,
    resource: input.resource,
    resourceId: input.resourceId == null ? null : String(input.resourceId),
    actor: input.actor ?? 'admin',
    outcome: input.outcome ?? 'success',
    metadata: input.metadata ? JSON.stringify(input.metadata) : null,
  },
});
```

This eliminates:
- The `ensureAuditLogTable()` function and its raw SQL DDL
- The dual-source-of-truth between schema.prisma and runtime code
- Future risk of schema/runtime drift if either is updated independently

### Affected Files

- `src/lib/audit-log.ts` — replace raw SQL with `prisma.auditLog.create()`, remove `ensureAuditLogTable()`

### Acceptance Criteria

1. `ensureAuditLogTable()` and all raw SQL removed from `audit-log.ts`
2. `writeAuditLog()` uses `prisma.auditLog.create()` exclusively
3. All existing callers unaffected (same function signature)
4. Migration `20260611000000_add_audit_logs` verified as already applied

## Proposal 2: Extract Repeated bcrypt Hashing to a Shared Utility

**Severity:** Low-Medium (DRY / Repeated Dynamic Import)
**Area:** `src/app/api/servers/route.ts`, `src/app/api/panels/route.ts`, `src/app/api/users/route.ts`, `src/app/api/users/[id]/route.ts`, `src/app/api/auth/login/route.ts`

### Problem

The bcrypt hashing pattern is copy-pasted across at least 5 route files:

```ts
const bcrypt = await import('bcryptjs');
const hash = await bcrypt.hash(plaintext, 10);
```

This appears in:
- `src/app/api/servers/route.ts:77-78` — server API key hashing
- `src/app/api/servers/[id]/route.ts:130-131` — server API key update
- `src/app/api/panels/route.ts:60-61` — panel API key hashing
- `src/app/api/users/route.ts:130-131` — user password hashing
- `src/app/api/users/[id]/route.ts:147-148` — user password update

The dynamic import (`await import('bcryptjs')`) is unnecessary — `bcryptjs` is a pure JavaScript module with no native dependencies. It should be a top-level import in a utility function.

Additionally, the hash comparison pattern (for login/verification) is likely duplicated in `src/app/api/auth/login/route.ts`.

### Proposal

Create a thin utility in `src/lib/crypto.ts`:

```ts
import bcrypt from 'bcryptjs';

const SALT_ROUNDS = 10;

export async function hashSecret(plaintext: string): Promise<string> {
  return bcrypt.hash(plaintext, SALT_ROUNDS);
}

export async function verifySecret(plaintext: string, hash: string): Promise<boolean> {
  return bcrypt.compare(plaintext, hash);
}
```

Then replace all inline `await import('bcryptjs')` patterns with `import { hashSecret } from '@/lib/crypto'`.

### Affected Files

- `src/lib/crypto.ts` — new utility (2 functions, ~10 lines)
- 5 route files — replace inline bcrypt calls with `hashSecret()` / `verifySecret()`

### Acceptance Criteria

1. No `await import('bcryptjs')` remains in any route file
2. `bcryptjs` imported once in `crypto.ts`
3. All existing password hashing and verification behavior unchanged
4. Salt rounds remain at 10

## Proposal 3: Replace Synchronous execFileSync in Service Monitor

**Severity:** Medium (Event Loop Blocking)
**Area:** `src/lib/service-monitor.ts`

### Problem

`service-monitor.ts` uses `execFileSync` (synchronous) for all systemctl operations:

- `checkServiceStatus()` (line 25) — called per-service on each check cycle
- `checkAllServices()` (line 53) — iterates all services synchronously
- `restartService()` (line 63) — blocks during restart with 15s timeout

The module's docstring states it's "Intended to be used server-side (e.g., in an API route or cron-like scheduler)." When invoked from an API route handler (`src/app/api/services/[service]/status/route.ts`), each `execFileSync` call blocks the Node.js event loop for up to 5 seconds (status check) or 15 seconds (restart).

In contrast, `vpn-services.ts` correctly uses `execFileAsync` (asynchronous) for the same pattern of CLI command execution.

With `checkAllServices()` iterating 2 services sequentially, the worst case is 10 seconds of event loop blocking per status check cycle. During this time, all other HTTP requests are queued.

### Proposal

Migrate to async `execFile` (same pattern already used in `vpn-services.ts`):

```ts
import { execFile } from 'child_process';
import { promisify } from 'util';

const execFileAsync = promisify(execFile);

export async function checkServiceStatus(serviceKey: ServiceKey): Promise<ServiceHealth> {
  // Same logic, but using await execFileAsync instead of execFileSync
}

export async function restartService(serviceKey: ServiceKey): Promise<boolean> {
  // Same logic, but using await execFileAsync instead of execFileSync
}
```

The `ServiceMonitor` class's `check()` callback is already async (line 107), so the change is compatible.

### Affected Files

- `src/lib/service-monitor.ts` — replace `execFileSync` with `execFileAsync`
- Any callers of `checkServiceStatus()` / `restartService()` — must await (likely already async from API route context)

### Acceptance Criteria

1. No `execFileSync` calls remain in `service-monitor.ts`
2. `checkServiceStatus()` and `restartService()` return Promises
3. `ServiceMonitor.check()` still works with the same semantics (status change detection, auto-restart)
4. API route callers already in async context, so only need `await` addition
