# Phase 12.11: Tailscale transport in chain apply - Research

**Researched:** 2026-05-02
**Domain:** Tailscale transport resolution wired into chain apply, push, and config-applier paths
**Confidence:** HIGH

## Summary

Phase 12.11 closes TSCL-04 and the CHAIN-01 transport slice. The audit closure identified that `resolveTransportAddress` in `tailscale.ts` and the 3-tier fallback strategy in `/api/servers/[id]/tailnet` exist but are NOT consumed by any active push or apply code path. Instead, `chain-router.ts` generates WireGuard peer endpoints and Xray routing rules using raw `server.hostname:server.port` (where port defaults to 22, the SSH port), and `/api/panels/push/chain-config` manually parses `panelUrl` to extract hostname and a default port of 3000. Neither path uses Tailscale IP resolution.

The fix is two-fold: (1) Wire `resolveTransportAddress` (or its 3-tier fallback equivalent) into the chain config generation and chain apply paths so that WireGuard peer endpoints use Tailscale IPs and remote panel URLs use resolved Tailscale transport; (2) Ensure `panel-sync-client` and `config-applier` consume Tailscale-resolved panel URLs rather than relying on ad-hoc hostname parsing.

**Primary recommendation:** Introduce a `resolvePanelTransport` helper that combines `RemotePanel.panelUrl` with Server tailnet data to produce a canonical transport URL, then inject it into `chain-router.generateChainConfig` (for WireGuard peer endpoints) and ensure `applyChainConfig` uses resolved panel URLs instead of raw `hostname:port`.

### Pattern 1: Transport Resolution Layer

**What:** A `resolvePanelTransport` function that takes a Server and a RemotePanel and returns a canonical transport URL using Tailscale IPs, falling back through the 3-tier strategy from `/api/servers/[id]/tailnet`.

**When to use:** Anywhere a URL to a remote panel is needed -- push, apply, health check.

**Example:**
```typescript
// Source: derived from existing /api/servers/[id]/tailnet route pattern
interface ResolvedTransport {
  /** Canonical URL for reaching the remote panel (https://<tailscaleIP>:<port>) */
  panelUrl: string;
  /** The Tailscale IPv4 address used */
  tailscaleIP: string;
  /** Whether the node is online per tailscale status */
  online: boolean;
  /** Which resolution tier succeeded */
  source: 'db' | 'cli-resolve' | 'fallback' | 'panel-url-direct';
}

async function resolvePanelTransport(
  server: { tailnetIP?: string | null; tailnetHostname?: string | null; hostname: string },
  panel: { panelUrl: string },
  defaultPort = 443,
): Promise<ResolvedTransport>
```

### Anti-Patterns to Avoid

- **Direct hostname:port without Tailscale resolution:** `server.hostname:server.port` defaults to SSH port 22 and uses whatever hostname was entered at server registration time. This is NOT the inter-panel transport address.
- **Manual URL parsing of panelUrl:** `/api/panels/push/chain-config` manually strips protocol and parses port from `panelUrl`. This is fragile and duplicates logic that `resolveTransportAddress` already handles.
- **Separate transport logic per route:** Each route handler implementing its own transport resolution leads to inconsistency. Centralize in a single `resolvePanelTransport` function.

## Common Pitfalls

### Pitfall 1: Server.port is SSH port, not VPN or panel port
**What goes wrong:** `Server.port` defaults to 22 in the Prisma schema (`Int @default(22)`). Using `server.hostname:server.port` for WireGuard peer endpoints produces `hostname:22`, which is the SSH port, not the WireGuard or panel port.
**Why it happens:** The Server model was designed for SSH-based management, not for inter-panel VPN communication.
**How to avoid:** Use Tailscale IP + service-specific ports (WireGuard typically 51820, panel HTTP typically 443 or 3333) rather than `Server.port`.
**Warning signs:** Any endpoint like `some.host:22/api/sync/apply` is wrong.

### Pitfall 2: panelUrl may not use Tailscale IP
**What goes wrong:** `RemotePanel.panelUrl` is set by the admin at registration time. If they entered a public IP or hostname instead of the Tailscale IP, the push/apply will try to reach the panel over the public internet instead of the encrypted tailnet.
**Why it happens:** Admins may not know the Tailscale IP at registration time, or may use the public IP by habit.
**How to avoid:** Resolve transport address from Server tailnet data, and use `panelUrl` only as a fallback. The Server record has `tailnetIP` and `tailnetHostname` fields populated by the 3-tier strategy.
**Warning signs:** PanelUrl contains `https://1.2.3.4` (public IP) instead of `https://100.x.y.z` (Tailscale CGNAT range).

### Pitfall 3: chain-router generates config with wrong endpoints before apply
**What goes wrong:** `generateChainConfig` in `chain-router.ts` creates WireGuard peer endpoints using `server.hostname:server.port` at config generation time. If the config is then pushed via panel-sync-client, the peer endpoints embedded in the payload point to wrong addresses.
**Why it happens:** The chain-router generates endpoints during config creation, not during transport resolution. The two are not coupled.
**How to avoid:** Either resolve Tailscale IPs before generating the config (so endpoints are correct in the payload) or strip endpoint data from the payload and have the remote panel resolve locally. The former is simpler and matches the existing architecture.
**Warning signs:** WireGuard peer config in `PanelSyncPayload.wireguardPeers` contains non-Tailscale endpoints.

### Pitfall 4: /api/panels/push/chain-config duplicates transport logic
**What goes wrong:** `/api/panels/push/chain-config` manually parses `panelUrl` to extract hostname and port (default 3000), duplicating logic that should use the centralized transport resolver.
**Why it happens:** This route was written independently and doesn't use `resolveTransportAddress`.
**How to avoid:** Import and use the centralized `resolvePanelTransport` function instead of manual URL parsing.
**Warning signs:** `panelUrl.replace(/^https?:\/\//, '').split('/')` string manipulation.

### Pitfall 5: Tailscale CLI may not be available on dev machine
**What goes wrong:** Tests or dev environment call `tailscale ip -4` and get ENOENT because Tailscale CLI is not installed on the Windows dev machine.
**Why it happens:** Tailscale CLI is a runtime dependency on the deployment server, not on the dev machine.
**How to avoid:** Mock the tailscale CLI calls in tests (already done in chain-router.test.ts via mock fetch). For dev mode, the 3-tier fallback should use DB-cached tailnetIP before attempting CLI resolution.

## Open Questions

1. **What port should WireGuard peer endpoints use?**
   - What we know: `Server.port` defaults to 22 (SSH). WireGuard typically uses 51820. The Server model has no `wireguardPort` field.
   - What's unclear: Whether the deployment uses standard WireGuard port 51820 or a custom port. The `Service` model has a `port` field for each service type.
   - Recommendation: Look up the WireGuard service port from the `Service` model (where `type = 'AWG'`) rather than hardcoding 51820. Add a `wireguardPort` field to `ChainNode` if Service lookup is too complex.

2. **Should chain config endpoints be resolved at generation time or apply time?**
   - What we know: `generateChainConfig` creates endpoints inline. `applyChainConfig` then pushes the config to remote panels.
   - What's unclear: Whether it's better to resolve at generation time (endpoints correct in payload) or at apply time (remote panel resolves locally).
   - Recommendation: Resolve at generation time for simplicity. The config payload should contain correct Tailscale endpoints. This matches the existing architecture where `generatePerPanelConfig` embeds endpoint data.

3. **Should the chain-config route also resolve transport, or only chains/apply?**
   - What we know: `/api/panels/push/chain-config` generates chain configs from panel mappings and manually parses panelUrl.
   - What's unclear: Whether this route is actively used in the push flow or only chains/apply matters for TSCL-04.
   - Recommendation: Fix both. The chain-config route should also use resolved transport for consistency.
