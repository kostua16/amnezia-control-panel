## Proposal 1: User-VPN Lifecycle — Compensating Transaction for Failed Provisioning

### Problem

`src/app/api/users/route.ts:157-200` — User creation is a two-phase operation with no rollback:

1. Prisma creates the user record (with protocols and optional quota)
2. VPN service creation is attempted for each assigned protocol
3. If VPN creation fails, the DB record persists as an orphan — active user with no actual VPN access

The code acknowledges this: *"Failures are logged but do not roll back the DB record."*

**Concrete scenario:** Admin creates user `alice` with AWG + 3x-ui. AWG creation succeeds. 3x-ui returns an error. Result: Alice has a DB record with `AWG` protocol (active) and `THREE_XUI` protocol (active) but only AWG actually works on the VPN side. The admin sees `vpnAllSuccess: false` in the response, but the user record is already committed.

Worse: `user-sync.ts` later runs `syncAllUsers()` and sees Alice as "active" with both protocols — it tries to unblock Alice in both services, potentially masking the original provisioning failure.

### Solution

**Option A — Delete-on-failure (simpler):** If any VPN provisioning step fails after the DB record is created, delete the user record and return a clear error with which service failed. Admin retries.

**Option B — Mark-partial (more flexible):** Set `isActive: false` on the user and/or mark failed `UserProtocol` records as `isActive: false`. Return 207 Multi-Status with per-service results. Admin can re-trigger provisioning for specific protocols.

### Scope

- `src/app/api/users/route.ts`: Add rollback or partial-success handling after VPN failures
- `src/lib/user-sync.ts`: Account for partially-provisioned users (don't assume all protocols are live)
- Tests: User creation with one VPN failure → verify DB state

### Impact

Prevents orphaned user records that look healthy in the DB but have broken VPN access.
Critical path: user onboarding — a bad first experience for the admin.

## Proposal 2: Prisma Type Safety — Eliminate `as never` Escape Hatches

### Problem

Multiple routes use `as never` to bypass Prisma's generated type checking:

| Location | Line | Expression |
|----------|------|------------|
| `src/app/api/users/route.ts` | 158 | `prisma.user.create({ data: userData as never })` |
| `src/app/api/users/route.ts` | 187 | `data: { config: result.config as never }` |

The root cause is that `userData` is typed as `Record<string, unknown>` (line 133), not as Prisma's generated `UserCreateInput`. This forces the `as never` cast to satisfy TypeScript.

**Why this matters:** If the Prisma schema changes (e.g., a required field is added, a field is renamed), the `as never` cast silently suppresses the compile error. The route will fail at runtime with a cryptic Prisma error instead of a clear TypeScript error at build time.

The same pattern appears in `panels/route.ts` where `bcrypt` is dynamically imported (`await import('bcryptjs')`) — this works but means the import is not checked at compile time.

### Solution

1. Type `userData` properly using Prisma's `Prisma.UserCreateInput` instead of `Record<string, unknown>`
2. Remove the `as never` cast — fix the underlying type mismatch instead of suppressing it
3. Use static `import bcrypt from 'bcryptjs'` in both `users/route.ts` and `panels/route.ts` (consistent with `auth/login/route.ts`)

### Scope

- `src/app/api/users/route.ts`: Replace `Record<string, unknown>` with proper Prisma types, remove `as never`
- `src/app/api/panels/route.ts`: Same dynamic import fix (line 59)
- `src/app/api/servers/route.ts`: Same dynamic import fix (line 76)
- Verify: `next build` passes with strict types

### Impact

Schema changes surface as compile errors instead of runtime failures.
~5 minutes of work per file, but prevents a class of silent regressions.

## Proposal 3: Auth Middleware Request Enrichment — Pass Decoded Claims to Route Handlers

### Problem

`src/middleware.ts` validates the JWT on every protected route but discards the decoded payload. Routes that need user context must re-decode:

- `src/app/api/auth/me/route.ts:11` — `decodeJwt(token)` to extract `userId` and `username`
- Any future route that needs admin identity (audit logs, rate limiting, per-admin preferences) will repeat this pattern

The middleware already has the decoded payload from `jwtVerify()` (line 65) but doesn't attach it to the request. Next.js middleware can set request headers to pass data to route handlers.

**Consequence:** If the JWT payload structure changes (e.g., adding `role` or `permissions`), every route that re-decodes must be updated independently. No single source of truth for "what does the session contain?"

### Solution

In middleware, after successful JWT verification, set request headers with the decoded claims:

```ts
// In middleware.ts, after jwtVerify succeeds:
const requestHeaders = new Headers(request.headers);
requestHeaders.set('x-user-id', payload.userId as string);
requestHeaders.set('x-user-name', payload.username as string);
return NextResponse.next({ request: { headers: requestHeaders } });
```

Route handlers read claims from headers instead of re-decoding JWT:

```ts
// In route handlers:
const userId = request.headers.get('x-user-id');
```

### Scope

- `src/middleware.ts`: Set `x-user-id` and `x-user-name` headers after JWT verification
- `src/app/api/auth/me/route.ts`: Read from headers instead of `decodeJwt()`
- Future routes: Use header-based claims pattern

### Impact

Single source of truth for session claims.
Eliminates redundant JWT decoding on every authenticated request.
Foundation for future RBAC (add `x-user-role` header when roles are introduced).
