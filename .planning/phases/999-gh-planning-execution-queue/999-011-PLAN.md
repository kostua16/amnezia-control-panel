## Proposal 13: Authenticate the Socket.IO broadcast channel

**Severity:** Medium–High (Security — defense in depth)
**Area:** `server.mjs`, `src/middleware.ts`, `src/lib/websocket.ts`

### Problem

The realtime channel is wide open, even though every HTTP API route is JWT-gated and the sync endpoints are HMAC-gated:

- `server.mjs:18-25` constructs the `SocketIOServer` with `cors: { origin: '*' }` and **no `io.use()` handshake middleware**. `server.mjs:27-33` only logs connect/disconnect — it never authenticates the socket.
- `src/middleware.ts:8,15` explicitly lists `/api/ws` in `PUBLIC_API_ROUTES`, so the upgrade request bypasses JWT verification entirely. The adjacent comment even says *"Socket.io upgrade handled separately"* — but "separately" resolves to "not at all".
- `src/lib/websocket.ts:58-61` `broadcastEvent()` calls `ioInstance.emit(event, data)`, pushing to **every** connected socket with no room/namespace scoping.

`grep` for `io.use` / socket auth across `src/lib`, `src/app`, and `server.mjs` returns nothing — confirmed no auth is wired anywhere.

**Impact (real threat model):** The panel manages remote VPN servers and is intended to be reachable over the network. Any client that can reach `/api/ws` connects unauthenticated and receives the full firehose: `stats:update` (live traffic counters), `resource:update` (host CPU/disk/mem), `alert:new`, `panel:push-progress`, and `chain:status-update`. This leaks real-time operational telemetry and config-push progress to an unauthenticated observer. Severity is bounded by the fact that it is read-only telemetry (no write/control is exposed over WS — control still requires the JWT-gated REST API), so this is defense-in-depth rather than a direct takeover — but the data leak itself is concrete and unguarded.

### Solution

Add a connection handshake that reuses the existing `auth-token` cookie/JWT already enforced by middleware:

```ts
// server.mjs — gate the handshake
import { jwtVerify } from 'jose';
io.use((socket, next) => {
  const token = socket.request.cookies['auth-token']; // needs cookie parsing
  if (!token) return next(new Error('unauthorized'));
  jwtVerify(token, new TextEncoder().encode(process.env.JWT_SECRET!))
    .then(() => next())
    .catch(() => next(new Error('unauthorized')));
});
```

Also constrain CORS to the panel origin (or same-origin, since the client and server share a host) instead of `'*'`, and send the cookie from the client (`io({ withCredentials: true })`).

### Scope

- `server.mjs` — add `io.use()` handshake; tighten/replace `cors`.
- `src/lib/websocket.ts` — no behavioral change (broadcast helpers unchanged).
- Client connect path (`src/hooks` socket setup) — ensure credentials are sent.
- Out of scope: per-room scoping (YAGNI for single-admin).

### Acceptance Criteria

- [ ] A socket handshake without a valid `auth-token` is rejected (`connect_error`).
- [ ] Authenticated admin session continues to receive all events.
- [ ] CORS no longer `'*'` in production builds.
- [ ] Existing tests (which stub the socket) still pass; add one test asserting unauthorized connect is rejected.

## Proposal 14: Reject stale / down-versioned sync payloads

**Severity:** Medium (Correctness / Integrity)
**Area:** `src/app/api/sync/receive/route.ts`, `src/lib/hmac.ts`, `src/lib/panel-sync-client.ts`

### Problem

The sync receive endpoint authenticates with API-key + HMAC and has an **idempotency** guard — but only for *equal* versions, not for *older* ones, and there is no timestamp freshness:

- `src/app/api/sync/receive/route.ts:100-127` skips processing only when `existingConfig.configVersion === configData.configVersion`. If a captured payload carries an **older** `configVersion` (e.g. 5 while current is 7), it falls through.
- `src/app/api/sync/receive/route.ts:37` accepts `generatedAt` as `z.string().datetime()` but **never compares it to the current time** — the field is schema-validated then ignored. No freshness window, no nonce.
- `src/app/api/sync/receive/route.ts:129-132` runs `storePreviousConfig()` *before* the overwrite, so a replayed older payload not only downgrades the cached config to version 5 but also records version 7 as the "previous" state — i.e. a replay silently looks like an intentional rollback.
- `src/lib/hmac.ts:16-30` verifies the signature with `timingSafeEqual` (correct), but HMAC authenticates *content*, not *freshness* — a byte-for-byte replay of a real `(body, X-Signature)` pair still verifies.

**Impact:** A network observer who captures one legitimate push (body + its `X-Signature` header) can replay it later to silently downgrade a remote panel's cached routing/WireGuard config to an older version. `configVersion` is the field meant to order these pushes; the absence of a monotonic guard is the concrete gap. Mitigated by TLS in production and by the fact that capturing a request requires a privileged network position — hence Medium, not High — but the fix is small and the protocol already implies version-ordering.

### Solution

Add two cheap guards in step 6, before the overwrite:

1. **Monotonic version:** reject when `existingConfig && configData.configVersion <= existingConfig.configVersion` (return 409 / idempotent-style 200, do not overwrite).
2. **Freshness:** reject when `Date.now() - Date.parse(configData.generatedAt)` exceeds a skew window (e.g. ±5 min) — defend against arbitrary-delay replays of otherwise-valid payloads.

```ts
// after step 5 (HMAC), before step 7 (storePreviousConfig)
const ageMs = Math.abs(Date.now() - Date.parse(configData.generatedAt));
if (ageMs > SYNC_FRESHNESS_MS) {
  return NextResponse.json({ success: false, error: 'Stale payload' }, { status: 401 });
}
if (existingConfig && configData.configVersion <= existingConfig.configVersion) {
  return NextResponse.json({ success: true, data: { applied: true, message: 'Stale version ignored' } });
}
```

### Scope

- `src/app/api/sync/receive/route.ts` — add freshness + monotonic-version guards.
- Optionally mirror the freshness check in `src/app/api/sync/apply/route.ts` if it accepts `generatedAt`.
- No schema/migration change.

### Acceptance Criteria

- [ ] Replaying an older `configVersion` does NOT overwrite the cached config.
- [ ] A payload whose `generatedAt` is outside the skew window is rejected (401).
- [ ] Equal-`configVersion` idempotency (existing behavior) still returns success.
- [ ] New unit test: replay of a captured older payload is a no-op.

## Proposal 15: Centralize user CRUD behind mutation hooks with cache invalidation

**Severity:** Medium (Correctness / UX)
**Area:** `src/hooks/use-users.ts`, `src/components/users/*`

### Problem

`useUsers` is query-only and the user list cache is never invalidated on mutation, so the UI shows stale data after every create/edit/block/delete:

- `src/hooks/use-users.ts:55-61` exposes only `useUsers` (`useQuery`, `queryKey: ['users', params]`, `staleTime: 10_000`). There are **no** `useMutation` hooks for user CRUD.
- User mutations are scattered raw `fetch` calls that bypass React Query entirely:
  - `src/components/users/create-user-modal.tsx:40` — `POST /api/users`
  - `src/components/users/edit-user-modal.tsx:94` — `PUT /api/users/[id]`
  - `src/components/users/user-quota-modal.tsx:90` — `PUT` (quota/speed)
  - `src/components/users/user-list.tsx:148` — `DELETE /api/users/[id]`
  - `src/components/users/user-list.tsx:180` — `POST` (block/unblock)
- `invalidateQueries` is used in only two places repo-wide (`src/hooks/use-alerts.ts`, `src/components/providers.tsx`) — neither touches the `['users']` cache.

**Impact:** After an admin creates a user, edits a quota, blocks, or deletes, the user list reflects the **pre-action** state for up to the 10 s `staleTime` (longer if the tab is backgrounded and `refetchOnWindowFocus` semantics apply). Concretely: an admin blocks a user, the row still shows active, they re-click block — confusing and double-work. This is a correctness gap in the data layer, distinct from the query-key *registry* work (260603-h8s, 12.9), which centralizes key *strings* but does not add mutation/invalidation.

### Solution

Add mutation hooks in `use-users.ts` that invalidate the users cache, and route the modals through them:

```ts
export function useUpdateUser() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (vars: { id: number; body: unknown }) =>
      fetch(`/api/users/${vars.id}`, { method: 'PUT', headers: jsonHeaders, body: JSON.stringify(vars.body) }).then(assertOk),
    onSuccess: () => qc.invalidateQueries({ queryKey: ['users'] }),
  });
}
// similarly: useCreateUser, useDeleteUser, useToggleUserBlock
```

Replace the raw `fetch` in the five call sites with the matching hook. Use the centralized query-key for `'users'` so invalidation matches reads exactly.

### Scope

- `src/hooks/use-users.ts` — add 4 mutation hooks (create / update / delete / toggle-block).
- `src/components/users/{create-user,edit-user,user-quota-modal,user-list}.tsx` — adopt hooks.
- Reuses the query-key registry rather than hard-coding `'users'`.

### Acceptance Criteria

- [ ] No raw `fetch` to `/api/users*` remains in `src/components/users`.
- [ ] Every successful user mutation invalidates the `['users']` cache.
- [ ] List reflects create/block/delete immediately after the mutation resolves.
- [ ] Error handling preserved (toast/inline) — no silent swallowing introduced.
