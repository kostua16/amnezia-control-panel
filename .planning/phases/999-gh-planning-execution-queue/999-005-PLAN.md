## Proposal 1: User CRUD Partial-Failure Semantics

### Problem

`src/app/api/users/route.ts` POST handler (line 105-246) creates the user in the DB, then calls VPN service creation sequentially. If any VPN service call fails:

1. The user record persists with empty/broken protocol configs
2. HTTP response is still **201 Created** with `vpnAllSuccess: false` buried in the body
3. Any client checking only `response.ok` or HTTP status treats this as success
4. No retry path exists — the admin must delete and recreate the user

The same pattern exists in `src/app/api/users/[id]/route.ts` PUT handler (line 87-277): VPN service add/remove operations are best-effort with no rollback of the DB state if they fail.

This is a **correctness issue** that will become critical once VPN services are no longer stubs. Today the stubs always "succeed," masking the problem.

### Solution

**Option A: HTTP 207 Multi-Status for partial success.** Return 207 when some VPN operations fail, with per-service status in the body. Clients that check `response.ok` (which is true for 2xx) would need updating, but the semantics are more honest.

**Option B: Record-and-retry pattern.** Store VPN operation status in the DB (e.g., `UserProtocol.status = 'pending' | 'active' | 'failed'`). Expose a `/api/users/[id]/retry-vpn` endpoint. Admin dashboard shows "VPN setup incomplete" badge.

**Option C: Fail-fast on VPN creation.** If any VPN service creation fails, roll back the DB user record (delete within the same route handler). Return 500 with clear error. Simpler but may frustrate admins when one VPN service is temporarily down.

### Scope

- `src/app/api/users/route.ts`: POST handler error semantics
- `src/app/api/users/[id]/route.ts`: PUT handler service add/remove
- `src/types/user.ts`: Add `vpnStatus` field to user response type (Option B)
- Frontend components: Show partial-failure state in user list/edit forms

### Impact

Prevents phantom users with broken VPN configs. Gives admins actionable feedback when VPN services are unavailable. Most impactful once VPN services move past stubs.

### Risk

Medium — changes API response contract; frontend may need updates. Option B is the safest (additive only).

### Estimated Effort

1-2 focused sessions (Option B); 1 session (Option C)

## Proposal 2: Production-Ready Health Endpoint

### Problem

`src/app/api/health/route.ts` is a 9-line stub:

```ts
export async function GET() {
  return NextResponse.json({ status: 'ok', timestamp: new Date().toISOString() });
}
```

It checks nothing. For a production panel that manages VPN services for up to 50 users, the health endpoint should verify:

1. **Database connectivity** — Can Prisma reach SQLite? (`prisma.$queryRaw\`SELECT 1\``)
2. **GeoIP data loaded** — Is the GeoIP database loaded and not stale?
3. **WebSocket server initialized** — Is Socket.IO ready?
4. **Disk space** — Is there room for SQLite WAL and GeoIP data? (optional, low priority)

A monitoring system (or Docker health check, or load balancer) pointing at `/api/health` currently gets false positives — the panel could have a corrupted DB, no GeoIP data, and a dead WebSocket server, and still return 200.

### Solution

Extend the health endpoint to check critical subsystems and return a structured response:

```ts
{
  status: 'ok' | 'degraded' | 'unhealthy',
  checks: {
    database: { ok: boolean, latencyMs?: number },
    geoip: { ok: boolean, loaded: boolean, stale: boolean },
    websocket: { ok: boolean, initialized: boolean },
  },
  timestamp: string
}
```

- Return 200 for `ok` and `degraded` (panel works but with limitations).
- Return 503 for `unhealthy` (database unreachable — panel cannot function).

### Scope

- `src/app/api/health/route.ts`: Rewrite with subsystem checks
- `src/lib/prisma.ts`: Export a `checkDatabaseConnection()` helper
- `src/lib/geoip-manager.ts`: Already exports `getGeoIPStatus()` — reuse
- `src/lib/websocket.ts`: Export `isWebSocketReady(): boolean`

### Impact

Enables real production monitoring. Docker `HEALTHCHECK`, load balancer probes, and alerting systems get actionable health data instead of false positives.

### Risk

Low — the health endpoint is public (no JWT required per middleware config). The checks must be fast and non-blocking. Database ping adds ~1-5ms. All other checks are in-memory reads.

### Estimated Effort

1 focused session

## Proposal 3: GeoIP Download Integrity Verification

### Problem

`src/lib/geoip-manager.ts:refresh()` (line 381-464) downloads `geoip.dat` from jsDelivr CDN or GitHub, writes it to disk, then parses it. The only size check is `stat.size < 1000` (line 422) — it rejects files under 1KB but accepts any corrupted or truncated file above that threshold.

Failure modes not caught:
1. **Truncated download** — Network timeout after partial write. A 4MB file with only the first 2MB parsed may load "successfully" but with missing countries.
2. **CDN corruption** — Rare but possible. A corrupted file passes the size check and overwrites the working database.
3. **HTML error page** — A CDN/GitHub error that returns a 200 with HTML body >1KB would be saved as `geoip.dat`.

The current code does attempt to parse after download (`this.loadFromFile()` at line 452), and a parse failure sets `status.error`. But the old database file has already been replaced at that point (`rename(tempPath, GEOIP_FILE)` at line 430). If parsing fails, the panel has no GeoIP data until the next refresh succeeds.

### Solution

**Atomic swap with validation:**

1. Download to temp file (already done).
2. **Parse the temp file** into a new `Map` before renaming.
3. Only if parsing succeeds and produces a reasonable number of countries (>100), rename temp to `geoip.dat`.
4. If parsing fails, delete the temp file and keep the existing database.

Additionally, verify the `Content-Type` header is not `text/html` before accepting the download.

### Scope

- `src/lib/geoip-manager.ts`: `refresh()` method
  - Move `parseDatFile()` call before `rename()`
  - Parse from temp path, validate country count
  - Only swap file on success
  - Add Content-Type guard to download loop
- `src/lib/__tests__/geoip-manager.test.ts`: Test corrupted download → old data preserved

### Impact

Eliminates the risk of a bad download wiping the working GeoIP database. The panel always has either the old data or verified new data — never an empty/broken state.

### Risk

Low — purely defensive. The change is internal to `GeoIPManager.refresh()`. Public API unchanged.

### Estimated Effort

1 focused session
