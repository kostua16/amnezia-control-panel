## Proposal 1: Transaction Boundaries for User Lifecycle Operations

**Severity:** High (Data Consistency)
**Area:** `src/app/api/users/route.ts`, `src/app/api/users/[id]/route.ts`

### Problem

User create (POST), update (PUT), and delete (DELETE) each perform 3–6 sequential Prisma writes with no `$transaction` wrapper. A partial failure leaves the database in an inconsistent state.

**Concrete examples:**

**POST `/api/users`** (`src/app/api/users/route.ts:158-201`):
1. `prisma.user.create()` — creates user + protocols + quota in one nested write (lines 158-163)
2. For each protocol: `prisma.userProtocol.update()` to persist VPN config (lines 186-189)
3. `writeAuditLog()` (line 206)

If step 2 fails for the second protocol after succeeding for the first, the user exists with partially-initialized VPN configs. The comment on line 166 acknowledges this: *"Failures are logged but do not roll back the DB record."*

**PUT `/api/users/[id]`** (`src/app/api/users/[id]/route.ts:152-253`):
1. `prisma.user.update()` (line 152)
2. For each removed service: `prisma.userProtocol.updateMany()` (line 196)
3. For each added service: `prisma.userProtocol.findFirst()` + `update()` or `create()` (lines 221-243)
4. `prisma.user.findUnique()` to fetch final state (line 248)
5. `writeAuditLog()` (line 255)

If VPN service deletion succeeds (external CLI call) but the `userProtocol.updateMany()` fails, the protocol record remains `isActive: true` while the VPN backend has already deleted the client.

**DELETE `/api/users/[id]`** (`src/app/api/users/[id]/route.ts:297-383`):
1. VPN deletions (external calls, lines 331-353)
2. `prisma.user.delete()` with cascade (line 356)
3. `writeAuditLog()` (line 360)

If step 1 partially fails and step 2 succeeds, the user is gone from DB but VPN clients still exist on the backend. The cascade deletes the protocol records, so there's no way to retry the VPN cleanup.

### Proposal

1. Wrap the DB-side operations (steps that modify Prisma models) in `prisma.$transaction()`:
   - **POST**: The `user.create` is already atomic (nested writes), but the subsequent `userProtocol.update` calls for VPN config should be in a transaction.
   - **PUT**: Wrap the `user.update` + all `userProtocol` writes in a single interactive transaction.
   - **DELETE**: Wrap VPN config cleanup + `user.delete` + audit log in a transaction. VPN backend calls stay outside (best-effort, logged).

2. Introduce a `withTransaction` helper for the common pattern:
   ```ts
   // src/lib/db-helpers.ts
   export async function withTransaction<T>(fn: (tx: PrismaTransaction) => Promise<T>): Promise<T> {
     return prisma.$transaction(fn);
   }
   ```

3. For VPN backend failures, record the failure state in a `vpnSyncStatus` field on `UserProtocol` (e.g., `"pending"`, `"synced"`, `"failed"`) so it can be retried.

### Affected Files

- `src/app/api/users/route.ts` — wrap POST in transaction
- `src/app/api/users/[id]/route.ts` — wrap PUT and DELETE in transactions
- `src/lib/db-helpers.ts` — new transaction helper (optional)

### Acceptance Criteria

1. POST: If any `userProtocol.update` fails, the entire user creation rolls back (no orphan user record)
2. PUT: If any service change fails, the user record reverts to pre-update state
3. DELETE: If VPN backend deletion fails, the user record still exists with `vpnSyncStatus: "pending_cleanup"` (retryable)
4. All existing tests pass

### Scope Note

This is scoped to user lifecycle only (the most critical multi-step path). Server, panel, and config routes can be evaluated separately if this pattern proves valuable.

## Proposal 2: Decompose vpn-services.ts into Focused Modules

**Severity:** Medium (Maintainability / 200-line guideline)
**Area:** `src/lib/vpn-services.ts` (791 lines)

### Problem

`vpn-services.ts` is a 791-line file that violates the project's own 200-line file size guideline (`development-rules.md`). It mixes four distinct concerns:

1. **CLI execution infrastructure** — `execFileAsync`, timeout handling, environment variable resolution (~50 lines)
2. **Input validation** — `sanitizeUsername()`, `validateWireGuardKey()`, `validateAddress()`, regex patterns (~80 lines)
3. **AWG operations** — `createAwgUser`, `deleteAwgUser`, `blockAwgUser`, `unblockAwgUser`, config parsing (~250 lines)
4. **3x-ui operations** — `createThreeXuiUser`, `deleteThreeXuiUser`, `blockThreeXuiUser`, `unblockThreeXuiUser`, API helpers (~300 lines)
5. **Shared utilities** — `ok()`, `fail()`, `getErrorMessage()`, result types (~30 lines)

The AWG and 3x-ui sections have no shared logic — they use completely different APIs (CLI vs HTTP). Combining them means any change to AWG operations risks breaking 3x-ui and vice versa.

**Why the prior review dismissed it:** The 260610 review noted "VPN service stubs — All commands return STUB_* values. This is by design." But the structural issue exists regardless of whether functions are stubs or real. At 791 lines, it's already the largest file in `src/lib/` and will only grow as real CLI/API integration progresses.

### Proposal

Split into four focused modules under `src/lib/vpn/`:

```
src/lib/vpn/
├── cli-executor.ts      # execFileAsync wrapper, timeout, env resolution (~60 lines)
├── validation.ts         # sanitizeUsername, validateWireGuardKey, etc. (~90 lines)
├── awg-service.ts        # createAwgUser, deleteAwgUser, block/unblock (~260 lines)
├── xui-service.ts        # createThreeXuiUser, deleteThreeXuiUser, xuiApi helper (~310 lines)
├── types.ts              # VpnServiceResult, AwgUserConfig, XuiUserConfig (~40 lines)
└── index.ts              # Re-exports all public functions (backward compat)
```

The `index.ts` re-exports maintain backward compatibility — existing imports like `import { createAwgUser } from '@/lib/vpn-services'` would redirect through `@/lib/vpn` via the barrel export.

### Affected Files

- `src/lib/vpn-services.ts` → becomes a thin re-export barrel (or is deleted after import migration)
- `src/lib/vpn/*.ts` — new files (6 files)
- All files importing from `@/lib/vpn-services` — update import paths (or keep using barrel)

### Acceptance Criteria

1. No file exceeds 200 lines
2. All existing imports resolve (via barrel or direct)
3. All existing tests pass without modification
4. AWG and xui modules have zero imports from each other (clean separation)

## Proposal 3: Composite Index for Traffic Log Aggregation

**Severity:** Medium (Performance, scales with data growth)
**Area:** `prisma/schema.prisma`, `src/app/api/stats/traffic/route.ts`

### Problem

The `TrafficLog` model has three individual indexes:

```prisma
@@index([userId])
@@index([serverId])
@@index([timestamp])
```

But the most common query patterns are compound:

1. **`GET /api/stats/traffic?userId=X&startDate=...&endDate=...`** — filters by `userId + timestamp` range, then groups by time bucket. The raw query at `src/app/api/stats/traffic/route.ts:70-72` generates `WHERE userId = ? AND timestamp >= ? AND timestamp <= ? GROUP BY bucket`.

2. **Broadcaster aggregate** — `prisma.trafficLog.aggregate({ _sum: { bytesIn, bytesOut } })` with no filter (covered by prior proposal 3).

3. **Per-user traffic** — `GET /api/stats/traffic/users` likely joins or filters by userId + time range.

SQLite can only use one index per query. For pattern 1, it must choose between `userId` or `timestamp` index, then filter the other column with a table scan. A composite index on `(userId, timestamp)` would serve both filter dimensions in a single index scan.

**Impact estimate:** With 50 users and hourly traffic snapshots over 6 months (~216K rows), a `WHERE userId = 5 AND timestamp >= '2026-01-01'` query must scan ~4.3K rows (all rows for that user) even though only ~4.3K match the timestamp filter. A composite index would narrow directly to the matching range.

### Proposal

Add a composite index to `TrafficLog`:

```prisma
@@index([userId, timestamp])
```

This is additive — existing single-column indexes remain for queries that filter by only one dimension. SQLite's query planner will automatically choose the composite index when both columns appear in the WHERE clause.

Optionally, also add `@@index([serverId, timestamp])` if per-server traffic queries become common.

### Affected Files

- `prisma/schema.prisma` — add `@@index([userId, timestamp])` to TrafficLog model
- Migration auto-generated by `prisma migrate dev`

### Acceptance Criteria

1. New composite index exists on `traffic_logs(userId, timestamp)`
2. `EXPLAIN QUERY PLAN` on the traffic stats raw query shows the composite index being used when `userId` filter is present
3. No regression in queries that only filter by `timestamp` (single-column index still used)
