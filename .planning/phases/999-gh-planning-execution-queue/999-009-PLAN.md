## Proposal 1: GeoIP Lookup Performance — Binary Search Over CIDR Table

**Severity:** High (Performance)
**Area:** `src/lib/geoip-manager.ts`

### Problem

`GeoIPManager.lookupCountry()` performs a linear scan over every country and every CIDR entry. The v2fly geoip.dat file contains ~200K+ CIDR ranges. Each geo-routed packet destination triggers this full scan — it is the hottest path in the routing pipeline.

Current complexity: **O(total_CIDRs)** per lookup.

### Proposal

On `loadFromFile()`, build a sorted array of `{ networkNum, mask, countryCode }` tuples sorted by `networkNum`. Use binary search to narrow candidates, then verify with the mask.

- Build phase: O(n log n) once on load
- Lookup phase: O(log n) per query

### Affected Files

- `src/lib/geoip-manager.ts` — add sorted table + binary search in `loadFromFile()` and `lookupCountry()`

### Acceptance Criteria

1. `lookupCountry()` uses binary search, not linear scan
2. Existing tests pass unchanged (behavior is identical)
3. Load time does not regress by more than 100ms

## Proposal 2: API Route Handler Abstraction

**Severity:** Medium (DRY / Maintainability)
**Area:** `src/app/api/**/*.ts`, `src/lib/api-response.ts`

### Problem

Every API route duplicates the same boilerplate:

```ts
export async function POST(request: NextRequest) {
  try {
    const body = await request.json();
    const parsed = schema.safeParse(body);
    if (!parsed.success) {
      const firstError = parsed.error.issues[0]?.message ?? 'Invalid request body';
      return NextResponse.json({ success: false, error: firstError }, { status: 422 });
    }
    // ... business logic ...
  } catch (err) {
    console.error('[api/...] Error:', err);
    if (err && typeof err === 'object' && 'code' in err && (err as { code: string }).code === 'P2002') {
      return NextResponse.json({ success: false, error: 'Duplicate' }, { status: 409 });
    }
    return NextResponse.json({ success: false, error: 'Failed' }, { status: 500 });
  }
}
```

The `api-response.ts` helpers (`success()`, `error()`, `validationError()`) exist but are inconsistently used. Routes at `src/app/api/users/route.ts`, `src/app/api/servers/route.ts`, and ~30 others all hand-roll this pattern.

### Proposal

Create a thin `withHandler(schema, handler)` wrapper in `src/lib/api-handler.ts`:

```ts
export function withHandler<B, C>(
  schema: ZodSchema<B>,
  handler: (body: B, ctx: C) => Promise<NextResponse>,
): (request: NextRequest) => Promise<NextResponse>
```

- Parses + validates request body via schema
- Catches P2002 → 409, generic → 500
- Uses existing `api-response.ts` helpers internally

Migrate routes progressively (not a big-bang refactor). New routes use the wrapper; existing routes migrate when touched.

### Affected Files

- `src/lib/api-handler.ts` — new file
- Existing routes — progressively migrate

### Acceptance Criteria

1. New `api-handler.ts` provides `withHandler` and `withQueryHandler` utilities
2. At least 3 existing routes migrated as proof-of-concept
3. All existing tests pass

## Proposal 3: Real-time Broadcaster Query Optimization

**Severity:** Medium (Performance, scales with data)
**Area:** `src/lib/real-time-broadcaster.ts`, `prisma/schema.prisma`

### Problem

`startBroadcaster()` runs `prisma.trafficLog.aggregate({ _sum: { bytesIn, bytesOut } })` every 30 seconds with no time-range filter. This sums the entire `traffic_logs` table. With 50 users generating traffic logs over months, this table will grow to 100K+ rows, and the aggregate query will degrade.

Additionally, `prisma.user.count()` is called three times (total, active, blocked) when a single query with `groupBy` or `_count` with `where` could be more efficient.

### Proposal

1. Add a time-range filter to the traffic aggregate (e.g., last 24 hours or "current billing period")
2. Replace 3 separate `user.count()` calls with a single `prisma.user.aggregate({ _count: true })` + `where` group
3. Consider caching the result and invalidating on write (WebSocket-driven update instead of polling)

### Affected Files

- `src/lib/real-time-broadcaster.ts` — add time-range filter to aggregate
- `src/types/monitoring.ts` — update dashboard stats shape if needed

### Acceptance Criteria

1. Traffic aggregate includes a time-range filter (configurable, default 24h)
2. User counts use fewer queries (1-2 instead of 3)
3. Dashboard stats UI still renders correctly
