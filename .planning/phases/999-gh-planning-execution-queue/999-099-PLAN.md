# Quick Plan: PR #722 workflow improvement intake

## Source
- PR #722: fix: resolve #704 - MON-I02: Align 80-turn budget with the 25-min timeout (monitor-github-runs)
- URL: https://github.com/kostua16/amnezia-control-panel/pull/722

## Summary
PR #722 adds STOP_BY deadline awareness to monitor-amnezia-control-panel-github-runs.yml (capture job start epoch, compute 20-min deadline with 5-min safety margin, inject into agent prompt) and tightens MAX_TURNS 80→50. Two follow-up opportunities: the deadline pattern is monitor-only and should be reusable, and no governance check validates MAX_TURNS vs timeout-minutes alignment across the ~20 agent-driven workflows.

## Quick Wins
- Extract STOP_BY deadline into reusable composite action -- The 'Capture job start time' + 'Compute STOP_BY deadline' steps (lines 66–94 of the PR diff) duplicate ~30 lines of bash with input validation. Extract into '.github/actions/compute-stop-by-deadline/action.yml' with inputs 'timeout-minutes' and 'safety-margin-minutes', outputting 'stop_by'. The monitor workflow would call this action instead of inlining the logic. Other long-running workflows (claude.yml, audit-fix.yml, gsd-planning-execute.yml) could then adopt it without duplicating the validation. (owner: gh-workflow-engineer, type: workflow-improvement)
- Add STOP_BY to the claude.yml and fix-issue.yml agent prompts -- claude.yml has MAX_TURNS:100 with timeout-minutes:10; fix-issue.yml has MAX_TURNS:60 with timeout-minutes:10. Neither passes a time-based deadline to the agent — the agent only knows its turn limit. If turns are slow (API latency, large tool outputs), the agent can burn its entire timeout without knowing time is short. Passing STOP_BY (computed from the same pattern as PR #722) gives the agent prompt-level time awareness so it wraps up early rather than being killed by the job timeout. (owner: gh-workflow-engineer, type: quick-task)
- Add actionlint to the monitor workflow's new bash steps -- The PR adds two new bash steps ('Capture job start time' and 'Compute STOP_BY deadline') but the verify-changed-files step at line 280 only runs actionlint if 'workflow_or_action_yaml_changed' is true. The new inline bash includes a 'case' statement with glob patterns and arithmetic — shellcheck coverage exists for standalone .sh files but these inline steps are not shellchecked. Adding 'shellcheck' annotation ('# shellcheck shell=bash') or extracting to a small script would close the gap. (owner: gh-workflow-engineer, type: quick-task)

## pr722.x Phase Candidates
- pr722.2: Extend workflow-governance-check.cjs to validate MAX_TURNS vs timeout-minutes alignment -- '.github/workflows/scripts/workflow-governance-check.cjs:106' already enforces 'timeout-minutes' presence on every job. Extend it to: (1) detect agent-driven jobs (those using 'run-zai' action or setting 'MAX_TURNS'), (2) warn if MAX_TURNS * 30s estimated turn time > timeout-minutes * 60s, (3) warn if no STOP_BY-like deadline mechanism exists for jobs with timeout > 15 minutes. This prevents future MON-I02-style misalignment without manual review. (owner: gh-workflow-engineer)
- pr722.1: Centralize turn-budget policy with per-workflow MAX_TURNS in a shared action -- 20+ workflows independently set 'env.MAX_TURNS' with no shared formula. Create '.github/actions/derive-turn-budget/action.yml' that takes 'timeout-minutes' and 'complexity' (simple/medium/complex) inputs and outputs the recommended 'max-turns'. Workflows would call 'uses: ./.github/actions/derive-turn-budget' instead of hardcoding values. This makes turn-budget tuning a single-file change and prevents future drift between turns and timeouts. (owner: gh-workflow-engineer)
- pr722.4: Add STOP_BY awareness to the kos-zai-run-failure-prevention skill -- The 'kos-zai-run-failure-prevention' skill ('.claude/skills/kos-zai-run-failure-prevention/SKILL.md') catalogs canonical run failure modes. Add 'timeout kill due to missing STOP_BY awareness' as a failure mode, with the prevention pattern: 'workflows with timeout > 15min MUST compute and inject STOP_BY via the compute-stop-by-deadline action'. This ensures future workflow authors get the pattern automatically during planning. (owner: gh-workflow-engineer)
