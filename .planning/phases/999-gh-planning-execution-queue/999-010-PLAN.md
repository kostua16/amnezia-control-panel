## Proposal 10: Deduplicate chain config generation — eliminate behavioral drift

**Severity:** High (Correctness)
**Area:** `src/lib/chain-router.ts`, `src/app/api/panels/push/chain-config/route.ts`

### Problem

`generateWireGuardPeers()` and `generateXrayRoutingRules()` are each implemented **twice**:

| File | Lines | Role |
|------|-------|------|
| `chain-router.ts:247-318, 322-395` | ~145 | Used by `applyChainConfig()` — the live chain apply path |
| `chain-config/route.ts:24-93, 97-204` | ~180 | Used by `POST /api/panels/push/chain-config` — the push wizard preview path |

These copies have **drifted apart**:

- **Mesh topology Xray rules**: `chain-router.ts` uses `outboundTag: 'direct'` for all mesh nodes. `chain-config/route.ts` uses `outboundTag: 'mesh_balancer'`. Same topology → different routing behavior depending on which code path executes.
- **Split topology Xray rules**: `chain-config/route.ts` adds geoip-based rules (`geoip: ru → direct`, `geoip: private → direct`) and routes remaining traffic to the foreign chain. `chain-router.ts` routes both domestic and foreign to `direct`. The push wizard preview and the actual apply would produce incompatible configs.
- **Linear Xray priorities**: `chain-config/route.ts` uses `priority: i * 10` (varies per node pair). `chain-router.ts` uses `priority: 0` for all. Different priority ordering means different rule evaluation order.

**Impact:** Admin previews a chain config in the push wizard, sees one set of routing rules, then applies it and gets different routing. In the worst case, traffic that was shown as "direct" in preview gets routed through a VPN chain (or vice versa).

### Solution

Extract both functions into a single shared module `src/lib/chain-config-generator.ts`. Resolve the behavioral differences:

1. Mesh: decide on `mesh_balancer` vs `direct` (likely `mesh_balancer` is correct for load balancing; `direct` is a placeholder).
2. Split: adopt the richer `chain-config/route.ts` rules (geoip-aware) as canonical.
3. Linear: adopt the per-node-pair priority from `chain-config/route.ts` for correct ordering.

Both `chain-router.ts` and `chain-config/route.ts` import from the shared module.

### Scope

- Create `src/lib/chain-config-generator.ts` (~150 lines, under the 200-line limit)
- Delete duplicated functions from both files
- Add unit tests comparing output of both paths to confirm identical results
- Resolve behavioral drift (pick canonical behavior per topology)

### Acceptance Criteria

- [ ] Zero duplicate `generateWireGuardPeers` / `generateXrayRoutingRules` implementations
- [ ] `chain-router.ts` and `chain-config/route.ts` import from shared module
- [ ] All three topologies produce identical output from both call sites
- [ ] Existing tests pass; new test confirms output parity

## Proposal 11: Config-applier shared push helper — DRY the remote push pattern

**Severity:** Medium (DRY)
**Area:** `src/lib/config-applier.ts`

### Problem

`applyAwgConfig()` (lines 25-138) and `applyThreeXuiConfig()` (lines 148-240) share ~80% identical code:

1. Construct body payload (different shape per service)
2. `signPayload(bodyPayload, apiKey)` for HMAC
3. `fetch(panelUrl + '/api/sync/apply', { method: 'POST', headers, body, signal: AbortSignal.timeout(15000) })`
4. Parse response: check `response.ok`, `data.applied`, `data.message`
5. Handle 404 with identical error shape ("Remote panel does not have /api/sync/apply")
6. Handle other HTTP errors with `enrichError()`
7. Handle fetch exceptions with `enrichError()`

Only step 1 (body construction) differs. Steps 2-7 are identical — ~90 lines of duplicated fetch + error logic.

**Impact:** Any fix to the push mechanism (e.g., changing timeout, adding retry, modifying error enrichment) must be applied in two places. The 404 handling was already copy-pasted with only the service name different.

### Solution

Extract a shared `pushToRemotePanel()` helper:

```ts
async function pushToRemotePanel(params: {
  panelUrl: string;
  panelName: string;
  apiKey: string;
  bodyPayload: Record<string, unknown>;
  service: 'awg' | 'three_xui';
}): Promise<ConfigApplierResult>
```

Both `applyAwgConfig` and `applyThreeXuiConfig` become thin wrappers that construct the body payload and delegate to `pushToRemotePanel`.

### Scope

- Refactor `config-applier.ts` — extract shared helper (~40 lines)
- Thin wrappers for AWG and 3x-ui (~15 lines each)
- No behavioral change; same error shapes, same timeouts, same retry semantics
- Add test confirming both services produce same error structure on failure

### Acceptance Criteria

- [ ] Zero duplicated fetch + HMAC + error handling logic in `config-applier.ts`
- [ ] `applyAwgConfig` and `applyThreeXuiConfig` are thin wrappers
- [ ] Error response shapes unchanged (no breaking change to consumers)
- [ ] File stays under 200 lines

## Proposal 12: Resource-monitor async conversion — extend proposal 9 scope

**Severity:** Medium (Performance)
**Area:** `src/lib/resource-monitor.ts`

### Problem

Proposal 9 addresses `service-monitor.ts` using `execFileSync` (blocking). `resource-monitor.ts` has the same class of issue:

- **`execFileSync('df', ...)`** (line 78) — synchronous disk usage query blocks the event loop for up to 5 seconds on timeout. Called once every 10 seconds via the broadcaster.
- **`execFileSync('powershell', ...)`** (line 59) — Windows path with same blocking behavior.
- **`getCpuUsage()`** — samples CPU twice with a 100ms `setTimeout` gap. While async, this means every `getSystemResources()` call takes at minimum 100ms to resolve. Combined with the sync `execFileSync` calls, the function blocks the event loop.

At 10-second intervals with a 10-second cache TTL, this means ~50% of the time there's either a sync block or a pending CPU sample.

### Solution

Mirror the approach from proposal 9:
- Replace `execFileSync` with `execFileAsync` for disk usage queries
- Keep CPU sampling async but consider caching the CPU sample independently (compute once per tick, reuse for the cache duration)
- Align with the async pattern already used in `vpn-services.ts`

### Scope

- Convert `getDiskUsage()` to async (`getDiskUsageAsync()`)
- Convert `getSystemResources()` callers to await the async version
- Maintain the 10-second cache TTL
- File stays under 200 lines

### Acceptance Criteria

- [ ] Zero `execFileSync` calls in `resource-monitor.ts`
- [ ] `getSystemResources()` no longer blocks the event loop
- [ ] Same output shape and cache behavior
- [ ] File stays under 200 lines
