## Proposal 2: Silent Dependency Fallback and Broken Test Hooks in chain-router

### Problem

`chain-router.ts:67-73` dynamically imports Prisma with a silent catch:

```ts
let prisma: Awaited<(typeof import('./prisma'))['prisma']> | null = null;
try {
  const mod = await import('./prisma');
  prisma = mod.prisma;
} catch {
  // Prisma not available (e.g. test environment)
}
```

If the import fails (missing generated client, wrong working directory, initialization error), the code silently proceeds with `wireguardPort = 51820` default. No warning is logged. Production behavior silently diverges from the intended lookup.

**Test hooks are empty stubs:**

```ts
// chain-router.ts:403-417
export function __setDeps(deps: { ... }): void {
  void deps; // Does nothing
}
export function __resetDeps(): void {
  // Does nothing
}
```

Tests import `__setDeps` from `transport-resolver` (which has real implementations) but chain-router's own Prisma-dependent logic (the `generateChainConfig` function) cannot be tested with mocked service data because:
1. The `prisma` variable is lexically scoped inside `generateChainConfig`
2. The `__setDeps` hook in chain-router is a no-op
3. Tests can't inject a mock `prisma.service.findFirst` to control the WireGuard port resolution

### Solution

Replace the silent import with explicit dependency injection:

1. Add a `private prismaOverride` field to chain-router's dependency surface (or refactor to a class-based approach)
2. Make `__setDeps` actually register the override so tests can control Prisma-dependent behavior
3. Log a warning when the Prisma import fails instead of silently continuing
4. Alternatively, accept Prisma as a function parameter to `generateChainConfig`

### Scope

- `src/lib/chain-router.ts`: Replace silent catch with explicit DI or parameter injection
- `src/lib/__tests__/chain-router.test.ts`: Add test cases for service-port resolution

### Impact

- Production: WireGuard port misconfigurations are detected immediately instead of silently defaulting
- Tests: Service port resolution becomes testable
- Pattern: Establishes DI precedent for other modules that dynamically import Prisma

## Proposal 3: VPN Stub Success Responses Creating Deployment-Correctness Gap

### Problem

`vpn-services.ts` stubs return `success: true` with fake data:

```ts
// vpn-services.ts:109-116 (createAwgUser)
result.config = {
  publicKey: publicKey ?? 'STUB_PUBLIC_KEY',
  privateKey: 'STUB_PRIVATE_KEY',
  address: 'STUB_ADDRESS',
  allowedIPs: '0.0.0.0/0',
};
```

The full user creation flow works end-to-end:
`POST /api/users` → `createAwgUser()` returns `{ success: true, config: { ... } }` → `createThreeXuiUser()` returns `{ success: true }` → User saved to DB with fake protocol config

**The system appears fully functional but creates users with non-working VPN credentials.** An admin deploying the panel today would see successful user creation, but the users cannot actually connect to any VPN service.

This is distinct from the prior review's deferral note ("Known; deferred to real-service integration testing") because:
- The prior review framed stubs as "replace when environment is known"
- The real risk is that **the happy path completes successfully with no indication that credentials are fake**
- There is no guard, flag, or UI indicator that tells the admin "this user was created with placeholder credentials"

### Solution

**Option A: Fail-loud stubs** — Return `success: false` with a clear message ("AWG CLI not available on this server") instead of fake success. This breaks the user creation flow until real commands are wired, which is the correct behavior.

**Option B: Feature flag** — Add a `STUB_VPN_SERVICES` env variable (default: false). When true, current behavior continues (development mode). When false (production), stubs throw or return errors. This prevents accidental deployment with stubs.

**Option C: Stub indicator in UI** — Add a `isStub` field to `VpnServiceResult` that the frontend can display as a warning banner.

### Recommended: Option A (fail-loud) + Option B (env guard)

### Scope

- `src/lib/vpn-services.ts`: Change stub responses from success→true to success→false with descriptive message, or throw when `STUB_VPN_SERVICES !== 'true'`
- `src/app/api/users/route.ts`: Handle the new failure mode (user created in DB but VPN service unavailable)
- Frontend: Display warning when VPN service is unavailable during user creation

### Impact

- Prevents deployment of a panel that silently creates broken users
- Makes the stub→real transition explicit rather than implicit
- Admin gets honest feedback about what's actually configured
