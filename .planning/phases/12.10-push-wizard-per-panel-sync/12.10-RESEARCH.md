# Phase 12.10: Push wizard and per-panel sync fixes - Research

**Researched:** 2026-05-02
**Domain:** Central-to-remote config push, per-panel API key delivery, Xray rule scoping
**Confidence:** HIGH

## Summary

Phase 12.10 closes the remaining CPUSH-01 through CPUSH-06 and VISED-03 gaps identified in the v12.x audit closure. The core issues are: (1) PushWizard sends empty API keys on push and rollback, making auth impossible; (2) `generatePerPanelConfig` includes all chain Xray rules that match any chain node label instead of scoping them to the matched panel's node only; (3) push result aggregation from WebSocket events loses `configVersion` and `retries` fields; (4) `/api/chains/apply` builds an empty `panelCredentials` map, making the visual editor apply path non-functional.

Phase 12.8 already fixed the response parsing contracts (config-applier HMAC + unwrap, panel-sync-client unwrap, chain-router `panelCredentials` param) and updated types/tests. The remaining work is purely about wiring the **front-end to actually deliver real API keys** and fixing the **Xray rule panel-scoping bug** in `generatePerPanelConfig`.

**Primary recommendation:** Add an API key input step to PushWizard (collected from admin at push time), pass keys through the push API, fix `generatePerPanelConfig` Xray rule filtering to match only the matched node's label, and populate `panelCredentials` in chains/apply from the caller's keys.

### Anti-Patterns to Avoid
- **Never store plaintext API keys in the database** -- only in-memory cache (Map) per 12.5-CONTEXT.md decision. The admin enters them at push time; they're cached in `panelApiKeyCache` for auto-resync.
- **Never send API keys over unencrypted transport** -- all inter-panel traffic is over Tailscale (encrypted).
- **Never skip HMAC verification on /api/sync/apply and /api/sync/receive** -- already fixed in 12.8 (config-applier + panel-sync-client both sign payloads).

## Common Pitfalls

### Pitfall 1: Empty API Keys in PushWizard
**What goes wrong:** PushWizard sends `panelApiKeys[id] = ''` for every panel. The push route calls `cachePanelApiKey(id, '')` (caches empty string). Then `pushConfigToPanel` sends empty `X-API-Key` header. Remote panel's `/api/sync/receive` does `bcrypt.compare('', panel.apiKeyHash)` which fails auth.
**Why it happens:** Original PushWizard had no UI for API key input; comment says "server will use cached keys from previous connections" but no previous push happened.
**How to avoid:** Add API key input fields to PushWizard step 1 (one per selected panel). The admin must enter the shared secret per panel. Cache via `cachePanelApiKey`.
**Warning signs:** Push always returns 401 for all panels.

### Pitfall 2: Empty API Key in Rollback
**What goes wrong:** PushWizard's `handleRollback` sends `apiKey: ''`. Rollback route validates `apiKey: z.string().min(1)` and returns 422.
**Why it happens:** Same root cause as Pitfall 1 -- no key collection mechanism.
**How to avoid:** Store the API keys from step 1 in component state (e.g., `Map<number, string>`) and reuse them for rollback calls.
**Warning signs:** Rollback always fails with "Invalid request body".

### Pitfall 3: Xray Rules Not Panel-Scoped
**What goes wrong:** A panel receives Xray routing rules that belong to other panels in the chain. For example, an entry panel gets the exit panel's routing rules.
**Why it happens:** `generatePerPanelConfig` line 42 filters rules by `nodeLabels.has(rule.nodeId)` where `nodeLabels` contains ALL chain node labels. It should filter by `rule.nodeId === matchedNode.label` (matching the wireguardPeers pattern at line 53).
**How to avoid:** Change the filter to match only the matched node's label.
**Warning signs:** Panels have routing rules for nodes they don't host; routing conflicts on multi-panel chains.

### Pitfall 4: PushResult Loses configVersion and retries
**What goes wrong:** PushWizard step 4 shows results but configVersion is always null and retries is always 0 because results are built from WebSocket events which don't carry these fields.
**Why it happens:** `PushProgressEvent` type doesn't include `configVersion` or `retries` fields. When step 4 aggregates results from progress events (push-wizard.tsx lines 97-121), it hardcodes `configVersion: null, retries: 0`.
**How to avoid:** Either add `configVersion` and `retries` to the broadcast event payload, or wait for the actual PushAllResult from the push API response instead of building it from WebSocket events.
**Warning signs:** Step 4 always shows "configVersion: --" and "retries: 0".

### Pitfall 5: chains/apply Empty PanelCredentials
**What goes wrong:** Visual chain editor "Save Chain" calls `/api/chains/apply` which builds an empty `panelCredentials` map. All nodes get "No panel credentials registered for server N" errors.
**Why it happens:** Route has a TODO comment (line 106): "Phase 12.10 will add apiKey input to the chains/apply request body". The route can't retrieve plaintext keys from DB (only bcrypt hashes stored).
**How to avoid:** Accept `panelApiKeys` in the chains/apply request body (same as push route), build `panelCredentials` from them.
**Warning signs:** Editor apply always fails with credential errors.

## Open Questions

1. **API key UX location in PushWizard**
   - What we know: PushWizard has 4 steps (Select Panels, Preview, Push, Results). API keys must be collected before push.
   - What's unclear: Should keys go in step 1 alongside panel selection (inline per-panel input), or as a separate sub-step between 1 and 2?
   - Recommendation: Inline in step 1 -- simplest UX, admin sees panels and keys together. The panel list already shows panel names.

2. **Should API keys persist across PushWizard sessions?**
   - What we know: `panelApiKeyCache` is an in-memory Map (volatile). Each server restart clears it. Admin must re-enter keys.
   - What's unclear: Should the browser remember keys across wizard sessions (localStorage)?
   - Recommendation: No localStorage for security (CLAUDE.md: "plaintext is not recoverable from the DB after save"). In-memory cache only. Admin enters keys each time.

3. **Should chains/apply accept panelApiKeys or reuse push mechanism?**
   - What we know: chains/apply uses `applyChainConfig` which needs `panelCredentials`. Push uses `pushConfigToAllPanels` which needs `panelApiKeys`.
   - What's unclear: Should the visual editor's "Save Chain" call the push API directly instead of chains/apply?
   - Recommendation: Add `panelApiKeys` to chains/apply body (consistent with push route schema). The TODO comment in the route already suggests this.
