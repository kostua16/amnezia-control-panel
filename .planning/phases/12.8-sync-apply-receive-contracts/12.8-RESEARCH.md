# Phase 12.8: Sync apply & receive contracts - Research

**Researched:** 2026-05-02
**Domain:** Inter-panel sync contract alignment (config-applier, panel-sync-client, route handlers)
**Confidence:** HIGH -- all findings from direct codebase inspection of source files

## Summary

This phase fixes two concrete contract mismatches between callers and route handlers:

1. **config-applier -> /api/sync/apply**: The `config-applier.ts` caller sends requests to `/api/sync/apply` with only `Content-Type` header -- no `X-API-Key` or `X-Signature`. The `/api/sync/apply` route handler requires both headers and returns 401 immediately. Even if auth passed, config-applier checks `data.applied` at top level while the route returns `{ success: true, data: { applied: true, ... } }` (nested under `data`).

2. **panel-sync-client -> /api/sync/receive**: The `pushConfigToPanel` function in `panel-sync-client.ts` correctly sends `X-API-Key` and `X-Signature` headers, but after a 200 response it checks `data.applied` and `data.configVersion` on the parsed JSON object -- while the `/api/sync/receive` route returns `{ success: true, data: { applied: true, configVersion: N } }`. The values are nested under `.data`, so `data.applied` is `undefined`.

Both mismatches are the exact same pattern: callers destructure top-level fields while route handlers wrap results in `{ success: boolean, data: { ... } }`.

**Primary recommendation:** Fix both callers to unwrap `.data` from route responses. Add HMAC signing to config-applier calls to `/api/sync/apply`. Fix chain-router transport to use `panel.panelUrl` instead of `http://hostname:port`.

## Common Pitfalls

### Pitfall 1: config-applier sends unsigned requests (GAPL-01 root cause)
**What goes wrong:** `applyAwgConfig()` and `applyThreeXuiConfig()` in `config-applier.ts` set only `Content-Type` header (lines 58, 149). The `/api/sync/apply` route checks `X-API-Key` and `X-Signature` at lines 156-164 and returns 401 immediately.
**Why it happens:** config-applier was written before HMAC auth was added to the route handler, or was never updated when auth was added.
**How to avoid:** Add `signPayload()` + `X-API-Key`/`X-Signature` headers to both `applyAwgConfig()` and `applyThreeXuiConfig()`. This requires the caller to have access to the plaintext API key.
**Warning signs:** Any 401 response from `/api/sync/apply` when called from config-applier.

### Pitfall 2: config-applier response parsing ignores nested `data` wrapper
**What goes wrong:** `applyAwgConfig()` checks `data.applied` (line 68) and `data.message` (line 78) directly on the JSON response. The route returns `{ success: true, data: { applied: true, ... } }` -- so `data.applied` is `undefined` (falsy), making config-applier always report failure even on 200 OK.
**Why it happens:** config-applier was written expecting a flat response shape that was never the actual route contract.
**How to avoid:** Parse `const resp = await response.json(); const result = resp.data;` then check `result.applied`.
**Warning signs:** config-applier returns `{ success: false }` with message "Remote panel did not apply the config" even though the route returned 200.

### Pitfall 3: panel-sync-client response parsing ignores nested `data` wrapper
**What goes wrong:** `pushConfigToPanel()` checks `data.applied` and `data.configVersion` (line 113) directly on the JSON response. The `/api/sync/receive` route returns `{ success: true, data: { applied: true, configVersion: N } }` -- so `data.applied` is `undefined`.
**Why it happens:** Same pattern as pitfall 2 -- the caller assumes flat response.
**How to avoid:** Parse `const resp = await response.json(); const result = resp.data;` then check `result.applied && typeof result.configVersion === 'number'`.
**Warning signs:** pushConfigToPanel treats all 200 responses as failures and retries 3 times unnecessarily.

### Pitfall 4: chain-router uses wrong transport URL (CHAIN-01 root cause)
**What goes wrong:** `applyChainConfig()` in `chain-router.ts` constructs `const panelUrl = \`http://${node.hostname}:${node.port}\`` (line 151). This uses the server's SSH hostname and port (default 22), not the panel's registered `panelUrl` (which is the Next.js HTTP URL).
**Why it happens:** chain-router was written to use `ChainNode.hostname`/`port` from the template, which are server-level fields, not panel-level fields.
**How to avoid:** chain-router needs access to the remote panel's `panelUrl` from the database, or it needs to receive the panelUrl as a parameter. The `RemotePanel.panelUrl` field in the database stores the correct HTTP URL.
**Warning signs:** applyChainConfig fails with connection refused or timeout to `hostname:22` instead of `panelUrl:3333`.
**Scope note:** CHAIN-01 has a secondary issue with Tailscale transport (TSCL-04) which is out of scope for this phase -- tracked by Phase 12.11.

### Pitfall 5: config-applier needs API key but currently has no access to it
**What goes wrong:** `applyAwgConfig()` and `applyThreeXuiConfig()` accept `(panelUrl, panelName, ...)` but not an API key. To sign requests, the API key must be passed in.
**Why it happens:** Functions were designed before auth was required.
**How to avoid:** Add `apiKey: string` parameter to `applyAwgConfig()`, `applyThreeXuiConfig()`, and `applyPanelConfig()`. Update all call sites (chain-router, any future callers).

## Open Questions (RESOLVED)

1. **How should config-applier receive the API key?**
   - What we know: `applyAwgConfig`, `applyThreeXuiConfig`, and `applyPanelConfig` currently have no `apiKey` parameter.
   - What's unclear: Should the key be passed down from chain-router (which needs DB access to get it), or should config-applier query the DB itself?
   - Recommendation: Pass `apiKey` as a parameter through the call chain. chain-router already calls `generatePerPanelConfig` which uses DB. Add a query for `RemotePanel` by `serverId` to get `panelUrl` and `apiKey` (plaintext at push time from the in-memory cache or from the push request). This follows the existing pattern in `panel-sync-client.ts` where `pushConfigToAllPanels` receives `panelApiKeys: Map<number, string>`.

2. **Should chain-router query RemotePanel directly, or receive panelUrl/apiKey as parameters?**
   - What we know: `applyChainConfig()` currently takes only `(chainConfig, sourceIp?)`.
   - What's unclear: Whether to add a DB query inside chain-router or pass a `Map<number, { panelUrl: string; apiKey: string }>` from the caller.
   - Recommendation: Accept `panelCredentials: Map<number, { panelUrl: string; apiKey: string }>` parameter. This keeps chain-router testable (no DB dependency) and matches the pattern used by `pushConfigToAllPanels` in panel-sync-client. The API route caller (`/api/chains/apply` if it exists, or the push wizard) would construct this map from the DB + in-memory key cache.

3. **Should `SyncReceiveResponse` type be updated to match actual route response?**
   - What we know: The type declares flat `{ applied, configVersion }`. The route returns `{ success, data: { applied, configVersion } }`.
   - What's unclear: Whether this type is consumed anywhere.
   - Recommendation: Update it. Also add a `SyncApplyResponse` type for the apply route's response shape. These types serve as the contract documentation.

### Known Threat Patterns for Node.js sync endpoints

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Missing auth headers (GAPL-01) | Spoofing | Ensure ALL callers send X-API-Key + X-Signature |
| Replay attacks | Tampering | HMAC covers full request body; body content includes configVersion for idempotency |
| API key exposure in logs | Information Disclosure | Never log plaintext API keys; routes compare against bcrypt hash |
| Response shape confusion | Tampering | Strict response type checking; unwrap `.data` consistently |

### Security consideration for this phase
The key security fix is ensuring config-applier signs its payloads. Currently it sends unsigned requests that would be rejected by the route's HMAC check (good -- the route is secure). But the 401 is treated as a generic error by config-applier rather than surfacing the auth issue clearly. After fixing auth, the full HMAC verification chain is intact.
