## Task Breakdown

### Task 1: GET /api/users API Endpoint (20 min)

**File:** src/app/api/users/route.ts (NEW)

Create a Next.js Route Handler that returns a paginated, searchable, sortable list of users from the Prisma database.

**Query parameters:**

| Param | Type | Default | Description |
|---|---|---|---|
| search | string | (empty) | Filter by username or displayName (case-insensitive) |
| sortBy | string | createdAt | Sort field: createdAt, username, displayName |
| sortOrder | string | desc | Sort direction: asc or desc |
| page | number | 1 | Page number |
| limit | number | 50 | Items per page (max 100) |

**Response shape** (matches existing PaginatedResponse from src/types/api.ts):

The API returns an object with success: true, a data array of UserWithServices (each user + assignedServices: ServiceType[]), and a pagination object containing page, limit, total, and totalPages.

**Implementation details:**

1. Use zod for query parameter validation (consistent with src/app/api/auth/login/route.ts pattern).
2. Import prisma from @/lib/prisma and use the success()/error() helpers from @/lib/api-response.
3. Query the User model with include: { protocols: { where: { isActive: true } } } to get assigned services.
4. Map UserProtocol[].serviceType into assignedServices: ServiceType[] on each user record.
5. Apply where clause with OR on username and displayName for search filtering.
6. Apply orderBy based on sortBy / sortOrder.
7. Compute total via prisma.user.count() with the same where clause.
8. Map Prisma enums correctly: isBlocked overrides isActive for display status (blocked > inactive > active).

**Validation schema:**

    const listUsersSchema = z.object({
      search: z.string().optional().default(""),
      sortBy: z.enum(["createdAt", "username", "displayName"]).optional().default("createdAt"),
      sortOrder: z.enum(["asc", "desc"]).optional().default("desc"),
      page: z.coerce.number().int().min(1).optional().default(1),
      limit: z.coerce.number().int().min(1).max(100).optional().default(50),
    });

**Error responses:**
- 422 if query params fail validation
- 500 if database query fails (with console.error logging, matching existing pattern)

### Task 2: React Query Hook -- useUsers (10 min)

**File:** src/hooks/use-users.ts (NEW)

Create a React Query hook following the exact same pattern as src/hooks/use-service-status.ts which uses @tanstack/react-query (already installed, version ^5.100.5).

    export interface UsersListParams {
      search?: string;
      sortBy?: string;
      sortOrder?: string;
      page?: number;
      limit?: number;
    }

    export function useUsers(params?: UsersListParams) {
      return useQuery({
        queryKey: ["users", params],
        queryFn: () => fetchUsers(params),
        staleTime: 10_000,
      });
    }

- fetchUsers builds the query string from params and calls GET /api/users.
- Returns the parsed PaginatedResponse with UserWithServices array.
- Uses the UserWithServices type from src/types/user.ts.

## Key Patterns to Follow

1. **Data fetching:** @tanstack/react-query via useQuery (see use-service-status.ts)
2. **API response:** Use success()/error() helpers from @/lib/api-response
3. **Validation:** zod schemas for API input validation
4. **Styling:** clsx for conditional classes, Tailwind CSS utility classes
5. **UI primitives:** Card, Button, Input from @/components/ui/
6. **Icons:** lucide-react (Pencil, Ban, ShieldCheck, Trash2, Search, Users, Plus)
7. **Status dots:** span with h-2.5 w-2.5 rounded-full bg-green-500 pattern from service-status.tsx
8. **Client components:** use client directive on interactive components
9. **Color scheme:** Dark theme with CSS variables from globals.css

## Design Decisions

- **React Query over SWR:** Codebase already uses @tanstack/react-query (installed and used in use-service-status.ts). No reason to add SWR.
- **Server-side pagination for 50 users:** Even though 50 users fit on one page, the API supports pagination from the start for correctness and future-proofing.
- **Action buttons are placeholders:** Edit, Delete, and Block/Unblock onClick handlers will console.log and show a TODO comment. Phases 4.3-4.8 will wire real functionality.
- **No confirmation dialog for Delete placeholder:** Will be added in Phase 4.7.
- **Search debounce:** 300ms debounce prevents excessive API calls on rapid typing.

## Potential Challenges

1. **Prisma include + map:** The UserProtocol relation uses serviceType as ServiceType enum. Need to map protocols: UserProtocol[] to assignedServices: ServiceType[]. Only include isActive: true protocols.
2. **Table responsiveness:** On mobile, the table may overflow. Wrap in overflow-x-auto div. Consider hiding the Quota column on small screens.
3. **Sort by displayName with nulls:** Prisma sorts nulls last by default. Use sortBy: displayName with asc to show named users first.
