<decisions>
## Implementation Decisions

### Tailscale Interaction
- **D-01:** Use Tailscale CLI (`tailscale` command) via `execFile` — same pattern as `vpn-services.ts` and `service-monitor.ts`. No local API (localhost:10000), no JS wrapper libraries.
- **D-02:** Real-time node status — every API call runs `tailscale status` fresh. No caching, no subscriptions. Simple and always up-to-date for 1-3 server scale.
- **D-03:** TailscaleManager as thin utility file `src/lib/tailscale.ts` with functions: `getStatus()`, `getNodes()`, `getNodeIP()`, `isReachable()`. No class-based abstraction.
- **D-04:** CLI binary resolution — try `tailscale` in PATH first, fallback to `/usr/bin/tailscale`.

### Subnet Advertising
- **D-05:** Auto-detect VPN subnets from server configuration (AmneziaWG default 10.0.0.0/24, Xray 172.16.0.0/12) + manual override for admin to add/remove ranges.
- **D-06:** Overlapping subnet handling — warn but don't block. Admin decides. At 1-3 server scale, conflicts are rare and manageable.

### Prisma Schema
- **D-07:** Extend existing `Server` model with Tailscale fields (no separate TailscaleNode model). Fields: `tailnetIP` (String), `tailnetHostname` (String), `dnsName` (String), `advertisedSubnets` (String[]).
- **D-08:** `isOnline` and `lastSeen` are NOT stored in DB — derived from `tailscale status` on each call (consistent with D-02 real-time approach).

### Setup Documentation
- **D-09:** In-panel setup wizard with automatic step validation. Wizard checks each step (e.g., `which tailscale`, `tailscale status`) before allowing admin to proceed. No manual checkboxes.
- **D-10:** Setup wizard covers: Tailscale installation verification, auth/login, subnet router configuration (`tailscale up --advertise-routes=...`), verify node appears in tailnet.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `src/lib/vpn-services.ts` — `runCommand()` helper with timeout, error swallowing, structured `VpnServiceResult`. Same pattern for Tailscale CLI calls.
- `src/lib/server-connection.ts` — `testConnection()` uses ping; `executeOnServer()` is a stub. Tailscale IP resolution replaces ping-based connectivity with direct mesh reachability.
- `src/lib/service-monitor.ts` — `execFileSync` for `systemctl` commands. Similar pattern for `tailscale` CLI.

### Established Patterns
- All shell commands use `execFile` (async) or `execFileSync` (sync) from `child_process` — no SSH, no HTTP to remote servers yet
- VPN service stubs return structured `{ success, message, config? }` results — follow this for Tailscale operations
- 10s timeout for all shell commands in vpn-services.ts

### Integration Points
- `Server` Prisma model needs migration to add tailnet fields
- `src/app/api/servers/` — existing server API routes will need tailnet status endpoints
- Future Phase 11.2 will consume `tailscale.ts` functions to build remote panel registration

</code_context>
