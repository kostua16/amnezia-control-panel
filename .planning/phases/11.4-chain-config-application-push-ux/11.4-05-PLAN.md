Key insight for the executor:
- `generateChainConfig()` takes Server[] and produces nodes with serverId = Server.id
- `generatePerPanelConfig()` matches node.serverId against a panelId (RemotePanel.id)
- Server.id and RemotePanel.id are DIFFERENT ID spaces (different Prisma tables)
- The NEW endpoint must generate ChainConfig where node.serverId = RemotePanel.id
- This means we CANNOT simply reuse generateChainConfig() -- we need a custom generation that uses RemotePanel data as the server source

**Create `src/app/api/panels/push/chain-config/route.ts` (POST endpoint):**

This endpoint generates a ChainConfig from a template + panel mapping. It is the server-side equivalent of `generateChainConfig` but uses RemotePanel data instead of Server data, so that `node.serverId` = `RemotePanel.id` (which is what `generatePerPanelConfig` and the push/diff endpoints expect).

Zod validation schema:
```typescript
const chainConfigRequestSchema = z.object({
  templateId: z.string().min(1),
  panelMapping: z.record(z.coerce.number().int(), z.coerce.number().int()),
  // key = node index in template, value = RemotePanel.id
});
```

Logic:
1. Validate template exists via `getTemplateById(templateId)`
2. Validate all required node indices have a panel mapping
3. Fetch all referenced RemotePanel records from prisma (`prisma.remotePanel.findMany({ where: { id: { in: panelIds } } })`)
4. Validate all panels exist and are active
5. Validate no duplicate panel assignments (each panel maps to at most one node)
6. Build a panel lookup: `Map<panelId, RemotePanel>`
7. Resolve template nodes with panel data:
   - For each template node at index `i`: `serverId = panelMapping[i]`, `hostname = panel.panelUrl.replace(/^https?:\/\//, '').split('/')[0]` (extract host from panelUrl), `port = 3000` (default panel port -- or parse from panelUrl)
8. Generate WireGuard peer configs using the same topology-based logic from `chain-router.ts` `generateWireGuardPeers` (replicate the function inline or extract as shared util). IMPORTANT: since this is template-based config generation for preview/push (not real key exchange), use the same STUB_PUBKEY pattern that chain-router.ts uses.
9. Generate Xray routing rules using the same topology-based logic from `chain-router.ts` `generateXrayRoutingRules` (replicate inline).
10. Return `{ success: true, data: chainConfig }` where chainConfig is the full ChainConfig object.

Response shape:
```json
{
  "success": true,
  "data": {
    "templateId": "2hop-linear",
    "nodes": [
      { "label": "Entry Server", "serverId": 1, "role": "entry", "protocol": "wireguard", "hostname": "100.x.x.x", "port": 3000 },
      { "label": "Exit Server", "serverId": 2, "role": "exit", "protocol": "wireguard", "hostname": "100.y.y.y", "port": 3000 }
    ],
    "wireguardPeers": [...],
    "xrayRoutingRules": [...],
    "generatedAt": "2026-04-30T..."
  }
}
```

**Create `src/app/api/panels/push/status/route.ts` (GET endpoint):**

This endpoint serves the polling fallback for push progress. Since push progress is transient (in-memory WebSocket events), this endpoint returns a simple status response. When no push is in progress, return empty events array.

Logic:
1. `GET` handler, no auth required (polling is fire-and-forget)
2. Return `{ success: true, data: { events: [] } }` -- empty events because push progress is ephemeral and already delivered via WebSocket
3. This satisfies the polling code in push-wizard.tsx (lines 123-141) which silently catches errors and gracefully handles empty event arrays

This is intentionally a no-op endpoint. The polling fallback was designed for resilience but WebSocket is the primary channel. The existing polling code in push-wizard.tsx already handles `{ events: [] }` gracefully (it just iterates and updates nothing).
