# Phase 12.9: WebSocket → React Query Key Alignment - Research

**Researched:** 2026-05-02
**Domain:** TanStack Query v5 cache invalidation via WebSocket event bridge
**Confidence:** HIGH

## Summary

Three React Query hooks (`use-dashboard-stats`, `use-system-resources`, `use-multi-panel-status`) define query keys that never get invalidated by WebSocket events because `WS_TO_QUERY_KEYS` in `providers.tsx` uses wrong key arrays. TanStack Query v5 `invalidateQueries` performs element-by-element prefix matching -- `['dashboard', 'stats']` does NOT match `['dashboard-stats']`. The server already broadcasts `stats:update` (30s) and `resource:update` (10s), but the bridge silently fails to invalidate the corresponding caches.

Additionally, `use-alerts.ts` performs its own invalidation via `useWebSocketContext`, creating duplicate invalidation with the bridge for `alert:new`. Two other WS events (`chain:status-update`, `panel:push-progress`) target keys that no React Query hook uses -- `use-chain-status.ts` bypasses React Query entirely with direct Socket.IO, and `push-wizard.tsx` reads `lastEvent` directly.

**Primary recommendation:** Fix the three broken key mappings, remove duplicate `alert:new` invalidation from providers.tsx (let `use-alerts.ts` own it), and remove meaningless entries for non-React-Query consumers.

### Fixed Bridge Flow

```
Server broadcasts          Client providers.tsx           React Query hooks
─────────────────          ──────────────────           ─────────────────
stats:update ──→ Socket ──→ WS_TO_QUERY_KEYS lookup ──→ invalidateQueries(['dashboard-stats'])
                                                             ↓
                                                    MATCH → cache invalidated → refetch triggered
```

### TanStack Query v5 Prefix Matching

`invalidateQueries({ queryKey: ['dashboard-stats'] })` matches any query whose key starts with `['dashboard-stats', ...]` element-by-element. Critically:

```typescript
// DOES match:
['dashboard-stats']                          // exact match
['dashboard-stats', 'some-filter']           // prefix match

// DOES NOT match:
['dashboard', 'stats']                       // different first element
['monitoring', 'resources']                  // completely different
```

Source: [TanStack Query Docs - Query Keys](https://tanstack.com/query/latest/docs/framework/react/guides/query-keys) [CITED: tanstack.com]

### Duplicate Invalidation: alert:new

`use-alerts.ts` already invalidates both `['alerts']` and `['alerts-unread-count']` inside its own `useEffect` listening to `lastEvent`:

```typescript
// In use-alerts.ts (already handles its own invalidation):
if (lastEvent['alert:new']) {
  queryClient.invalidateQueries({ queryKey: ['alerts'] });
  queryClient.invalidateQueries({ queryKey: ['alerts-unread-count'] });
}
```

The bridge in `providers.tsx` also invalidates `['alerts']` for `alert:new`. This is harmless (double-invalidate is idempotent) but wasteful. The bridge entry for `alert:new` should be removed to keep a single source of truth per concern. [VERIFIED: codebase grep]

## Common Pitfalls

### Pitfall 1: Element-by-element prefix matching confusion
**What goes wrong:** Developer assumes `['dashboard', 'stats']` matches `['dashboard-stats']` because it looks like a substring.
**Why it happens:** TanStack Query uses array element comparison, not string concatenation.
**How to avoid:** Copy queryKey values directly from hook definitions; never construct them manually.
**Warning signs:** `stats:update` fires but `useQuery` shows stale data until next `refetchInterval` tick.

### Pitfall 2: Duplicate invalidation masking the real bug
**What goes wrong:** Fixing one layer (bridge) while the other layer (hook-level invalidation) already works, leading to confusion about which fix solved the problem.
**Why it happens:** `use-alerts.ts` added its own invalidation as a workaround; the bridge was never fixed.
**How to avoid:** Remove the `alert:new` entry from the bridge after verifying `use-alerts.ts` handles it.
**Warning signs:** `alert:new` events trigger refetch even if bridge is removed.

### Pitfall 3: Leaving no-op entries in WS_TO_QUERY_KEYS
**What goes wrong:** Future developers see `chain:status-update → [['chains']]` and assume some hook uses `['chains']`, wasting investigation time.
**Why it happens:** Hooks were added later without RQ, but bridge entries were never cleaned up.
**How to avoid:** Remove entries for events with no React Query consumers.
**Warning signs:** Searching codebase for a queryKey prefix returns zero results.

### Verification: TanStack Query prefix matching behavior

```typescript
// These DO match:
queryClient.invalidateQueries({ queryKey: ['dashboard-stats'] });
// matches queryKey: ['dashboard-stats']

queryClient.invalidateQueries({ queryKey: ['users'] });
// matches queryKey: ['users', { page: 1 }]

// These DO NOT match:
queryClient.invalidateQueries({ queryKey: ['dashboard', 'stats'] });
// does NOT match queryKey: ['dashboard-stats']
```
