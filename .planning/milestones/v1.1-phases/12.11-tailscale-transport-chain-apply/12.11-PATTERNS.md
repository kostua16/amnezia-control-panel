## Pattern Assignments

### `src/lib/transport-resolver.ts` (utility, request-response) -- NEW FILE

**Analog:** `src/app/api/servers/[id]/tailnet/route.ts`

This is the primary new file. It extracts the 3-tier fallback logic from the tailnet route into a reusable utility function. The tailnet route currently implements inline resolution; the new file generalizes it.

**Imports pattern** (tailnet route lines 1-3):
```typescript
import { prisma } from '@/lib/prisma';
import { getNodeIP, isReachable } from '@/lib/tailscale';
```

The new utility should import from these same modules. It should NOT import NextResponse (not a route handler).

**Core 3-tier fallback pattern** (tailnet route lines 42-69):
```typescript
let resolvedIP: string | null = null;
let hostnameUsed: string = '';
let source: 'db' | 'cli-resolve' | 'fallback' = 'db';

// Tier 1: Use tailnetIP from DB (D-07)
if (server.tailnetIP) {
  resolvedIP = server.tailnetIP;
  hostnameUsed = server.tailnetHostname ?? server.hostname;
  source = 'db';
}

// Tier 2: Resolve via tailnetHostname
if (!resolvedIP && server.tailnetHostname) {
  resolvedIP = await getNodeIP(server.tailnetHostname);
  if (resolvedIP) {
    hostnameUsed = server.tailnetHostname;
    source = 'cli-resolve';
  }
}

// Tier 3: Fallback via server hostname
if (!resolvedIP) {
  resolvedIP = await getNodeIP(server.hostname);
  if (resolvedIP) {
    hostnameUsed = server.hostname;
    source = 'fallback';
  }
}
```

**DB cache-back pattern** (tailnet route lines 84-92):
```typescript
// Cache resolved IP back to Server record if not from DB
if (source !== 'db') {
  await prisma.server.update({
    where: { id: serverId },
    data: {
      tailnetIP: resolvedIP,
      tailnetHostname: hostnameUsed,
    },
  });
}
```

**Return type pattern** -- derive from existing `TransportAddress` type (`src/types/tailscale.ts` lines 57-62):
```typescript
export interface TransportAddress {
  tailscaleIP: string;
  hostname: string;
  port: number;
}
```

The new `ResolvedTransport` should extend this with `online`, `source`, and `panelUrl` fields as described in RESEARCH.md Pattern 1.

**Key difference from analog:** The tailnet route is a Next.js API handler (uses `NextRequest`, `NextResponse`, `RouteContext`). The new utility is a plain async function -- no HTTP framing. Extract only the resolution logic, not the request/response wrappers.

## Database Schema Constraints

**RemotePanel has NO `serverId` field.** The `RemotePanel` model (schema.prisma lines 316-328) has: `id`, `name`, `panelUrl`, `apiKeyHash`, `isActive`, `createdAt`, `updatedAt`. There is no foreign key to `Server`.

**Server model** (schema.prisma lines 76-93) has: `id`, `name`, `hostname`, `port` (default 22), `apiKeyHash`, `tailnetIP` (nullable), `tailnetHostname` (nullable), `dnsName` (nullable), `advertisedSubnets`, `isActive`.

**Implication:** The `/api/chains/apply` route (line 95) queries `remotePanel.serverId` which does NOT exist in the schema. This is a latent bug. Phase 12.11 must either:
1. Add a `serverId` field to `RemotePanel` (migration), or
2. Match panels to servers by correlating `panelUrl` hostname with `server.hostname`/`server.tailnetIP`, or
3. Have the caller provide panel-to-server mapping in the request body.
