# Phase 11.1: Tailscale Foundation - Research

**Researched:** 2026-04-29
**Domain:** Tailscale CLI integration, subnet routing, inter-panel transport
**Confidence:** HIGH

## Summary

Phase 11.1 introduces Tailscale as the encrypted mesh transport layer between panels. This is a pure backend + minimal UI phase: extend the Server Prisma model with tailnet fields, build a thin `tailscale.ts` utility that shells out to the `tailscale` CLI (same pattern as `vpn-services.ts`), create API routes for node listing and status, and build an in-panel setup wizard with step validation.

The key finding is that `tailscale status --json` returns a rich `Status` object with `Self` (local node) and `Peer` (map of all tailnet nodes), each containing `TailscaleIPs`, `DNSName`, `Online`, `HostName`, `OS`, `AllowedIPs`, and `PrimaryRoutes`. This is the single data source for all tailnet discovery needs. The modern way to advertise routes on an already-connected node is `tailscale set --advertise-routes=...` (not `tailscale up`), which avoids disrupting the existing connection. The `tailscale ip -4` command returns only the IPv4 Tailscale address for the local or a named node, which is useful for transport address resolution.

No new npm dependencies are needed. The phase uses `child_process.execFile` (already in the project), Prisma migrations for schema changes, and the existing API route pattern. The setup wizard is the only new UI component.

**Primary recommendation:** Use `tailscale status --json` as the single data source, parse the `Peer` map into a flat array, and derive everything (IPs, hostnames, online status, advertised routes) from that. Use `tailscale set` (not `tailscale up`) for modifying advertised routes on a running node.

### Locked Decisions

- **D-01:** Use Tailscale CLI (`tailscale` command) via `execFile` -- same pattern as `vpn-services.ts` and `service-monitor.ts`. No local API (localhost:10000), no JS wrapper libraries.
- **D-02:** Real-time node status -- every API call runs `tailscale status` fresh. No caching, no subscriptions. Simple and always up-to-date for 1-3 server scale.
- **D-03:** TailscaleManager as thin utility file `src/lib/tailscale.ts` with functions: `getStatus()`, `getNodes()`, `getNodeIP()`, `isReachable()`. No class-based abstraction.
- **D-04:** CLI binary resolution -- try `tailscale` in PATH first, fallback to `/usr/bin/tailscale`.
- **D-05:** Auto-detect VPN subnets from server configuration (AmneziaWG default 10.0.0.0/24, Xray 172.16.0.0/12) + manual override for admin to add/remove ranges.
- **D-06:** Overlapping subnet handling -- warn but don't block. Admin decides. At 1-3 server scale, conflicts are rare and manageable.
- **D-07:** Extend existing `Server` model with Tailscale fields (no separate TailscaleNode model). Fields: `tailnetIP` (String), `tailnetHostname` (String), `dnsName` (String), `advertisedSubnets` (String[]).
- **D-08:** `isOnline` and `lastSeen` are NOT stored in DB -- derived from `tailscale status` on each call (consistent with D-02 real-time approach).
- **D-09:** In-panel setup wizard with automatic step validation. Wizard checks each step (e.g., `which tailscale`, `tailscale status`) before allowing admin to proceed. No manual checkboxes.
- **D-10:** Setup wizard covers: Tailscale installation verification, auth/login, subnet router configuration (`tailscale up --advertise-routes=...`), verify node appears in tailnet.

### Pattern 1: CLI Execution via execFile

**What:** Use `promisify(execFile)` to run Tailscale CLI commands, same pattern as `vpn-services.ts`.
**When to use:** Every Tailscale operation (status, ip, set, ping, version).
**Example:**
```typescript
// Source: existing pattern in src/lib/vpn-services.ts lines 47-75
import { execFile } from 'child_process';
import { promisify } from 'util';

const execFileAsync = promisify(execFile);

const TAILSCALE_BIN = 'tailscale'; // D-04: try PATH first, fallback to /usr/bin/tailscale

async function runTailscale(
  args: string[],
  label: string,
  timeout = 10_000,
): Promise<{ success: boolean; stdout: string; message: string }> {
  try {
    const { stdout, stderr } = await execFileAsync(TAILSCALE_BIN, args, {
      timeout,
      encoding: 'utf-8',
    });
    return { success: true, stdout: stdout.trim(), message: stdout.trim() || 'OK' };
  } catch (err) {
    const msg = err instanceof Error ? err.message : String(err);
    return { success: false, stdout: '', message: msg };
  }
}
```

**Security note:** `execFile` with array-based arguments (not string-based `exec`) provides inherent protection against shell injection because arguments are never passed through a shell. The existing `vpn-services.ts` already follows this pattern. All user-provided inputs (CIDR values, hostnames) must be validated with zod before passing as arguments.

### Pattern 2: Parse `tailscale status --json`

**What:** Run `tailscale status --json`, parse the JSON output, extract peer data.
**When to use:** Node discovery, status listing, online check.
**Example:**
```typescript
// Source: Tailscale Go source ipn/ipnstate/ipnstate.go PeerStatus struct
// https://github.com/tailscale/tailscale/blob/main/ipn/ipnstate/ipnstate.go

interface TailscalePeer {
  ID: string;              // tailcfg.StableNodeID
  PublicKey: string;       // base64 node key (map key in Peer)
  HostName: string;        // OS hostname (not unique)
  DNSName: string;         // FQDN, e.g., "server1.tail1234.ts.net."
  OS: string;              // "linux", "windows", etc.
  TailscaleIPs: string[];  // e.g., ["100.64.0.1"]
  AllowedIPs?: string[];   // advertised + assigned prefixes
  PrimaryRoutes?: string[];// subnet routes this node advertises
  Online: boolean;
  Active: boolean;
  Relay: string;           // DERP region code if relayed (e.g., "nyc", "fra")
  CurAddr: string;         // direct connection endpoint IP:port
  RxBytes: number;
  TxBytes: number;
  LastSeen?: string;       // ISO timestamp, only present if offline
}

interface TailscaleStatus {
  Version: string;
  BackendState: string;    // "Running", "Stopped", "NeedsLogin", etc.
  TailscaleIPs: string[];
  Self: TailscalePeer;
  Peer: Record<string, TailscalePeer>; // keyed by node public key (NOT hostname/IP)
  CurrentTailnet: {
    Name: string;
    MagicDNSSuffix: string;
    MagicDNSEnabled: boolean;
  } | null;
  Health: string[];
}
```

### Anti-Patterns to Avoid

- **Using `tailscale up --advertise-routes` to change routes on a running node:** This may disrupt the connection. Use `tailscale set --advertise-routes=...` for modifications after initial setup. Per D-10, `tailscale up` is only for initial connect+configure.
- **Caching `tailscale status` results:** D-02 explicitly forbids caching. Always run fresh. At 1-3 server scale, the <100ms latency of a local CLI call is negligible.
- **Building a class-based TailscaleManager:** D-03 says thin utility file with functions. Follow the `vpn-services.ts` pattern of exported async functions.
- **Storing `isOnline` or `lastSeen` in the database:** D-08 says derive from `tailscale status` on each call. Stale DB state would be misleading.
- **Using the Tailscale Local API (localhost:10000):** D-01 says CLI only. The Local API requires socket path configuration and adds complexity with no benefit at this scale.

## Common Pitfalls

### Pitfall 1: `tailscale status --json` Peer map is keyed by public key, not by hostname or IP
**What goes wrong:** Trying to look up peers by hostname or IP in the map fails because the key is the base64-encoded node public key.
**Why it happens:** The Go source uses `map[key.NodePublic]*PeerStatus`, and JSON serialization preserves this.
**How to avoid:** Convert the `Peer` map to an array (`Object.values(status.Peer)`) and search/filter by `DNSName`, `TailscaleIPs`, or `HostName` fields.
**Warning signs:** "Cannot read property 'DNSName' of undefined" when trying to access a peer by hostname.

### Pitfall 2: `tailscale set` requires the node to be already connected
**What goes wrong:** Running `tailscale set --advertise-routes=...` on a node that is not logged in to Tailscale returns an error.
**Why it happens:** `tailscale set` modifies preferences on a running `tailscaled` daemon. If the daemon is not running or authenticated, there is nothing to configure.
**How to avoid:** In the setup wizard, verify `tailscale status` returns `BackendState: "Running"` before attempting to advertise routes. For initial setup, use `tailscale up --advertise-routes=...` (D-10).
**Warning signs:** "tailscaled: not connected" or "BackendState: NeedsLogin" in status output.

### Pitfall 3: Prisma `String[]` in SQLite is stored as JSON, not as a native array
**What goes wrong:** Querying or filtering by `advertisedSubnets` does not work with plain SQL `IN` clause.
**Why it happens:** SQLite has no native array type. Prisma stores `String[]` as a JSON string like `'["10.0.0.0/24","172.16.0.0/12"]'`.
**How to avoid:** For this phase, the array is only read and written as a whole (no per-element querying needed). Prisma handles serialization/deserialization transparently. [CITED: Prisma docs -- String[] maps to JSON in SQLite]
**Warning signs:** Raw SQL queries against the `advertisedSubnets` column return JSON strings, not arrays.

### Pitfall 4: Tailscale requires IP forwarding enabled for subnet routing
**What goes wrong:** Routes are advertised but traffic does not flow through the subnet router.
**Why it happens:** Linux kernel drops forwarded packets unless `net.ipv4.ip_forward = 1` is set.
**How to avoid:** The setup wizard (D-09/D-10) must verify IP forwarding is enabled before advertising routes. Check via `sysctl net.ipv4.ip_forward`. [CITED: Tailscale subnet router docs]
**Warning signs:** "Routes advertised but peer cannot reach subnet" -- classic IP forwarding issue.

### Pitfall 5: `tailscale status --json` may include non-subnet-router peers
**What goes wrong:** Node listing shows all devices in the tailnet (phones, laptops), not just VPN servers.
**Why it happens:** Every device on the tailnet appears in the `Peer` map.
**How to avoid:** The panel should filter peers. Two strategies: (1) match peers to registered `Server` records by `tailnetIP` or `dnsName`, (2) check `PrimaryRoutes` field -- only subnet routers have non-empty primary routes. Phase 11.2 will need to match tailnet nodes to registered servers. For Phase 11.1, show all peers and let the admin identify which are servers.
**Warning signs:** Unexpected devices (personal phones, laptops) appearing in the tailnet nodes list.

## Code Examples

### Get Tailscale Status (JSON)
```typescript
// Source: Tailscale CLI docs, ipn/ipnstate/ipnstate.go
async function getStatus(): Promise<TailscaleStatus | null> {
  const result = await runTailscale(['status', '--json'], 'Tailscale:getStatus');
  if (!result.success) return null;
  try {
    return JSON.parse(result.stdout) as TailscaleStatus;
  } catch {
    return null;
  }
}
```

### Get All Tailnet Nodes
```typescript
// Source: derived from Peer map structure in ipnstate.go
async function getNodes(): Promise<TailscalePeer[]> {
  const status = await getStatus();
  if (!status?.Peer) return [];
  return Object.values(status.Peer);
}
```

```typescript
async function advertiseRoutes(subnets: string[]): Promise<boolean> {
  const routes = subnets.join(',');
  const result = await runTailscale(
    ['set', `--advertise-routes=${routes}`],
    'Tailscale:advertiseRoutes',
```

### Verify Tailscale Installation
```typescript
// Source: D-04 CLI binary resolution
async function verifyInstalled(): Promise<{ installed: boolean; version: string }> {
  const result = await runTailscale(['version'], 'Tailscale:verifyInstall', 5_000);
  if (!result.success) {
    return { installed: false, version: '' };
  }
  // Output is like "1.78.0\n  tailscale commit: abc123..."
  const version = result.stdout.split('\n')[0].trim();
  return { installed: true, version };
}
```

## Open Questions

1. **Headscale compatibility**
   - What we know: The project might use Headscale (self-hosted control server) instead of Tailscale's cloud coordination. The `--login-server` flag supports this.
   - What is unclear: Whether the admin uses Headscale. If yes, the setup wizard needs to capture the Headscale URL.
   - Recommendation: The `tailscale` CLI is agnostic to control server. No code change needed. The setup wizard should accept an optional login server URL if needed. For Phase 11.1, document that Headscale is supported but do not add extra UI unless requested.

2. **Sudo/root requirements for `tailscale set`**
   - What we know: Modifying routes via `tailscale set` requires the process to have permission to communicate with `tailscaled`. The panel runs as a web server, typically non-root.
   - What is unclear: Whether the panel process needs sudo to run `tailscale set`.
   - Recommendation: The existing `service-monitor.ts` uses `execFileSync` for `systemctl` commands, which also typically require root. Check how the panel currently handles permissions. If the panel already runs as root (common for single-server deployment), no issue. If not, may need a sudoers rule.

### Known Threat Patterns for Tailscale CLI Integration

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Command injection via subnet CIDR | Tampering | Validate with zod CIDR regex before passing to `execFile`. `execFile` with array args prevents shell injection by design. |
| Exposing tailnet topology to unauthorized users | Information Disclosure | API routes must require admin JWT auth (existing middleware). Never expose `Peer.PublicKey` or `User` details to frontend. |
| Unprivileged process running `tailscale set` | Elevation of Privilege | Panel must run with sufficient privileges to communicate with `tailscaled`. Use socket permissions or sudoers rule. |
| Subnet route hijacking (advertising overlapping routes) | Tampering | D-06: warn on overlap, admin decides. Tailscale admin console requires explicit route approval. |

**Key security note:** `execFile` with array-based arguments (not string-based `exec`) provides inherent protection against shell injection. The existing `vpn-services.ts` already follows this pattern. The `sanitizeUsername` pattern from `vpn-services.ts` should be adapted for CIDR validation -- validate with zod before passing to `execFile`.
