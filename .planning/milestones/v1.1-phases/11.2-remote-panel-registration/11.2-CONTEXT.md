# Phase 11.2: Remote Panel Registration - Context

**Gathered:** 2026-04-29
**Status:** Ready for planning

<domain>
## Phase Boundary

Admin can register remote panels from the central panel, test connectivity, monitor real-time connection status, and manage (edit/remove) remote panels. This forms the multi-panel topology that all subsequent v1.1 phases depend on.

</domain>

<decisions>
## Implementation Decisions

### Remote Panel Data Model
- Auth credentials stored as hashed API key (matches existing Server model bcrypt pattern)
- Separate `RemotePanel` Prisma model — cleaner separation from local Server model
- Tailscale IP resolved at runtime via TailscaleManager (always fresh, no stale cached IPs)

### Connectivity & Status
- Periodic health check at 30s interval (reuse existing service monitoring pattern)
- Connectivity test returns `{success, latencyMs, version, services[]}` matching ServerTestResult pattern
- Last 10 connection results stored in SQLite for debugging

### Management UI
- New "Panels" tab in sidebar navigation (separate from local Servers)
- Single registration form with inline validation (same as AddServerForm pattern)
- Badge-based status (green/yellow/red) with details drawer (matches service status pattern)

### Claude's Discretion
- Exact RemotePanel Prisma schema fields beyond the decided ones (e.g., lastCheckAt, lastError)
- Connection history table structure (separate model or JSON column on RemotePanel)
- Health check implementation details (cron-like, setInterval, or background worker)
- Exact badge thresholds for latency-based status colors

</decisions>
