# Phase 12.4: Sync apply & WS cache invalidation - Context

**Gathered:** 2026-05-01
**Status:** Ready for planning

<domain>
## Phase Boundary

Remote `/api/sync/apply` endpoint exists on the receiving panel so config-applier doesn't get 404. Dashboard/resource queries invalidate on relevant WebSocket events instead of relying on polling intervals alone.

Gap: GAPL-01, GAPL-02 from v1.0 audit.

**GAPL-01:** `config-applier.ts` sends POST to remote `/api/sync/apply` but the endpoint doesn't exist — returns 404 which is silently treated as "success with warning". The endpoint needs to actually apply the received config to AWG/3x-ui services.

**GAPL-02:** `providers.tsx` has WebSocket listener and React Query but they're not connected — WS events don't trigger query invalidation. Dashboard/resources still rely on polling intervals (30s staleTime, 30s refetchInterval).

</domain>

<decisions>
## Implementation Decisions

### Claude's Discretion
All implementation choices at Claude's discretion — infrastructure phase.

Key constraints:
- `/api/sync/receive` already exists and stores config in CachedPanelConfig
- `/api/sync/apply` must read from CachedPanelConfig and apply to services
- `config-applier.ts` already has the 404 fallback — once endpoint exists, the fallback becomes dead code (clean up)
- WS-driven invalidation: in `providers.tsx`, watch `lastEvent` and call `queryClient.invalidateQueries()` for relevant query keys when events arrive
- Keep polling as fallback — don't remove it, just make WS invalidation the primary trigger

</decisions>
