# Phase 11.3: Panel Sync Protocol & Hybrid Autonomy - Context

**Gathered:** 2026-04-30
**Status:** Ready for planning

<domain>
## Phase Boundary

Central panel can push configurations to remote panels over the Tailscale mesh, and remote panels cache their last-known-good config to operate autonomously when central is unreachable. This phase implements the config push transport, local config caching, and autonomous fallback mechanism.

</domain>

<decisions>
## Implementation Decisions

### Push Transport & Auth
- API key header (`X-API-Key`) for push request authentication — reuse existing `apiKeyHash` from RemotePanel model
- 3 retries with exponential backoff (1s, 2s, 4s), then mark as failed
- Sequential push to each panel (simple, predictable errors) — 1-3 panels
- 15s request timeout per panel (accounts for config processing time on remote)

### Config Payload & Caching
- JSON per-panel chain config with `panelRole`, `chainNodes[]`, `routingRules[]`
- Zod schema validation on receiver side — reject invalid configs with clear error
- New Prisma model `CachedPanelConfig` — single row per panel with version, config JSON, receivedAt
- Simple incrementing integer `configVersion` — compare versions to detect changes

### Hybrid Autonomy & Resync
- Central-down detection: health check failure x3 consecutive (leverages existing 30s interval)
- Fallback behavior: log warning, continue serving cached config, emit WebSocket event for UI notification
- Automatic resync on next successful health check after fallback mode — push latest config
- Sync acknowledgment: receiver returns `{applied: true, configVersion}` — idempotent

### Claude's Discretion
- Exact panelRole values and chainNodes structure within the JSON payload
- CachedPanelConfig schema details (additional fields beyond decided ones)
- WebSocket event payload structure for fallback notifications
- How config version is incremented (central-side counter vs database sequence)

</decisions>

<specifics>
## Specific Ideas

- Push should be idempotent — same config version pushed twice should be a no-op on the receiver
- Fallback mode should be visible in UI — the panels page should show "running on cached config" status
- Config diff between current cached and incoming push would be useful for debugging

</specifics>
